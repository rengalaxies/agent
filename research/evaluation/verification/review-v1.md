# Редакторское ревью методики

14.11.2026. Отдельный агент получил документы без истории чата и прочитал их как будущий implementer evaluator. Это техническое/методологическое ревью по builder-check, **не независимая человеческая разметка, не E1/E2 и не результат оценки качества ImpactMap**. Отчёт ниже фиксирует обе полученные существенные находки и решения исполнителя.

## 1. Hints и отрицательные контроли без API-изменения

Находка: ready input требовал непустой список «изменённых операций», но blueprint содержал README-only и unchanged-API кейсы. Это оставляло куратору выбор, который меняет LS1 и FAR.

Решение: hints означают операции **под рассмотрением**, а не утверждение о наличии изменения. Источник — все явно названные операции в task либо изменённые объявления provider diff, до gold. Каждый hint имеет basis_kind и hash артефакта. Если оснований нет, hints пусты; LS1 возвращает пустой ответ с query_not_identified, не доказательство безопасности. Кейс остаётся в назначенном denominator. Schema ready допускает пустой список. Правило не зависит от stratum.

Проверка: новая проверка `ready no-API-change control: empty operation hints accepted` сначала завершилась AssertionError на старой схеме; после изменения schema и protocol прошла. Это проверка контракта, не запуск поискового baseline.

## 2. Дедупликация непривязываемых кандидатов

Находка: U учитывает уникальные предупреждения, но без operation нельзя дедуплицировать по обычной pair identity. Неограниченный candidate_id позволял считать одинаковый finding/check/claim по-разному.

Решение: явные cross-refs объединяются прежде подсчёта. Для оставшегося unbound вывода — один bucket на case и нормализованное consumer designation. Все raw_refs сохраняются; возможные операции не размножают FP. ID — SHA256 канонического JSON `[case_id, consumer_designation, "UNBOUND"]`. Если операция однозначна, запись относится к P. Формула и ограничения описаны в разделе 6 протокола; сумма U выводится отдельно. Проверка canonical ID и реальности links между файлами относится к evaluator 06, schema сама не доказывает хеш.

Проверка: schema отвергает arbitrary ID/старую форму без consumer designation и набора raw_refs; тест находится в `check_contracts.py`. Никакой существующий scorer этим не объявлен готовым.

## Итог

Обе существенные неоднозначности уточнены. После одной правки выполнена техническая проверка схем, draft-шаблонов, ошибочных fixtures, квот и арифметики; фактический результат — [contract-checks.json](contract-checks.json). Повторное ревью агентом после исправлений не выполнялось; финальное сопоставление с AC и исправлениями сделал исполнитель. Утверждение thresholds человеком и независимые эмпирические эксперты остаются будущими действиями 06, не результатом этого ревью.
