# Протокол закрытого evaluation-набора 0.3.0

## Статус

Evaluation-набор подготовлен и структурно проверен, но основной эксперимент E3 на нём не выполнялся. Значение `main_e3_executed: false` зафиксировано в `experiments/evaluation-catalog.yaml`.

## Состав

- 40 новых сценариев, отсутствующих в development-наборе;
- 20 опасных и 20 допустимых изменений;
- F1 и F2 - по 8 сценариев, F3-F6 - по 6 сценариев;
- в каждом семействе присутствуют оба класса;
- представлены сценарии с одним и двумя активными потребителями;
- каждый шаблон имеет отдельный `template_group`, который не используется в development-наборе;
- структура схемы не меняется: проверяются скрытые семантические изменения.

## Разделение данных

- входы валидаторов: `scenarios/evaluation/*.yaml`;
- фиксированная политика baseline: `policies/v1-ind.yaml`;
- эталонные классы и локальные решения: `oracles/evaluation.yaml`;
- состав, группы и контрольные хеши: `experiments/evaluation-catalog.yaml`;
- конфигурация будущего запуска: `experiments/evaluation.yaml`.

Oracle не передаётся `ReleaseEngine`. Протокол 0.3.0 остаётся архивной контрольной точкой; для будущего запуска в рабочей ветке 0.3.1 реализована более строгая двухпроцессная цепочка из `docs/e3-execution-chain-0.3.1.md`. Сначала должны завершиться все 160 прогонов валидаторов и зафиксироваться хеш raw results. Только отдельный scoring-процесс может проверить этот хеш, загрузить oracle и рассчитать метрики.

## Правила формирования эталона

Эталон формируется из версии `ConsumerObligation`, действующей в карточке сценария, а не из результата V0, V1-ind, V1-oracle или V2.

- Если новый контракт нарушает хотя бы одно обязательство активного потребителя, локальный эталон этого потребителя равен `REJECT`.
- Если обязательство выполнено напрямую или через допустимую проверенную миграцию, локальный эталон равен `ACCEPT`.
- Глобальный эталон формируется по правилу `REJECT > NEEDS_REVIEW > ACCEPT`.
- В основной бинарной части каталога опасному сценарию соответствует `REJECT`, допустимому - `ACCEPT`.
- Сценарии неопределённости и `NEEDS_REVIEW` проверяются отдельно в E4 и не подмешиваются в бинарный primary contrast E3.

## Проверки до E3

Разрешены только проверки, не использующие результаты режимов для изменения набора:

- парсинг Pydantic-моделями;
- уникальность идентификаторов;
- точное покрытие oracle;
- баланс классов и семейств;
- совпадение множества потребителей в сценарии и oracle;
- отсутствие меток и baseline-правил во входных YAML;
- неизменность структуры схемы;
- соответствие изменённых полей заявленному семейству;
- фиксация SHA-256 каталога, oracle, baseline и генератора.

До подтверждения автором работы запрещено запускать scored E3, менять V0/V1-ind/V1-oracle/V2, дополнять baseline правилами из evaluation-сценариев или исправлять сценарий из-за неудобного результата режима.

## Правило после запуска

Основной E3 выполняется один раз на зафиксированном commit. Если обнаружится техническая ошибка, исходный запуск сохраняется, причина документируется, исправление получает новую версию, а подтверждающий вывод переносится на новый evaluation-набор. Повтор детерминированного сценария не считается новой единицей наблюдения.

## Ограничение

Набор сформирован внутри проекта без независимой экспертной разметки. Он позволяет провести воспроизводимое внутреннее сравнение V2 и V1-ind, но сам по себе не подтверждает внешнюю валидность и реалистичность промышленных частот сценариев.
