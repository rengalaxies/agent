## Что считается наблюдением

Наблюдение: результат запуска кода, теста или замера с указанным корпусом
и версией, либо прямое чтение кода. Интерпретация: вывод автора аудита из
наблюдений. Гипотеза: утверждение о клиентах, рынке, пользе или будущем
поведении, которое никто не проверял.

## Противоречия и как они разрешены

| № | Противоречие | Разрешение | Основание решения |
|---|---|---|---|
| K1 | Основной пользователь: coding agent (H2, PRODUCT.md) или разработчик через UI (UX-аудит) | В пилоте пользователь результата это автор изменения, человек. Агент участвует как исполнитель в одной из веток сравнения. UI в пилоте не используется | Ни одна сторона не наблюдала пользователя. Последствия ошибки несёт человек, поэтому мерить пользу надо на его решении |
| K2 | Встроенный агент сопровождения входит в продукт (H4) или модель не нужна (ADR-007) | Модель в пилоте выключена | O9: в текущем протоколе модель по построению не добавляет рёбер. O10: в корпоративной сети клиент модели не подключится |
| K3 | Аудит архитектуры ставит 6 недель инженерных шагов 1-4 до проверки пользы. Исследование Ontonet запрещает продуктовый код до внешнего случая | Ни то, ни другое. Делаем только то, без чего пилот измерит заранее известный дефект: шум пробелов, молчание на неклассифицированном изменении, привязку к коммиту, устаревание исправлений. Шаги 1-2 аудита (журнал, ядро в процессе демо, пакет) не нужны: пилот идёт через CLI, без демо | O3, O5, O8, O14 гарантируют провал пилота по причинам, которые уже известны. Шаги 1-2 лечат демо, которое в пилоте не участвует |
| K4 | Демо принято как работающее (O12), UX-аудит считает его непонятным (I3) | Противоречия нет: механика работает на синтетике, понятность не проверена. Пилот не опирается ни на то, ни на другое | |
| K5 | Синтетика показывает 0 пропусков в профиле, реальный код даёт тысячи пробелов (O5) и ноль рёбер (O6) | Синтетический результат не переносится на клиента. Применимость к его коду меряется первой, до любого обещания пользы | O1, O2: самые обычные формы вызова не входят в грамматику |
| K6 | Конкуренты: DG-каталоги и миграционные продукты (competitive-evidence 16.10) или coding agent (I1) | Принимаем I1. Документ 16.10 описывал другой продукт, исполнителя изменений | Пересечение с DG касалось исполнения и согласований, которых в текущем модуле нет |
| K7 | product-focus называет первым сегментом "команды с межсервисными интеграциями", а язык велит выбирать по реальному случаю. Код при этом уже привязан к Python `requests` | Сегмент сужен до тех, чей код попадает в существующую грамматику. Расширение грамматики только по пробе на коде клиента и не больше двух форм | Расширять профиль вслепую это гонка с агентом, который поддерживает все стеки (I1) |

## Что из этого следует для пилота

1. Сегмент определяется кодом, который уже есть: Python, `requests`,
   провайдер на FastAPI или с OpenAPI JSON. Других стеков в пилоте нет.
2. Первое действие с клиентом это проба покрытия на его коде. Без неё
   любое обещание пользы опирается на синтетику.
3. Предмет пилота: список затронутых потребителей с проверяемыми
   основаниями, а не классификация последствий. Классификация есть для
   двух узких случаев, список потребителей нужен при любом изменении.
4. Модель выключена, UI не используется, работу инструмента
   сопровождает наш инженер, и это часть предложения.
5. Критерии продолжения берутся из roast v4 §3 без изменений. Их записали
   до данных, менять их сейчас значит подгонять.
