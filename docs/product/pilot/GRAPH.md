# Роль обновляемого графа

Граф — память сервиса об основаниях связей и контекст новой задачи. Он
сокращает повторный поиск, показывает путь влияния и свежесть. Это целевая
архитектура: сейчас ядро пересчитывает карту и хранит историю контекстов.

## Пример

Reporting вызывает GET /orders в Orders: файл/строки из кода и наблюдаемое
Reporting → Orders за указанное окно. Jira предлагает ограничить страницу;
агент находит связь в графе. PR позволяет уточнить конкретное изменение.
Нагрузка помогает приоритизировать проверку, но не доказывает поломку.
Runtime-ребро между сервисами не становится связью конкретной операции,
если в наблюдении нет маршрута/метода.

| Объект | Данные |
|---|---|
| Сервис / операция | Стабильная идентичность, окружение, репозиторий, объявление |
| Место вызова | Потребитель, файл/строки, версия |
| Наблюдение | Источник, стороны, окно, доступные агрегаты |
| Связь | Тип, основания, версия/окно, актуальность, статус |
| Jira / PR | Намерение/diff, анализ и версия графа |
| Владение | Источник кандидата во владельцы, не полномочие согласовать |

Идентичности, удаление/инвалидизация и периоды свежести фиксируются перед
реализацией. Ребро из кода, наблюдаемый вызов и кандидат модели раздельны.
Модель не повышает доверие другой модели одним согласием.

Изменение обновляет затронутые основания. Удаление источника, смена прав и
конфликт не стирают историю незаметно. При отказе видна область устаревания.
Отсутствие трафика, sampling и неинструментированный сервис не доказывают
отсутствия потребителя. Человеку доступен простой просмотр пути и источников;
большой визуальный редактор не требуется.

[Tempo service graphs](https://grafana.com/docs/tempo/latest/metrics-from-traces/service_graphs/)
строят связи из трасс. Дашборд CPU или суммарного RPS не сообщает, какая
команда вызывает какую операцию. Коннектор выбирается по реальным данным,
с областью пропусков и окном наблюдения.
