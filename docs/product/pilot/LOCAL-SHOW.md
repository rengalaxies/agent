# Первый разговор: изменение API и его потребители

Пользователь показа — разработчик/ревьюер внутреннего HTTP API. Его вопрос:
«Кого позвать в review и что проверить перед merge?» После показа нужно решить,
помогают ли проверяемые основания выбрать следующую проверку, а не разрешить релиз.

Это существующее синтетическое HTTP-приложение, MODEL OFF. В нём Orders/Reporting
получают 250 → 100 → 250 записей. Другая фикстура автономного Jira/PR сервиса использует
100 → 20: её нельзя смешивать с этим показом. Клиентская полезность не измерена.
Известные main/profile-4 ошибки намерения и деклараций описаны в отчёте проверки;
это не инструмент для самостоятельного подключения незнакомого проекта без квалификации.

## Из чистого checkout

Linux, Python 3.12, Docker Engine с Compose, обычный пользователь с доступом к Docker
socket; свободный 127.0.0.1:18081, браузер. Сеть нужна для wheels/base image, не для модели.
Не запускать команды как root и не применять их на общей ВМ. Из корня checkout:

```bash
python3.12 -m venv .venv
. .venv/bin/activate
export PYTHONPATH=src:.
python -m pip install --require-hashes -r infra/agent_graph_demo/requirements.lock
mkdir -p work/wheels
python -m pip download --only-binary=:all: --require-hashes -r infra/agent_graph_demo/requirements.lock --dest work/wheels
docker build --network=none -f infra/agent_graph_demo/Dockerfile --build-arg PRODUCT_SHA="$(git rev-parse HEAD)" -t agent-graph-demo:local-show .
DEMO_IMAGE_ID="$(docker image inspect agent-graph-demo:local-show --format '{{.Id}}')"
python tools/agent_graph_demo/local_show.py --directory work/local-show init --image "$DEMO_IMAGE_ID"
python tools/agent_graph_demo/local_show.py --directory work/local-show serve
```

Init просит локальный пароль минимум 16 символов; значение не печатается.
Открыть http://127.0.0.1:18081/, username operator. Никаких Jira/App/cloud credentials.
Конфигурация и SQLite остаются в work/local-show: не публиковать их как материалы показа.
Не повторять init поверх существующей установки. После перезапуска использовать serve:
история и прежние показы сохраняются. При обновлении кода не менять SHA вручную в state;
использовать отдельный каталог показа, сохранив прежнюю историю.

Второй терминал: тот же checkout/venv/PYTHONPATH. SESSION — UUID показанный в
«Техническое состояние и сброс» работающего UI. Перед run версия должна быть подготовлена
и анализ закончен. Версия и generation проверяются runner, одновременный второй оператор
не поддерживается.

```bash
python tools/agent_graph_demo/local_show.py --directory work/local-show run --session SESSION --version A
# После соответствующего действия UI повторить с --version B, затем D, затем E.
python tools/agent_graph_demo/local_show.py --directory work/local-show observe
python tools/agent_graph_demo/local_show.py --directory work/local-show stop
```

Observe освежает факт запущенной версии, а не повторяет тест. Без observe более 120 секунд
запущенная версия станет «Не подтверждено». После run нажать «Получить результаты».
Stop останавливает только собственный exact sandbox через прежний guard; не docker prune.
Для UNKNOWN/STARTING требуется явная reconciliation по основному RUNBOOK, не удаление БД.

## Сценарий разговора

1. Новый показ → обследовать исходники. Слева Reporting/Billing → Orders и Health → Status.
   Выбор связи открывает точный источник. Совпавшая строка /orders сама не связывает Health с Orders.
2. Оператор run A. Проверка: Reporting/Billing 250/250, PASS; запущена исходная версия.
3. «Уменьшить страницу Orders до 100». Предложена новая версия, запущена ещё старая.
   Reporting: потенциальная потеря полноты, цитата одиночного вызова и diff.
   Billing обходит страницы; его RECHECK_REQUIRED не означает установленную поломку.
4. Run B: Reporting 100/250, пропущено 150; Billing 250/250, Health/Status работает.
   Это наблюдённый результат runner на фикстуре, а не вывод статического анализатора.
5. «Исправить пагинацию Reporting», затем run D. Reporting снова 250/250.
   В статическом сравнении B→D нет нового изменения API: ограниченный вывод/воздержание
   не означает доказанной совместимости. Проверка исполнения — отдельное основание.
6. «Добавить потребителя Export», затем run E. Новая связь из исходника; Export 250/250.
7. Открыть B в истории: старый риск и прежняя проверка остаются историческими.
   Вернуться к текущему результату. Если graph API недоступен, старые цитаты скрыты,
   видна ошибка и локальная кнопка повторной загрузки.
8. Stop в терминале, затем «Сбросить после остановки» в UI. Новый UUID/исходная версия,
   прежняя история доступна в сохранённых показах. Пять последовательных показов проверяет
   существующая acceptance. После stop остановить backend Ctrl+C. Повтор — serve, не init.

Источник анализа/графа читается worker автоматически после действия UI.
Запуск сервисов и независимого по алгоритму oracle требует оператора.
Кнопка исправления применяет заранее подготовленный код, не LLM и не автономный repair.
Сохранённый job в истории явно помечен и не выдаётся за новый анализ.

## Что предлагаем проверить участнику

Один согласованный HTTP API и его Python-потребители, доступ к разрешённым репозиториям,
версии до/после, источник требований, при наличии — безопасные журналы вызовов.
Сначала владелец данных определяет допустимые операции и права; команда принимает
решение о merge. Этот локальный показ не требует передавать клиентские данные вообще.
Подключение внешних источников/публикация обсуждаются отдельно по CONNECT.md.

Сравнить тот же конкретный вопрос обычным поиском, сильным coding agent и сервисом
при одинаковых данных/правах. Измерять реальные минуты поиска и проверки оснований,
ложные/пропущенные связи, время подключения/поддержки корпуса и нагрузку на разработчиков.
Записать подготовку тоже; не подменять её временем машины. Пороги согласовать до результатов.

- Полезно: основания меняют конкретное решение (кого позвать, что проверить), затраты
  приемлемы, ложные связи не мешают. Это проверяемая гипотеза.
- Бесполезно: вывод не добавляет действия относительно обычного процесса либо его проверка
  и подготовка дороже пользы.
- Неубедительно: нет независимых ожиданий/знаменателя пропусков, неравные доступы,
  мало случаев или измерений. Не превращать это в успех.

После показа: какое изменение рассматривалось? Кто затронут и почему? Где риск,
а где тест? Чего не хватало для решения? Что оказалось ложным/пропущенным?
Как бы вы решили вопрос сегодня? Кто готов предоставить независимо выбранный случай?
Протокол измерения — PROTOCOL.md, условия/отзыв данных — CONNECT.md.
Человеческого пилота, преимущества над агентом и работы на клиентском корпусе пока нет.
