## Целевой минимальный сценарий

Задача без PR → извлечение намерения → кандидаты операций/сервисов → проверяемая
область влияния, основания, владельцы или UNKNOWN, уточнения → комментарий после
проверки правил публикации → изменение задачи обновляет результат → PR уточняет
предположение → исправление и повторная проверка сохраняют историю.

Первый пилот: один трекер, выделенный контур, ограниченный поддерживаемый HTTP/Python
корпус, доверенный оператор, решение человека. До PR влияние предварительное;
сходство задач не доказывает техническую зависимость. Нет обещания общего анализа
всех языков, транзитивной полноты, автономного исправления или атомарности DB/API.

Jira остаётся первым адаптером из-за существующего кода. Если первый участник
предоставляет только Kaiten/Яндекс Трекер, порядок адаптеров пересматривается явно.
MCP — транспорт, REST — равноправный путь, общий контракт скрывает различия.
REST Jira Cloud не переписывается на MCP ради самого протокола. Data Center отдельно.

## Порядок и правила завершения

I0 фиксирует критерии. I1/I2/I3/I4 можно вести параллельно после согласования
контракта между I1/I2; не менять общие файлы одновременно без разделения владения.
I5 требует I2/I3/I4, но I6 локально не ждёт ВМ. I7 после I1, не блокирует I5/I8.
I8 требует настоящего раннего сценария и участника; предварительные разговоры о
пилоте допустимы раньше. Code/LOCAL/CI/LIVE/participant фиксируются раздельно.

Первый режим подключения может использовать периодическое чтение с checkpoint
и повторным fetch вместо webhook: это не требует публичного входящего HTTPS.
Проверить доступность полной инкрементальной выборки/пагинации, а не считать search
полным обходом. Частота/задержка явны. Webhook доставку, когда подключена, принимать отдельно.

Adapter: normalize только внешний формат; provider остаётся в идентичности ресурса.
Core: intention→candidate retrieval→evidence-backed impact→publication policy.
Каждый вывод связан с версией задачи, graph basis и источниками. Документация,
комментарии и MCP results — данные, не инструкции на выполнение инструментов.
Изменение задачи отзывает прежнюю применимость. Ровно-одна внешняя запись при
неатомарном API не обещается; проверяются adoption/dedup/reconciliation/нет self-loop.

I2 не разрешает вызовы модели: сначала отдельный протокол и разрешённый бюджет.
Можно применять детерминированный matcher, словарь и подтверждение человеком;
если этого недостаточно для бизнес-формулировок, это продуктовый gap, не PASS.
Порог публикации и требования к полезности фиксируются до просмотра итоговых случаев,
не подбираются ради красивого результата. Часть ожиданий задаёт независимый человек.

I5 минимально не требует UI, если продуктовая поверхность — комментарий трекера.
I6 не должен выдавать отдельное UI demo за production inbox: источник/версия результата
и prepared repair явно обозначены. Service archive не содержит Docker UI artifact.

## Что продаём и кому

Предложение: предварительная проверка межсервисного влияния при постановке задачи,
затем уточнение по PR, с проверяемыми основаниями и ограничениями. Покупатель-гипотеза:
техлид/руководитель платформы/архитектор команды с повторяющимися межсервисными изменениями.
Не продавать обещание полного графа из одного токена, автономного исправления или
доказанной экономии. Помимо трекера нужны разрешённые источники системы/графа.

Первый коммерческий формат — ограниченный пилот с фиксированным объёмом подключения,
работ и отчётом, критериями до запуска, затем решение о подписке/сопровождении.
Оплата фиксированных работ не означает обязательного положительного вывода о пользе.
Цена/длительность не установлены: уточняются после оценки доступа, объёма и поддержки.
Возможная база дальнейшего тарифа — согласованный контур сервисов/репозиториев и
нагрузка; это гипотеза ценообразования, не подтверждённая готовность платить.

Измерять: оправданно найденные затронутые команды до PR, FP/FN/unknown при известном
знаменателе, изменившееся решение/проверку, время поиска и проверки оснований,
подготовку корпуса, поддержку и шум. Не приписывать предотвращённые инциденты
непроизошедшим событиям и не заменять время человека длительностью CI.

## Рубежи

- Сейчас: технический прототип/синтетическое демо есть, не подтверждённая польза.
- Демо цели: ранний task-first сценарий с понятными основаниями и честной неизвестностью.
- Технический MVP: один реальный tracker+Git контур, I5 и эксплуатация пройдены.
- Пилот: участник работает с согласованными реальными случаями, I8 даёт измерения.
- Повторяемая продажа: понятен труд подключения, есть подтверждённая польза и
  обязательства, которые продукт способен выполнять. Массовые продажи пока не доказаны.

Не входят в первый пилот: пять production-коннекторов, все языки/протоколы,
автономные правки/merge, общекорпоративный SSO/multitenancy. Если клиент требует
изоляцию/SSO, это предварительное условие его контура, не скрытое обещание.
