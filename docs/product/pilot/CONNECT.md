# Подключение к пилоту, остановка и выход

29.10.2026. Порядок для участника закрытого пилота. Технические детали установки
лежат в [runbook сервиса](../../../infra/agent_service/README.md), параметры App и
секретов в [M2-A](../../implementation/autonomous-mvp/m2-a-2026-10-28/OWNER-AND-M3.md).
Постоянного инженера или разметчика со стороны поставщика в схеме нет. Если пилоту
понадобится постоянная ручная работа, она записывается как недостаток готовности.

## Вход: что согласовать до установки

| Пункт | Что фиксируем | Кто решает |
|---|---|---|
| Репозитории | Список `owner/repo`, какая ветка считается основной, какие repo только читаются | Владелец кода участника |
| Jira | Сайт, один проект, технический аккаунт; или «без Jira» | Администратор Jira |
| Данные | Код и тексты задач обрабатываются на ВМ сервиса; модель выключена; внешних вызовов нет, кроме GitHub/Jira API | Владелец данных участника |
| Права App | Metadata, Contents, Pull requests: read. Issues: write. Только выбранные репозитории | Администратор GitHub |
| Identity | App ID, installation ID, login бота. Сервис пишет только от этого бота | Администратор GitHub |
| Секреты | PEM App, webhook secrets, Jira token хранятся в хранилище секретов участника и на ВМ в root-only файле. Не в Git, чате, логах и артефактах | Администратор участника |
| Публикация | Первая неделя `publication: dry_run`: комментарии пишутся в файлы на ВМ. Затем `live` на тех же repo | Участник и поставщик вместе |
| Копии | Ежедневная копия state, 7 штук; копия перед каждым обновлением | Оператор ВМ |
| Инциденты | Кто принимает сообщение и в какие часы | Обе стороны, письменно |

## Установка (один раз)

1. Оператор ВМ ставит согласованный релиз по runbook: скачать архив, сверить SHA256 и
   manifest, `box install` с отдельным `installation_id` и пустым state.
2. Администратор GitHub создаёт App, ставит её на выбранные repo и передаёт IDs.
   PEM передаётся только через хранилище секретов.
3. Оператор кладёт секреты в `/etc/agent-service/secrets.env` и PEM рядом, права root
   и сервисного пользователя.
4. `agent-service-box doctor` и probe identity: App, installation, список repo, bot.
   Без PASS дальше не идём.
5. Администраторы регистрируют webhook на HTTPS-адрес: GitHub `pull_request`,
   `issue_comment`; Jira admin webhook с secret на один проект.
6. Пробное событие: тестовый PR в выбранном repo. В `dry_run` проверяем файл
   комментария, затем переключаем на `live`.

Человеческие минуты на каждом шаге записываются в журнал пилота.

## Как остановить публикацию без потери истории

| Ситуация | Действие | Что сохраняется |
|---|---|---|
| Комментарии мешают или ошибочны | Переключить `publication: dry_run` и перезапустить сервис | Очередь и история в SQLite; новые результаты пишутся в файлы |
| Нужно остановить всё | `systemctl stop agent-service agent-service-sync.timer` | State на диске; webhook-доставки GitHub можно переотправить позже, пропущенное подберёт сверка |
| Отозвать доступ немедленно | Suspend или uninstall App, отключить Jira-аккаунт | State на ВМ; сервис покажет 401/403 в `/status` и не будет повторять запись |
| Плохой релиз | `box rollback` на прежний релиз | Совместимый state остаётся; несовместимый восстанавливается из копии `pre-update` |

Ни одно действие не удаляет историю. Восстановление SQLite из копии не откатывает
комментарии, которые уже опубликованы. Пока сервис стоит, последний комментарий
остаётся видимым и может быть устаревшим: верхней границы у этого окна нет.

## Инцидент

Инцидент: ложный или вредный комментарий, утечка, падение сервиса дольше суток,
запись не туда. Порядок: остановить публикацию (таблица выше), записать request и
delivery IDs, comment ID и версию релиза, сообщить второй стороне. Разбор идёт по
истории state и журналу systemd. Секреты при разборе не печатаются.

## Выход из пилота

1. Остановить сервис и таймер.
2. Участник удаляет App из организации и webhook, отзывает Jira token.
3. Комментарии бота остаются в PR и задачах. Участник может удалить их сам; поставщик
   этого не делает.
4. По решению участника: передать ему архив state или удалить state, копии и зеркала
   на ВМ с записью, что именно удалено.
5. Удалить ВМ, если она создавалась для пилота.

Выход не требует участия поставщика, кроме шага 4, если state хранится у него.
