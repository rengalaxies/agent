## Исходное положение

Внешних пользователей и записанных интервью нет. Ядро честно работает на
синтетике и узко на коде: Python `requests` с URL из литерала или константы
того же файла, FastAPI или OpenAPI JSON у поставщика, три вида изменений.
f-строки и адреса из настроек, самые обычные формы в реальном коде, дают
пробел. Любое изменение операции вне трёх классов даёт тишину. На реальных
репозиториях тысячи шумовых пробелов. Модель в текущем протоколе не
добавляет рёбер. UI экспертно признан трудным для понимания, людьми не
проверялся.

Подтверждённое кодом отличие одно: основание каждой связи привязано к
байтам файла и строкам, отрицательный ответ ограничен списком мест, куда
инструмент не смог заглянуть, свежесть вычисляется. Главный конкурент:
coding agent клиента, который ищет в любом стеке, но не даёт ни
проверяемого основания, ни ограниченного "не найдено".

Подробно в [EVIDENCE.md](EVIDENCE.md).

## Стратегия этапа

**Проверить на реальных изменениях одного клиента, даёт ли проверяемый
список потребителей пользу сверх его coding agent. Ничего другого на этом
этапе не строить.**

Три следствия:

1. Сегмент выбирает код, а не рынок. Ядро применимо только там, где
   потребители на Python вызывают внутренний API через `requests`. Это
   прежде всего платформы данных и внутренние backend-сервисы, которые
   потребляют DAG, отчёты и ML-пайплайны других команд. Расширять стек до
   доказательства пользы значит соревноваться с агентом в его сильной стороне.
2. Первая проверка это не польза, а применимость. Проба покрытия на коде
   клиента до любых обещаний. Если два клиента подряд её не проходят,
   продукт в нынешнем виде не нужен рынку, и это ответ.
3. Пилот сопровождаемый. Наш инженер делает подключение и разбор
   пробелов, его часы входят в сравнение. Иначе мы бы сравнивали готовый
   агент клиента с инструментом, которого без нас нет.

## Кому и почему он согласится

Техлиду команды, которая владеет внутренним API и меняет его хотя бы раз в
месяц, а потребители в чужих репозиториях. Неопределённость возникает при
планировании и ревью PR: "все ли потребители учтены?". Сейчас ответ
собирают поиском по строке пути, вопросом в чат и памятью старших. Цена
ошибки ложится на команду-потребителя: в худшем случае отчёт молча теряет
данные. Решение о пилоте принимает техлид вместе с тем, кто выдаёт доступ к
репозиториям; о покупке, по гипотезе, руководитель платформы.

Он согласится, если интервью подтвердит, что такая неопределённость у него
реально была за последние 90 дней. Его выгода от пилота при любом исходе:
отчёты с точными ссылками по каждому своему изменению, которые можно сразу
вставить в PR, и измеренная доля потребителей, которую его coding agent
пропускает на его собственном коде. Его цена: около 12-16 часов на 2-3
человек за 6 недель. Эти часы и согласие на доступ и есть первая проверка
спроса.

## Предложение в одной строке

Клиент даёт доступ на чтение к репозиториям поставщика и потребителей и
сообщает о PR, меняющих API → наш инженер с инструментом в контуре клиента
строит по каждому изменению список затронутых мест вызова → автор
получает отчёт со ссылками на строки в коммите, тем, что проверить, и
списком неразобранных мест → вставляет его в PR и зовёт владельцев →
качество проверяется слепым эталоном разметчика клиента и сравнением с
текущим процессом и coding agent без графа.

## Рекомендуемое решение владельцу

**Какой пилот.** Сопровождаемый пилот "проверяемый список потребителей для
изменений внутреннего API": 12 реальных изменений (6 из истории, 6 живых),
около 6 недель после получения доступа, три ветки сравнения, критерии
продолжения из v4 без изменений.

**Кому.** Одной команде-владельцу внутреннего API на FastAPI или с OpenAPI
JSON, у которого не меньше трёх потребителей на Python с `requests` в
репозиториях других команд, и которая прошла пробу покрытия. Предпочтительно
там, где разрешён coding agent.

**С каким обещанием.** "По каждому изменению вашего API за время пилота вы
получите список мест вызова у потребителей с точной строкой в коммите,
явный список того, что инструмент не разобрал, и измеренное сравнение с
вашим текущим процессом и вашим coding agent. Экономию не обещаем: её
меряем". Решение о выпуске остаётся у команды. Модель не используется, код
не покидает контур.

**Сроки и остановка.** Клиента, согласного на пробу, ищем до 13.11.2026. Нет
такого клиента, или два клиента подряд не прошли пробу, или модуль пропустил
больше серьёзных потребителей, чем агент без него: продуктовый трек
останавливается, ядро остаётся результатом ВКР.

**Что делаем сразу.** Слить PR #45 после ревью, написать скрипт пробы (B7),
начать проблемные интервью по `docs/launch-2026-10/02-STAKEHOLDER-INTERVIEWS-RU-EN.md`.
Остальной backlog (около 2-2,5 недель) только после согласия клиента на
пробу.
