# Экономическая логика предложения

Редакция 24.10.2026. Цены здесь нет, и это намеренно. Прежние 100-150 тыс.
руб. отозваны (`docs/product-focus-2026-10-20.md` §8), новых данных для цены
нет. Ниже: из чего складываются наши затраты, за что потенциально платят,
какие данные нужны и как проверить цену.

## 1. Наши затраты

### Пилот у одного клиента

Оценки до замера. Пилот меряет их по журналу труда ([PROTOCOL.md](PROTOCOL.md) §9).

| Статья | Оценка, часы нашей стороны | Чем определяется |
|---|---|---|
| Интервью и подготовка | 3 | |
| Проба покрытия | 6-8 | Число репозиториев потребителей и мест вызова |
| Подключение: среда, policy, соответствие адресов | 8-12 | Число адресов и окружений, порядок выдачи доступа |
| Анализ и отчёт, A2 | 1-2 на задачу, 12-24 на серию | Число пробелов у файлов с вызовами API |
| Оператор A1, если клиент поручает его нам | 0,5-0,75 на задачу, 6-9 на серию | Второй человек нашей стороны |
| Координация, журналы, эталон | 8-10 | |
| Итоговый анализ и встреча | 8-10 | |
| **Итого** | **около 50-75** | Без A1 нижняя граница |

Инфраструктура: машина клиента, CPU. Анализ корпуса на 1000 файлов занимает
секунды (аудит архитектуры, замер 3,2 с на `analyze_change`). GPU и модель не
нужны: в пилоте модель выключена, расход на токены 0.

Потерянные затраты: проба у клиента, который её не прошёл (около 10 ч), и
интервью без следующего шага. Их тоже записываем: это цена привлечения.

### Одноразовая разработка до пилота

[BACKLOG.md](BACKLOG.md): около 2,5-3,5 недель одного разработчика, знакомого
с кодом. Делается только после согласия клиента на пробу, кроме B7 и B8.

### Если сервис продолжится

| Статья | Что меряем в пилоте, чтобы оценить |
|---|---|
| Работа инженера на изменение | Тёплые часы A2 на задачу |
| Подключение нового API или команды | Холодные часы подключения |
| Поддержка формы вызова, которой нет в грамматике | Часы на B6 у первого клиента |
| Сопровождение версий ядра | Не меряется в пилоте, оценка позже |

## 2. За какую единицу ценности могут платить

| Единица | За | Против | Что должно подтвердиться |
|---|---|---|---|
| API поставщика под наблюдением в месяц | Совпадает с гипотезой о памяти: польза растёт на серии изменений одного API. Предсказуемо для клиента и для нас | Если API меняется редко, клиент платит за простой | Изменений на API в месяц достаточно, чтобы тёплая экономия покрывала цену |
| Проанализированное изменение (PR) | Прямо привязана к результату и к нашим часам на задачу | Наказывает частое использование, плохо продаётся как подписка | Клиенту важна цена отдельного ответа |
| Место пользователя | Привычно для инструментов разработки | Наша ценность на API, а не на человека. Пользователь отчёта появляется раз в несколько недель | Почти наверняка не подходит |
| Предотвращённый инцидент | Ближе всего к ценности для покупателя | На 12 задачах не измерить, спор о том, был бы инцидент или нет | Не годится для первой цены |
| Проектная лицензия в контуре плюс поддержка | Привычная форма закупки в крупных компаниях | Требует упакованного продукта, которого нет. Сопровождение инженером в неё не укладывается | Позже, после автоматизации подключения |

Рабочая гипотеза для проверки: **API поставщика под наблюдением в месяц, с
включённым сопровождением инженером**. Запасная: за изменение. Выбор
подтверждается или отклоняется на итоговой встрече пилота.

Сопровождение инженером включено в цену и называется в предложении
открыто. Продавать его как автономный продукт нельзя: без инженера
сегодня нет ни подключения, ни разбора пробелов.

## 3. Данные, нужные для цены

| Данные | Откуда |
|---|---|
| Изменений API в месяц на один API | История Git клиента, интервью |
| Число потребителей и команд на API | Проба покрытия |
| Текущий труд на одно изменение по сбору потребителей | Ветка A0 и A1 в пилоте |
| Труд с модулем на изменение, холодный и тёплый | Ветка A2 в пилоте |
| Стоимость часа разработчика клиента | Клиент; если не даёт, диапазон рынка, помеченный как допущение |
| Стоимость последнего инцидента из-за изменения API | Интервью и записи клиента |
| Наша полная стоимость часа инженера | Наша сторона |
| Как клиент закупает инструменты: карта, счёт, тендер, порог согласования | Интервью с тем, кто решает о бюджете |

## 4. Как проверить цену

1. **Нижняя граница.** Наша полная стоимость обслуживания одного API в
   месяц: тёплые часы инженера на изменение × изменений в месяц × наша
   ставка, плюс доля подключения и поддержки формы вызова, разнесённая на
   срок договора. Считается по журналу пилота.
2. **Верхний ориентир.** Измеренная экономия труда клиента в месяц:
   `(T_A1 − T_A2)` на изменение × изменений в месяц × ставка клиента. Плюс,
   только если клиент сам дал данные: разница пропусков S1 × его стоимость
   инцидента. Если `T_A2 ≥ T_A1`, денежной экономии труда нет, и цена может
   держаться только на проверяемости (исход "проверка вместо поиска" в
   [PROTOCOL.md](PROTOCOL.md) §8).
3. **Если верхний ориентир ниже нижней границы**, сервис с сопровождением не
   окупается при нынешней автоматизации. Цену не снижаем ниже затрат.
   Решение: автоматизировать подключение или остановиться.
4. **Предложение с ценой.** На итоговой встрече тому, кто решает о бюджете,
   даём письменное предложение продолжения на 3 месяца по цене между
   границами, в единице "API в месяц", с запасной единицей "за изменение".
   Цена в предложении считается от измеренных величин, и расчёт показывается
   клиенту.
5. **Сигнал.** Подтверждением считается действие: подписанный заказ, счёт к
   оплате, заявка в бюджет с датой. "Интересно, вернёмся позже" это отказ
   на данный момент, записывается как отказ. Одного клиента мало для цены:
   с первым клиентом проверяется только то, что цена между границами
   вообще существует.

## 5. Чего здесь нет

Нет оценки рынка, выручки и экономии клиента. Любое такое число сейчас было
бы выдумкой: внешних измерений нет ни одного.
