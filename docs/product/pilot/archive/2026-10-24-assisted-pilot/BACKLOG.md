# Ближайший backlog пилота

Редакция 24.10.2026. Сюда входит только то, что нужно для проверки H-pilot
([PROTOCOL.md](https://github.com/rengalaxies/agent/blob/0fab62a03bc237ba25af28b8d9748c2d8fdfd515/docs/product/pilot/PROTOCOL.md) §1) или убирает препятствие пилоту. Каждый пункт
связан с наблюдением, из-за которого без него пилот измерил бы заранее
известный дефект ([EVIDENCE.md](https://github.com/rengalaxies/agent/blob/0fab62a03bc237ba25af28b8d9748c2d8fdfd515/docs/product/pilot/EVIDENCE.md)).

Оценки для одного разработчика, знакомого с кодом. Изменения ядра поднимают
`PROFILE`. Демо на них не перезакрепляется: демо заморожено.

## Порядок

| Когда | Пункты |
|---|---|
| Сразу, до поиска клиента не ждать | B8, B7 |
| После согласия первого клиента на пробу | B2, B3, B1, B5, B4 |
| После пробы, только если она не пройдена из-за формы вызова | B6 |

Так основная разработка (около 2 недель) начинается, когда есть кому её
применить. Пока клиент согласует доступ, она успевает к ретроспективе.

## Пункты

| ID | Проблема пилота | Изменение | Ожидаемый эффект | Как проверить | Оценка |
|---|---|---|---|---|---|
| B8 | Провайдер с `$ref` у `page_size` в OpenAPI молча пропускает смену default и заявляет полное покрытие | Ревью и слияние готового PR #45 (`fix/graph-openapi-page-size-ref`) | Пробел и `PAGE_DEFAULT_UNRESOLVED` вместо молчания на OpenAPI клиента | Регрессия `test_r6_*` проходит в Linux CI | 0,5 дня |
| B7 | Ворота 0 нечем мерить: нет способа посчитать покрытие на коде клиента | Скрипт пробы: инвентаризация мест вызова по адресам, хостам, путям и именам переменных окружения; разметка формы вызова; подсчёт `R / \|C\|` и пробелов в файлах из `C` | Проба занимает часы, а не дни; распределение форм вызова сохраняется как данные о рынке | Прогон на `examples/agent_graph` даёт известный ответ; прогон на fastapi 0.115 не падает | 2 дня |
| B2 | Любое изменение операции, кроме трёх классов, даёт `deltas=[]` (O3). На реальных изменениях клиента модуль в основном молчал бы | Новая delta `OPERATION_CHANGED_UNCLASSIFIED`: если нормализованный текст декоратора, сигнатуры и тела обработчика FastAPI или JSON-объект операции OpenAPI различаются между base и head, каждому потребителю операции `RECHECK_REQUIRED` с основаниями обеих сторон. Изменения в функциях, которые обработчик вызывает из других файлов, не отслеживаются, и отчёт это пишет | Модуль отвечает на любое изменение операции списком потребителей, а не тишиной. Это тот же принцип, что в F1: неизвестное не выдаётся за неизменное | Тест: смена `response_model`, нового обязательного параметра и тела обработчика даёт delta и `RECHECK_REQUIRED` у каждого потребителя; несвязанная правка файла поставщика delta не даёт | 3-4 дня |
| B3 | `revision` это непроверяемая строка (O14). Основание "файл, строки, коммит" нельзя воспроизвести, а проверяемость и есть предмет пилота | Минимальная часть ADR-004 без зеркал: команда, которая выгружает дерево коммита через `git archive` для каждого репозитория policy, записывает SHA коммита как `revision` и вызывает `prepare_context` и `analyze_change` для пары base/head | Ссылка в отчёте ведёт на строку в конкретном коммите. Ревьюер повторяет анализ по двум SHA. Инженер не собирает каталоги руками | Повторный запуск на тех же SHA через сутки даёт тот же результат; отчёт ссылается на SHA, а не на каталог | 2-3 дня |
| B1 | На реальном коде тысячи пробелов `unknown_http_client`, включая `dict.get` и `@app.get` (O5). Отрицательный ответ "вот где не смотрели" не прочитать | Разделить код пробела: декораторы маршрутов не считать вызовами клиента; `unknown_http_client` оставить для получателей, связанных в файле с известным конструктором клиента (`requests.Session`, `httpx.Client` и подобные) или с аргументом, похожим на URL или путь; остальное записывать как `unclassified_method_call`. Ярлык покрытия и отчёт считаются по первому классу, второй остаётся в JSON | Человек видит десятки мест, а не тысячи. Ни одно место не исчезает: шум переходит в отдельный код | На fastapi 0.115 и django 5.1 число `unknown_http_client` падает не меньше чем на 90% (порог выбран до прогона); тесты на `Session` и обёртку по-прежнему дают пробел | 2-3 дня |
| B5 | Результат ядра это JSON. Автору нужен текст для PR | Рендер отчёта в Markdown из результата `analyze_change`: изменённые операции; потребители со ссылками на строку в коммите; характер использования; что проверить; кандидаты во владельцы из CODEOWNERS с пометкой "кандидат"; пробелы класса `unknown_http_client` в файлах, где встречается адрес API; раздел "что отчёт не утверждает". Отправки никуда нет | Автор вставляет отчёт в PR без переписывания. Инженер тратит время на разбор, а не на оформление | Отчёт по сценарию B демо называет Reporting, строку вызова и проверку; формулировки силы свидетельств совпадают с правилами аудита интеграции (статическая находка это условный прогноз) | 2-3 дня |
| B4 | Правка несвязанного файла делает STALE все исправления людей (O8). В живой фазе каждый новый коммит обесценивал бы исправления, и гипотеза о памяти проверялась бы на заведомом дефекте | Часть ADR-006: исправление человека устаревает, только если изменились байты файлов, на которые оно ссылается. Набор репозиториев фиксируется до первого исправления (процедура, не код), потому что добавление репозитория скрывает прежние исправления | Исправление, сделанное на ретроспективе, доживает до живых задач, если его основание не менялось. Пилот меряет число повторных исправлений | `docs/audits/architecture/bench/verify_claims.py` (PR #44), проверка 2 даёт `CURRENT` после правки несвязанного файла и `STALE` после правки процитированного | 3-5 дней |
| B6 | Проба может показать, что вызовы клиента написаны f-строками, через импортированную константу или `os.environ.get` с default (O2) | Не больше двух форм, выбранных по распределению из пробы. Кандидаты: f-строка из разрешимых частей; константа, импортированная из модуля того же репозитория; `os.environ.get("ИМЯ", "литерал")` с соответствием имени сервису в policy | Покрытие клиента переходит порог пробы, если причина в форме вызова, а не в обёртках и SDK | Повторная проба: `R / \|C\|` до и после | до 1 недели, жёсткий предел |

Итого: B8 и B7 около 2,5 дней сразу; B1-B5 около 2-2,5 недель после согласия
клиента; B6 до недели по условию.

## Что сознательно не входит

| Не делаем | Почему |
|---|---|
| Шаги 1-2 аудита архитектуры: журнал, ядро внутри процесса демо, пакет ядра | Лечат демо и сопровождение. Пилот идёт через CLI из checkout на закреплённом SHA |
| Зеркала Git, инкрементальный индекс, очистка хранилища (полные ADR-004, ADR-005) | На корпусах до тысяч файлов полный пересчёт занимает секунды (O7) |
| MCP-адаптер | Агент клиента вызывает CLI через shell. Делаем тонкий адаптер только для чтения, если агент клиента не умеет запускать команды, и только тогда |
| Модельный цикл, `MODEL_PROPOSED_EDGE`, квалификация моделей | O9, O10. Проверка модели на пробелах имеет смысл только после пилота, на размеченных пробелах клиента |
| UI демо, развёртывание ветки UX-аудита, обновление ВМ | В пилоте отчёт это Markdown в PR. Понятность UI не проверялась на людях |
| Расширение грамматики сверх B6, `httpx`, `Session`, обёртки, другие языки | Гонка с coding agent, который поддерживает все стеки (I1) |
| RabbitMQ | Discovery-кода нет |
| Многопользовательский режим, SSO, ACL | Один инженер, один контур клиента |
