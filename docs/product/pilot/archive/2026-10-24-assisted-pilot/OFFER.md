# Предложение пилота: проверяемый список потребителей для изменений внутреннего API

Редакция 24.10.2026. Это предложение сопровождаемого пилота. Анализ выполняет
наш инженер с помощью инструмента. Это не автономный продукт и не готовая
коммерческая поставка. Основания выбора: [EVIDENCE.md](https://github.com/rengalaxies/agent/blob/0fab62a03bc237ba25af28b8d9748c2d8fdfd515/docs/product/pilot/EVIDENCE.md).
Как меряем: [PROTOCOL.md](https://github.com/rengalaxies/agent/blob/0fab62a03bc237ba25af28b8d9748c2d8fdfd515/docs/product/pilot/PROTOCOL.md).

Предложение показываем только после проблемного интервью, в котором
человек сам описал недавнее изменение своего API. Если такого случая у него
нет, предложение не показываем.

## Для кого

Команда, которая владеет внутренним HTTP API и меняет его, а потребители
этого API живут в репозиториях других команд и написаны на Python.

Типичная картина: команда платформы данных или внутреннего backend
поддерживает сервис на FastAPI (или с опубликованным OpenAPI JSON). Его
вызывают Airflow DAG, сервисы отчётности, скрипты сверки, ML-пайплайны
соседних команд через `requests`. Изменения контракта случаются хотя бы
раз в месяц.

Условия входа, которые проверяются до старта:

| Условие | Почему |
|---|---|
| Один API поставщика, у которого не меньше трёх потребителей в репозиториях других команд | Меньше трёх потребителей автор помнит сам, инструмент не нужен |
| Потребители на Python и вызывают API через `requests` | Других клиентов ядро не разбирает (см. "Ограничения") |
| Провайдер объявлен через FastAPI или OpenAPI JSON | То же |
| Не меньше 6 изменений API за последние 6 месяцев в истории Git или не меньше 3 запланированных на ближайшие 6 недель | Иначе нечего сравнивать, пилот превращается в разовый показ |
| Наш контакт имеет право читать репозитории потребителей и может согласовать доступ на чтение для пилота | Без этого нет ни анализа, ни эталона |
| Проба покрытия пройдена (см. ниже) | Иначе пилот измерит только то, что инструмент не видит код клиента |
| Желательно: в команде разрешён coding agent с доступом к этим репозиториям | Без него сравнение отвечает только на вопрос "лучше ли текущего процесса", а не "лучше ли агента" |

## Рабочая ситуация

**Кто что меняет.** Разработчик команды-поставщика готовит PR: убирает
устаревший параметр, вводит default размера страницы, удаляет операцию,
меняет формат ответа.

**Когда возникает неопределённость.** При планировании ("кого это
заденет?") и на ревью PR ("кого позвать, что проверить?"). Ревьюер
спрашивает, все ли потребители учтены, и ответить с основаниями нечем.

**Как ищут сейчас.** Поиск по коду по строке пути или имени хоста, вопрос в
общем чате "кто использует `/v1/orders`?", устаревшая страница в wiki или
каталоге, память старших разработчиков, иногда журналы доступа по
сервисным учётным записям. Отдельно: coding agent, если он разрешён. Его
ответ нельзя воспроизвести, а "потребителей больше нет" ничем не
ограничено. Это описание ситуации из наших документов, а не из интервью с
клиентом: в интервью его нужно подтвердить или опровергнуть.

**Кто несёт последствия ошибки.** Команда-потребитель: упавший DAG или,
хуже, отчёт, который молча получает первые 100 записей из 250. Её
пользователи получают неверные цифры. Команда-поставщик откатывает
изменение и разбирает инцидент.

**Кто принимает решение о внедрении.** О пилоте: техлид команды-поставщика
вместе с тем, кто выдаёт доступ на чтение репозиториев (обычно
руководитель направления и служба безопасности). О покупке: руководитель
платформы или направления разработки. Это гипотеза H5: роль и бюджет
уточняются в интервью.

## Почему человек согласится потратить время

1. Основную работу делаем мы. Его вклад ограничен и записан заранее
   (раздел "Что делает команда клиента").
2. По каждому реальному изменению его API за время пилота он получает
   список потребителей с точными строками кода на конкретном коммите. Этот
   список можно вставить в описание PR и позвать владельцев.
3. Он получает независимую оценку того, сколько потребителей пропускает
   его coding agent без графа на его собственном коде. Эта цифра полезна
   ему при любом исходе пилота, например для решения о том, насколько
   доверять агенту на ревью.
4. Ретроспективный разбор его прошлых изменений, включая то, что уже
   вызвало инцидент, если такое было.
5. Пилот бесплатный. Платой за него служат время команды и доступ к
   материалам. Цену обсуждаем только после измерений
   ([ECONOMICS.md](https://github.com/rengalaxies/agent/blob/0fab62a03bc237ba25af28b8d9748c2d8fdfd515/docs/product/pilot/ECONOMICS.md)).

## Вход и выход

| Шаг | Что |
|---|---|
| Клиент предоставляет | Доступ на чтение к репозиторию поставщика и репозиториям потребителей. Список базовых адресов сервиса по окружениям. CODEOWNERS или сведения о владельцах. Linux-машину или WSL2 внутри своего контура для запуска инструмента. По возможности: журналы доступа к API за 30-90 дней по сервисным учётным записям или User-Agent, без тел запросов |
| Что выполняет наш инженер | Ставит инструмент в контуре клиента. Задаёт policy: репозитории, адреса, соответствие адреса сервису. Для каждого изменения выгружает два коммита (base и head), запускает анализ, разбирает пробелы, относящиеся к API поставщика, пишет отчёт |
| Что выполняет инструмент | Находит в коде потребителей вызовы операций API поставщика, сопоставляет их с изменёнными операциями, для каждого вызова даёт основание (файл, строки, digest, коммит), отдельно перечисляет места, которые не смог разобрать |
| Что получает команда | Отчёт по изменению: изменённые операции; потребители и точные места вызова со ссылками на строки в коммите; что инструмент знает о характере использования (одиночный запрос, обход страниц, явный размер страницы); что проверить у каждого потребителя; кандидаты во владельцы; список неразобранных мест, относящихся к API; раздел "что отчёт не утверждает" |
| Как команда его использует | Автор вставляет список в PR, зовёт владельцев затронутых потребителей, решает, менять ли контракт, вводить ли версию или переходный период. Решение о выпуске остаётся за командой |
| Как проверяется качество | Независимый эталон затронутых потребителей по каждому изменению, собранный сотрудником клиента вслепую. Сравнение с текущим процессом и с coding agent без графа. Подробно в [PROTOCOL.md](https://github.com/rengalaxies/agent/blob/0fab62a03bc237ba25af28b8d9748c2d8fdfd515/docs/product/pilot/PROTOCOL.md) |

## Ограничения, о которых говорим до старта

### Что ядро разбирает на 24.10.2026

| Сторона | Поддержано | Не поддержано, даёт пробел |
|---|---|---|
| Потребитель | `requests.get/post/put/patch/delete/...`, `requests.request`, импортированные из `requests` функции. URL: литерал, константа модуля в том же файле, сложение таких строк через `+` | f-строки, адрес из `os.environ` или модуля настроек, `requests.Session`, `httpx`, `aiohttp`, собственные обёртки, сгенерированные SDK, другие языки, распаковка `**kwargs` в параметрах |
| Поставщик | Декораторы FastAPI на функциях верхнего уровня, OpenAPI JSON | `$ref` у пути или параметра в OpenAPI (даёт пробел `openapi_ref_unsupported`), схемы ответа (не читаются вовсе), OpenAPI YAML, другие фреймворки, роуты, собранные динамически |
| Изменение | Удаление операции; смена default `page_size`; смена объявления, где default не распознан | Изменение схемы ответа, типов, обязательных полей, кодов статуса. Новый потребитель не считается изменением |
| Среда | Linux, Python-код с синтаксисом до 3.12, корпус до 20 МБ на одну policy | Windows без WSL, синтаксис 3.14 |

До старта мы делаем изменения из [BACKLOG.md](https://github.com/rengalaxies/agent/blob/0fab62a03bc237ba25af28b8d9748c2d8fdfd515/docs/product/pilot/BACKLOG.md): неклассифицированное
изменение операции даёт "перепроверить у каждого потребителя" вместо
молчания, шум пробелов сокращается, анализ привязывается к коммитам Git.
f-строки и адреса из настроек добавляются, только если проба покрытия
покажет, что без них клиент не проходит порог, и не больше двух форм.

### Что отчёт не утверждает

- Что потребителей нет, если их нет в списке. Отрицательный ответ
  ограничен: "в поддержанной грамматике по этим репозиториям на этих
  коммитах не найдено, вот неразобранные места".
- Что изменение совместимо или безопасно к выпуску.
- Что потребитель действительно сломается. Находка это условный прогноз со
  ссылкой на код. Подтверждает её владелец потребителя или тест.
- Ничего о репозиториях, которые не подключены.

### Роль человека

| Кто | Что делает | Чего не делает инструмент |
|---|---|---|
| Наш инженер | Настраивает policy, запускает анализ, разбирает пробелы, пишет отчёт, исправляет ошибочные связи как "исправление человека" | Не утверждает требования за людей |
| Автор изменения | Читает отчёт, решает, что делать с изменением, зовёт владельцев | Не блокирует релиз, не отправляет сообщения |
| Владелец потребителя | Подтверждает или опровергает влияние на свой код | Не правит код потребителя |
| Разметчик клиента | Собирает эталон вслепую | |

### Состояние LLM

В пилоте модель не используется. Причины: в текущем протоколе принятый
кандидат модели по построению повторяет ребро, которое уже нашёл
статический анализ; в реальной серии 22.10.2026 полный цикл прошли 2 из 6
сочетаний модели и случая, контроль с decoy не завершила ни одна модель;
клиент модели не работает через корпоративный прокси. Код клиента не
уходит ни в какую модель. Coding agent клиента в ветке сравнения
работает по правилам клиента и на его ответственности.

### Труд подключения

Оценки до замера. В пилоте каждую минуту записываем ([PROTOCOL.md](https://github.com/rengalaxies/agent/blob/0fab62a03bc237ba25af28b8d9748c2d8fdfd515/docs/product/pilot/PROTOCOL.md)).

| Работа | Кто | Оценка |
|---|---|---|
| Проблемное интервью | Техлид клиента, наш ведущий | 1 ч |
| Согласование доступа и запуска в контуре | Техлид, безопасность клиента | 1-3 ч у клиента, срок не оцениваем |
| Проба покрытия | Наш инженер; техлид отвечает на вопросы | 6-8 ч у нас, 1 ч у клиента |
| Policy: репозитории, адреса, соответствие сервисам | Наш инженер; техлид подтверждает | 8-12 ч у нас, 1 ч у клиента |

## Ход пилота

Сроки предлагаемые. Начало зависит от доступа.

| Неделя | Что происходит | Ворота |
|---|---|---|
| 0 | Интервью, согласие, доступ, проба покрытия | Проба пройдена, иначе пилот не начинаем и честно говорим почему |
| 1 | Policy, отбор задач, фиксация эталона ретроспективных изменений | Список задач заморожен до первого запуска |
| 1-2 | Ретроспектива: 6 прошлых изменений, три ветки сравнения | |
| 2-5 | Живые изменения: каждый PR, меняющий API, по мере появления, цель 6 | Если к концу недели 5 задач меньше 8 всего, продлеваем один раз на 2 недели или решаем на том, что есть |
| 6 | Разбор результатов с клиентом, решение | Критерии из [PROTOCOL.md](https://github.com/rengalaxies/agent/blob/0fab62a03bc237ba25af28b8d9748c2d8fdfd515/docs/product/pilot/PROTOCOL.md) §8 |

Объём: 12 изменений, минимум 8 для решения. 12 совпадает с диагностической
серией v4, записанной заранее (`docs/product-architecture-roast-2026-10-20.md`
§3). Это диагностика, а не статистическое доказательство.

## Что делает наша команда

- Готовит и проводит интервью и пробу покрытия.
- Ставит инструмент в контуре клиента и задаёт policy.
- По каждому изменению выпускает отчёт до merge PR, если клиент сообщил о
  PR хотя бы за рабочий день. Время выпуска фиксируется.
- Ведёт журнал труда своей стороны.
- Обеспечивает изоляцию веток сравнения: оператор ветки "агент без графа"
  не видит отчётов инструмента.
- Готовит итоговый отчёт с абсолютными числами по каждой задаче.

## Что делает команда клиента

Оценка до замера: около 12-16 часов на 2-3 человек за 6 недель.

| Роль | Что | Оценка |
|---|---|---|
| Техлид поставщика | Интервью, проба, подтверждение policy, итоговая встреча | 4-5 ч |
| Автор каждого изменения | Сообщает о PR, читает отчёт, записывает, что сделал | 15-20 мин на изменение |
| Разметчик (не автор изменений) | Собирает эталон по каждому изменению вслепую | 30 мин на изменение |
| Оператор агента без графа | Запускает своего coding agent по заданию, записывает время. Если клиент разрешает, это делает второй человек с нашей стороны | 30-45 мин на изменение |

## Материалы и доступы для старта

- Решение о том, где работает инструмент: машина клиента, его ВМ или WSL2.
  Код из контура не выносим.
- Доступ на чтение к репозиториям поставщика и потребителей на время
  пилота.
- Список базовых адресов API поставщика по окружениям и конфигурации, где
  потребители их задают.
- CODEOWNERS или иной источник владельцев.
- Список изменений API за 6 месяцев (PR или коммиты) и, если были, записи об
  инцидентах из-за них.
- Журналы доступа к API по потребителям за 30-90 дней, если их можно
  выгрузить без тел запросов. Необязательно, но сильно улучшает эталон.
- Сведения о coding agent: какой, с каким доступом, куда уходит контекст.
- Согласие на запись трудозатрат и на использование обезличенных итогов.

## Что обещаем и чего не обещаем

Обещаем: по каждому изменению API за время пилота отчёт с проверяемыми
основаниями и явным списком того, что инструмент не разобрал; измеренное
сравнение с вашим текущим процессом и вашим coding agent на ваших
изменениях; итоговые числа без отбора удобных метрик.

Не обещаем: экономию времени или денег, полноту списка потребителей,
поддержку стеков вне таблицы ограничений, автономную работу без нашего
инженера, допуск к выпуску.
