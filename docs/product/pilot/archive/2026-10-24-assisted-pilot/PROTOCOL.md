# Протокол измерений пилота

Редакция 24.10.2026. Протокол фиксируется до первого запуска на коде
клиента. После фиксации меняются только опечатки. Любое иное изменение
записывается в журнал отклонений (§9) с датой и причиной, а результаты
по прежнему и новому правилу показываются оба.

Основа: диагностическая серия v4 (`docs/product-architecture-roast-2026-10-20.md`
§3, `docs/agent-graph-implementation-2026-10-21.md` §6). Протокол переносит её
с синтетики на реальные изменения клиента и не меняет критерии.

## 1. Основная гипотеза

**H-pilot.** На реальных изменениях внутреннего API клиента, попадающих в
поддержанный профиль, coding agent вместе с модулем и нашим инженером
выдаёт автору изменения список затронутых потребителей:

- с числом серьёзных пропусков не больше, чем у того же coding agent без
  модуля (`FN_A2 − FN_A1 ≤ 0`, оба абсолютных числа и знаменатель);
- с полным активным трудом обеих сторон не больше 0,8 от варианта без
  модуля на всей серии, включая подключение (`T_A2 ≤ 0,8 × T_A1`).

Оба условия из v4. Порог 20% выбран заранее как операционный ориентир, а не
как обнаруженный эффект.

Вторичный вопрос, который пилот тоже закрывает: проходит ли код клиента
пробу покрытия. Это ответ на Q3 из исследования Ontonet, и он ценен сам по
себе: если типичный клиент её не проходит, продукт в нынешнем виде не
применим.

## 2. Ворота 0: проба покрытия

Выполняется до отбора задач, на текущем `main` клиента.

1. Перечислить все места в репозиториях потребителей, которые обращаются к
   API поставщика. Источник: поиск по базовым адресам из policy, по имени
   хоста, по префиксам путей операций, плюс имена переменных окружения и
   ключей настроек, где задан адрес. Каждое место размечает наш инженер:
   потребитель, операция, форма вызова (литерал, константа, f-строка,
   окружение, модуль настроек, `Session`, `httpx`, обёртка, SDK, другое).
   Это множество `C`.
2. Запустить `prepare_context` на тех же коммитах.
3. Посчитать `R`: места из `C`, которые ядро разрешило в ребро к правильной
   операции. Покрытие `R / |C|`.
4. Посчитать пробелы, которые относятся к файлам из `C`, и пробелы в
   остальных файлах отдельно.

**Предлагаемое условие прохода:** `R / |C| ≥ 0,5` после не более двух
дополнительных форм вызова из [BACKLOG.md](https://github.com/rengalaxies/agent/blob/0fab62a03bc237ba25af28b8d9748c2d8fdfd515/docs/product/pilot/BACKLOG.md) (B6), реализуемых не
дольше недели. Обоснование: ниже половины основную работу по поиску делает
агент или человек, и модуль добавляет к ней подготовку, не сокращая её. Порог
это допущение, его владелец утверждает до пробы.

Если проба не пройдена, пилот не начинается. Распределение форм вызова
записывается: это данные о рынке, а не провал клиента.

Ограничение: `C` собирает наша сторона, и поиск по строкам пропускает
вызовы с адресом, собранным совсем динамически. Поэтому покрытие на пробе
верхняя оценка. Эталон в §5 строится иначе и это корректирует.

## 3. Отбор задач

Задача: одно изменение API поставщика между двумя коммитами (base, head).

1. Ретроспектива. Берутся **все** слитые PR за последние 6 месяцев, которые
   меняют объявление хотя бы одной операции API (сигнатуру обработчика,
   декоратор, параметры, OpenAPI) или тело обработчика операции. Список
   составляет техлид клиента без нашего участия.
2. Из списка по зерну, записанному до жеребьёвки, отбираются 6 задач со
   стратификацией: не меньше 2 задач, где по мнению техлида были
   затронуты потребители, и не меньше 1 задачи без затронутых
   потребителей. Изменение, которое вызвало инцидент, включается вне
   жребия и помечается.
3. Живые задачи. Каждый PR, меняющий API, за недели 2-5 входит в серию по
   порядку появления, пока задач всего не станет 12.
4. После фиксации задачу нельзя исключить из-за того, что результат
   плохой. Исключение возможно только по причине, не связанной с
   результатом (PR отменён до анализа), и записывается в журнал отклонений.
5. Задачи вне поддержанного класса изменений (например, смена схемы ответа)
   не исключаются. По ним модуль отвечает "перепроверить у каждого
   потребителя операции" (B2). Это честная часть серии: клиенту такие
   изменения тоже приходят.

## 4. Ветки сравнения

| Ветка | Кто выполняет | Что получает | Результат ветки |
|---|---|---|---|
| A0. Текущий процесс | Автор изменения | Ничего сверх обычного | Для живых задач: список потребителей, который автор собрал бы своими средствами, и записанное время. Для ретроспективы: восстановление по PR, чату и инцидентам, помечается как слабые данные |
| A1. Coding agent без модуля | Оператор агента (сотрудник клиента или второй человек с нашей стороны) | Те же репозитории, тот же агент, право вести заметки между задачами | Список затронутых потребителей с объяснением, который оператор готов отдать автору |
| A2. Coding agent с модулем | Наш инженер | То же, плюс CLI модуля и его отчёт. Если агент клиента не может запускать команды, A2 выполняет наш инженер с модулем без агента, и это записывается | Список затронутых потребителей и отчёт по изменению |

Правила изоляции:

- Оператор A1 не видит отчётов A2 и обсуждений по ним до конца пилота.
- Оператор A1 и инженер A2 разные люди.
- Порядок выполнения A1 и A2 по задаче чередуется по зерну, записанному
  заранее.
- Задание обеим веткам одно и то же текстом: "Изменение `base..head` в
  репозитории X. Перечисли места в подключённых репозиториях, где поведение
  может измениться, с основанием, и что проверить". Подсказки о
  потребителях не даются.
- Если у клиента нет разрешённого coding agent, A1 = A0. Тогда пилот
  отвечает на вопрос "лучше ли модуль текущего процесса", но не закрывает
  Q1 (преимущество над агентом). Это записывается в итог заранее.

Результатом ветки считается только финальный список, отданный автору.
Пробел модуля, который инженер не превратил в пункт списка, не считается
найденным потребителем.

## 5. Эталон

Эталон по каждой задаче собирает разметчик клиента, который не автор
изменения и не оператор A1.

1. Пул кандидатов: объединение списков A0, A1, A2; все места из пробы
   покрытия (§2) для затронутых операций; потребители из журналов доступа
   за 30-90 дней, если журналы даны; для ретроспективы ещё PR-исправления в
   репозиториях потребителей и записи инцидентов после изменения.
2. Пул перемешивается и обезличивается: разметчик не знает, какая ветка
   нашла кандидата.
3. Для каждого кандидата разметчик ставит: затронут или нет; серьёзность
   (S1 молчаливая порча или потеря данных, S2 явный сбой: ошибка, упавшая
   задача, S3 незначительно); основание своего решения.
4. Эталон по задаче фиксируется (хеш файла записывается в журнал) до
   раскрытия, какая ветка что нашла.

Ограничение пула: потребитель, которого не нашла ни одна ветка, ни поиск,
ни журналы, в эталон не попадёт. Это общий недостаток всех вариантов, и
он указывается в итоге.

## 6. Показатели

### Основные (решают продолжение)

| Показатель | Определение |
|---|---|
| `FN_k` | Число мест эталона с серьёзностью S1 или S2, которых нет в финальном списке ветки `k`. Считается по всей серии, знаменатель: число таких мест в эталоне |
| `T_k` | Полный активный труд людей обеих сторон в минутах на ветку `k` по всей серии: подключение, проба (для A2), policy, исправления знаний, запуск, разбор пробелов, написание списка, разбор ложных предупреждений, исправление контекста. Ожидание машины в `T` не входит |

### Качество

| Показатель | Определение |
|---|---|
| Все пропуски | `FN` по всем серьёзностям, включая S3 |
| `FP_k` | Пункты списка, которые эталон считает незатронутыми, и минуты на их разбор |
| Корректность оснований | Доля пунктов списка, основание которых разметчик подтвердил по коду за 2 минуты или быстрее. Отдельно: время проверки одного пункта |
| Пробелы на задачу | Число пробелов модуля, относящихся к файлам с вызовами API поставщика, которые инженер должен был просмотреть |
| Покрытие по задаче | Доля мест эталона, разрешённых ядром в ребро |
| Ограниченный отрицательный ответ | По задачам, где эталон пуст: сколько веток ответили "не найдено" и сколько из них перечислили, где не смотрели |

### Польза

| Показатель | Определение |
|---|---|
| Своевременность | Список выдан до merge PR: да или нет; часы от сообщения о PR до списка |
| Действия по списку | Что автор сделал из-за пункта списка: позвал владельца, изменил PR, ввёл переходный период, отказался от изменения. Чтение отчёта действием не считается |
| Подтверждение владельцем | Владелец потребителя подтвердил или опроверг влияние |

### Затраты

| Показатель | Определение |
|---|---|
| Часы нашей стороны | По ролям и шагам, отдельно холодное подключение и работа на задачу |
| Часы клиента | По ролям и шагам |
| Машинное время | Время `prepare_context` и `analyze_change`, размер корпуса |
| Токены и деньги на модель | В A2 модель модуля выключена: 0. Расход агента клиента в A1 и A2 записывается, если клиент его видит |

### Коммерческий сигнал

Какое конкретное действие клиент совершил после итоговой встречи: попросил
продолжения, привёл другую команду, начал разговор о бюджете, отказался.
Положительный отзыв без действия не считается сигналом.

## 7. Цена ложного предупреждения и пропуска

Чисел у нас нет, и придумывать их нельзя. В пилоте собираем:

| Ошибка | Что стоит | Как меряем в пилоте |
|---|---|---|
| Пропуск S1 | Потребитель молча получает неполные или неверные данные. Обнаруживается поздно, иногда пользователями отчётов. Стоимость: поиск причины, исправление, пересчёт данных, координация команд | Ретроспектива: часы и последствия реального инцидента по записям клиента. Интервью: последний такой случай. Для живых задач разметчик оценивает класс последствий, а не рубли |
| Пропуск S2 | Явный сбой у потребителя: упавшая задача, ошибка. Обнаруживается быстро, стоимость в часах исправления и откате | То же |
| Ложное предупреждение | Минуты автора на разбор; лишнее обращение к чужой команде; при большом числе привычка не читать отчёт | Минуты на разбор каждого FP; было ли обращение к другой команде |
| Пробел без ответа | Минуты инженера на просмотр | Минуты на пробел |

Рабочая гипотеза асимметрии: пропуск S1 стоит часы и дни, ложное
предупреждение минуты. Поэтому критерий продолжения требует не больше
серьёзных пропусков и не ограничивает FP напрямую: стоимость FP уже входит в
`T`. Если по данным клиента пропуск стоит меньше, чем разбор всех
предупреждений за месяц, эта логика неверна, и это записывается в итог.

## 8. Решение по итогам

Решение принимается по всей серии, на заранее записанных правилах. Итог
показывает числа по каждой задаче, холодный и тёплый режимы и точку
окупаемости подготовки: после какого числа задач `T_A2` догоняет `T_A1`.

| Исход | Условие | Действие |
|---|---|---|
| Продолжить | `FN_A2 ≤ FN_A1` и `T_A2 ≤ 0,8 × T_A1` на серии, и клиент совершил конкретное следующее действие | Предложение платного продолжения по [ECONOMICS.md](https://github.com/rengalaxies/agent/blob/0fab62a03bc237ba25af28b8d9748c2d8fdfd515/docs/product/pilot/ECONOMICS.md) и второй клиент того же сегмента |
| Изменить: автоматизировать подключение | `FN_A2 ≤ FN_A1`, `T_A2 > 0,8 × T_A1` на серии, но на задачах после подключения `T_A2 ≤ 0,8 × T_A1` | Автоматизировать самую дорогую часть подключения по журналу труда, повторить со вторым клиентом. Без нового расширения грамматики |
| Изменить: проверка вместо поиска | `FN_A2 ≤ FN_A1`, по труду выигрыша нет, но корректность оснований и время проверки пункта заметно лучше у A2, и клиент сам называет проверяемость причиной продолжения | Проверить позиционирование "ревью и аудит изменений": модуль проверяет основания находок агента. Готовность платить проверяется отдельным шагом |
| Остановить | `FN_A2 > FN_A1` | Разобрать каждый пропуск. Прекратить продуктовый трек, ядро остаётся результатом ВКР. Пропуск из-за найденной ошибки кода не даёт права переиграть серию |
| Остановить | Проба покрытия не пройдена у двух клиентов подряд | Продукт в нынешнем виде к их коду не применим. Расширение грамматики под каждого клиента не делаем: это гонка с агентом |
| Остановить | До 13.11.2026 нет клиента, согласившегося на пробу | Прекратить продуктовый трек до появления случая |

Невыполненный критерий нельзя заменить другой метрикой после просмотра
результатов. Положительный исход открывает следующую внешнюю проверку и
коммерческий шаг, а не подтверждает рынок: 12 задач у одного клиента не
дают статистического вывода.

## 9. Журналы

| Журнал | Кто ведёт | Поля |
|---|---|---|
| Труд | Каждый участник | Дата, роль, ветка, задача, шаг, начало, конец, активные минуты |
| Задачи | Наш инженер | ID, base, head, класс изменения, ретро или живая, дата PR, дата merge |
| Выдачи | Каждая ветка | Задача, финальный список, время выдачи, хеш файла |
| Эталон | Разметчик | Задача, кандидаты, решение, серьёзность, основание, хеш файла |
| Действия | Автор | Задача, пункт списка, что сделано |
| Отклонения | Наш ведущий | Дата, что изменено в протоколе, почему, как это влияет на сравнение |

Журналы хранятся в контуре клиента. В публичный репозиторий попадают
только обезличенные агрегаты с согласия клиента. Имена людей, сервисов и
фрагменты кода клиента в репозиторий не попадают.
