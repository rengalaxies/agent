# Две пилотные сессии

Я получил по два письменных ответа от разработчика и продакта. Статус — WRITTEN_RESPONSES_RECEIVED. Участники быстро разобрались с заданиями без ИИ; точное время я не фиксировал. [Результаты и первичная разметка E7](e7-2026-11-27/README.md). Ниже сохранён протокол, подготовленный до получения ответов; его временной бюджет не является измеренной длительностью выполнения.

## Проверяемая гипотеза H-U-pilot

На двух заданных задачах своей роли участник с исходниками и карточкой ImpactMap самостоятельно указывает потребителя, проверяемое основание, риск либо ограничение и допустимый следующий шаг. Для каждой задачи критерий выполнения — 4 из 4 элементов корректны без содержательной подсказки. Это рабочий критерий осуществимости, выбранный для этой пилотной проверки.

Критическое неверное действие, пропуск существенного ограничения или подсказка правильного ответа означает невыполнение задачи по этому критерию. Отказ либо отсутствие ответа сохраняется. Результат фиксируется по каждому заданию. При двух ролях и двух задачах максимум четыре наблюдения, связанные внутри участника.

## Проведение 30–40 минут на участника

1. Получить согласие на обезличенные заметки. Запись только при отдельном согласии. Зафиксировать роль и опыт.
2. Выдать только папку нужной роли из «Участникам». Эталон находится в материалах модератора.
3. Нейтрально прочитать задание, попросить проговаривать ход решения. Не обучать ответу конкретного случая.
4. Дать две задачи по 8–10 минут. Фиксировать начало/конец, активное время, ожидание и помощь.
5. Сохранить дословный ответ. Не исправлять его до оценки. После ответа задать вопросы о непонятном.
6. Сопоставить с эталоном. Если участник предлагает обоснованное другое решение, сохранить расхождение для внешнего разбора.
7. Спросить о недавнем реальном похожем случае, обычном процессе, частоте и барьерах пилота. Разделять факт прошлого случая и мнение о будущем использовании.

## Оценка

Четыре элемента оцениваются по 0/1. Правильность адреса потребителя и основания сверяется с кодом. Риск формулируется условно, бизнес-ущерб без данных не утверждается. Следующий шаг — проверка, согласование либо восстановление доступа по случаю. Разрешение выпуска на основании неполных данных является критическим неверным действием.

Разработчик 1 — удалён endpoint, есть прямой вызов. Разработчик 2 — consumer явно передаёт page_size=60, уменьшение default само по себе не меняет размер этого вызова.
Продакт 1 — consumer использует уменьшенный default, требуется проверка полноты Reporting и согласование с владельцем. Продакт 2 — URL consumer относится к другому host, показанное изменение provider не доказывает воздействие на него.

Я подготовил код и вывод системы. Желательно, чтобы оценку ответа проверил второй человек по тем же материалам. Его имя и статус оценки фиксируются отдельно.

## Границы

Это пилотная проверка понимания на синтетических задачах. Текущий дизайн содержит одно условие с ImpactMap. Он даёт наблюдения о решении и затруднениях. Сравнительный эффект времени, рыночный спрос и частота реальной проблемы требуют отдельных данных. Если меняется критерий, материалы или задача, новую версию нужно зафиксировать до следующей сессии.

## Возврат результатов

Для каждой задачи нужны анонимный ID, роль, дата, дословные четыре пункта ответа, активные минуты, помощь модератора, оценки по четырём элементам и основание оценки. Заполнить sessions.csv. Для реального случая отдельно записать факты, источники, барьеры и следующий согласованный шаг. Контактные данные в публичные материалы не включаются.
