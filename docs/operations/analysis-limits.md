# Рабочие лимиты анализа ImpactMap

Изменение исходников15.11.2026 послеca81bfb: профиль для испытанного пилота10 репозиториев / около100 тыс. строк. Значения по умолчанию:

| Ограничение | Значение | Что считается |
|---|---:|---|
| Суммарный объём |8 000 000 байт|Суммарный бюджет рассматриваемых файлов по всем разрешённым репозиториям за один сбор; до декодирования и некоторых последующих проверок|
| Число файлов |2048|Сохранённые записи inventory за один сбор; часть пропусков Git в этот счётчик не входит|
| Один файл |65 536 байт|Прежний предел; больший файл пропускается с file_limit и неполным покрытием|
| Время сбора |60 секунд|Один вызов collector; не полный PR pipeline, ожидание очереди, сеть или SLO|

Счётчики зависят от режима чтения. В Git размер подходящего blob учитывается до чтения его содержимого и проверки LFS/binary, поэтому некоторые последующие пропуски всё равно расходуют byte budget. Oversize/symlink/submodule и другие пропуски внутри GitReader попадают в gaps и могут не попасть в inventory/max_files. В worktree ряд ошибок и пропусков добавляет inventory-записи. Отдельный ограничитель обхода и временной бюджет продолжают действовать;2048 не означает предел общего числа файлов на диске или всех gap-записей.

Это проверенный рабочий профиль для контролируемых sparse-корпусов, не обещание произвольных8MB/100k проектов. Лимит не связан с контекстным окном LLM; MODEL OFF. Права/allowlist/include/исключения чувствительных файлов не расширяются. Верхние валидационные границы20MB/10000files/120s/256KiB-file не изменены и не являются рекомендацией или подтверждённой ёмкостью.

## Применение и переход

Если `limits` отсутствует в Policy, новый source загружает эти defaults; пропущенные поля частичного `limits` тоже используют новые defaults. Явные значения оператора сохраняются. Например, policy с2_000_000/256/15 останется такой же после обновления кода. Старые конфиги/установленный релиз/исторические benchmark manifests автоматически не переписываются.

Для явной конфигурации блока Policy:

```json
{
  "limits": {
    "max_corpus_bytes": 8000000,
    "max_files": 2048,
    "max_file_bytes": 65536,
    "scan_seconds": 60.0
  }
}
```

Блок относится к файлу графовой Policy, на который указывает `core.policy_path` сервиса. `limits` верхнего ServiceConfig управляет очередью/lease/retry и имеет другой смысл. Не заменяйте его этим блоком. Policy загружается при создании CoreAnalyzer; применение новых исходников/настроек к установленному worker требует отдельного согласованного обновления/перезапуска в пачке10. Эта пачка не обновляла ВМ.

## Что происходит при остановке

При превышении суммарных байтов, количества файлов, ограничителя обхода или времени collector завершает сбор без сохранения частичного context. Сервис возвращает FAILED/budget_exhausted, пустые findings и понятное сообщение с настроенным пределом. Это не отсутствие влияния и не исправление прежних рисков. Короткий русский комментарий сохраняет диагноз.

Сообщение не содержит путей, текста исходников, исключения или токенов. Число в сообщении — настроенный предел, не заявленный фактический объём чтения. Детальные raw-пробы отдельно фиксируют принятые байты и долю коллекции; после abort доля выполненного анализа0.

Сначала сузьте разрешённые `include` до нужного исходного кода и контрактов, проверьте состав корпуса. Если полезный код не помещается, оператор выбирает увеличенные лимиты по замерам времени/памяти/очереди целевого стенда. Глобальные budgets продолжают действовать; обход не обрезает корпус молча. Недоступный репозиторий или большой отдельный файл сохраняют видимые gaps/PARTIAL по прежним правилам.

## Версии и доказательства
