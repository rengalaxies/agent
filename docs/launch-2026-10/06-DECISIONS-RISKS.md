# ADR и реестр открытых расхождений
Дата 2026-10-13. Статус: proposed. Ничего в ВКР или существующем научном коде не изменено этими плановыми файлами.

## ADR-001: Публичный UI как продуктовая надстройка
Проблема: ВКР (раздел 2.2.5) исключает отдельный UI из обязательного научного прототипа; интервью требуют доступного демонстратора.
Решение: публичный UI входит в **startup discovery MVP**, но не в необходимые для H1 компоненты. Раздельная VM и IPv4 для UI; private core не доступен напрямую извне.
Влияние: в ВКР можно позже добавить примечание «вспомогательный интерфейс для апробации», не меняя H1, предмет и novelty. При формальной правке проверить главы 2, 4 и приложение.
Риск: UI съест время и бюджет; mitigation - максимум 5 экранов, сначала storyboard.

## ADR-002: V1-oracle удалён по прямому решению автора 2026-10-13
Решение: **V1-oracle исключить** из текущей исследовательской программы. Оставить V0 (структурный ориентир), V1-ind (основной контроль) и V2 (исследуемый механизм). Отдельный scoring oracle для разметки и оценки сохранить: это другой компонент.
ВКР ещё содержит V1-oracle во введении/задачах, обзоре, матрицах сравнения, разделах 2.1/2.2 и протоколе 3.2 - необходимо точечно синхронизировать после просмотра текущей версии Google Docs. Изъять только V1-oracle и контраст Δoracle, объяснить достаточность V1-ind и ограничение вывода. H1 и независимую разметку не изменять. После редакции проверить вводные определения и все перекрёстные ссылки.
Риск: нет усиленного контроля того, что вручную заданные предикаты могут устранить различие V2/V1-ind. Прямо признать, что преимущество V2 не доказывает невозможность выразить ту же семантику ручными правилами.
## ADR-003: Knowledge map не новая центральная база истины
Факт: repo уже содержит knowledge-1, подтверждение/отзыв и immutable snapshots.
Решение: map-2 поверх текущих хранилищ как derived read-model + impact view, без миграции ownership в единый центральный каталог.
Риск: семантический центр решений под видом единого графа; mitigation - локальные domain verdicts и per-domain authoritative data.

## ADR-004: Cloud topology
Решение: UI VM public + core VM private сначала. Для физически распределённого E4 отдельно 3 domain VMs и broker/control; одна core VM не даёт доказательства изоляции физического хоста.
Риск: 24/7 облачные затраты, открытые админ-порты. Mitigation: расписание, budget caps, security reviews.

## ADR-005: Агенты и безопасность
Решение: доступные LLM via API только для candidate generation/critique; deterministic governance + strict provenance. При недоступной модели ручной маршрут, нет автоматического разрешения.
Риск: hallucinated mappings, prompt injection через контракты, стоимость и непредсказуемость. Меры: schema validation, allowlisted tool calls, scope, quotas, HITL.

## ADR-006: Startup pivot без переписывания ВКР
Смена трека на «Стартап» - управленческое требование проекта, не доказательство product-market fit. Отдельно нужны buyer/user segmentation, problem discovery, value, UX, demo, pilot proposal, economics; H1 остаётся исследовательской.
Риск: некорректные обещания сокращения инцидентов и TTM без данных.

## Обязательные проверки перед решением
- Какую роль занимает первый откликнувшийся участник, какой текст приглашения ему направляли, язык и цель звонка?
- Есть ли действующий грант Cloud.ru/ресурсы/квоты, доступ к API моделей, DNS-домен и безопасный канал администрирования?
- Что в репозитории реально задеплоено и какой интерфейс/API существует?
- Как разрешаем V1-oracle? Авторское решение обязательно перед финальным E3.
- Можно ли использовать присланные артефакты и сохранять интервью-цитаты? Только с разрешением.

## Приоритеты рисков
P0: утечка секретов/PII; ложное ACCEPT; смешение oracle/evaluation; неправомерные обещания реализации.
P1: неполный registry; конфликт V1-oracle; нестабильный демо-UI; неконтролируемые Cloud.ru расходы.
P2: ненужный graph DB; чрезмерное количество моделей; попытка сделать production self-service до customer discovery.
