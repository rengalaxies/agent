# Cloud.ru: потребление ресурсов и бюджет по стадиям
Дата проверки публичных тарифных страниц: 2026-10-13. Это **сценарная модель**, не коммерческое предложение. Перед provision проверить доступность конкретного VM flavor/региона и итоговую корзину; нельзя заменять рублёвые цены выдуманными.

## Что тарифицируется
VM compute (часы включённого состояния), boot/data disks (ГБ-часы даже при выключенной VM), публичный IPv4 (часы аренды, даже при выключенной VM), возможный SNAT, object storage, Foundation Models (отдельно входные/выходные токены), дополнительные сервисы/снимки. У Cloud.ru входящий/исходящий VM-трафик заявлен временно нетарифицируемым; проверить актуальность на день запуска.

## Подтвержденные примеры ставок (с НДС, опубликованные Cloud.ru)
- Аренда одного публичного IPv4: **0,2074 руб./час** (~149,33 руб. за 720 ч).
- 12 vCPU/24 GB: **23,7534 руб./час** (~17 102,45 руб. за 720 ч).
- 12 vCPU/48 GB: **32,025 руб./час** (~23 058 руб. за 720 ч).
- 16 vCPU/64 GB: **31,9152 руб./час** (~22 978,94 руб. за 720 ч).
Это лишь опубликованные flavors; тариф небольших UI-VM 2/4, private 8/32 и storage **здесь не подтверждён**. Значит, приведённые ниже маленькие ВМ - ресурсный план, а не оценка их конкретной цены.

## Ресурсная матрица
| Этап | Вычисления | Storage provisioned | LLM | Режим |
|---|---|---|---|---|
| P0: интервью/макет | локально | 5-10 GB assets | 0-30 вызовов | без облака |
| P1: публичный demo | UI 2 vCPU/4 GiB + core 8 vCPU/32 GiB | UI 25-40 GB; core 150-250 GB | 50-300 вызовов/нед. | UI 24/7, core по необходимости |
| P1+: тяжёлый интеграционный пилот | UI тот же; core 12-16 vCPU/48-64 GiB | core 250-350 GB | 300-1500 вызовов/нед. | расписание, stop idle |
| P2: E4 multi-VM | 3 x (4 vCPU/16 GiB) + broker/control 8 vCPU/32 GiB + UI | 100-150 GB/dom + 150-250 GB platform | число вызовов из E4 manifest | временные стендовые окна |
| P3: E1 load | P2 + generator 8 vCPU/32 GiB | +100-200 GB на результаты и traces | deterministic core - 0; agent path - измерять | 60 запусков* до корректировки пилота |

Примечание: три разные конфигурационные среды ВКР - это профили внутренних/партнёрских/новых доменов. Не путать их с обязательством держать три разных облачных provider/region одновременно. Для физической проверки E4 выделить три доменных VM (в одной зоне), а межзоновые испытания отдельно обосновать.

## Диск - расчёт, не угадывание
Базовая формула raw_GB = event_rate_per_sec * seconds * avg_payload_bytes / 1e9.
Пример 1000 ev/s * 900 s * 2048 bytes ~ 1.84 GB raw. Kafka retention + metadata + replication + indexes + containers + traces могут увеличить фактическое использование. На пилоте измерить коэффициент A = disk_used / raw_input_bytes на каждом сервисе; storage = OS+images + retained event log*A_log + DB*A_db + observability + headroom 30%.
Ограничить сроки хранения синтетики; сохранять seed, manifests, hashes, метрики, выбранные трассы, а не вечные копии всех потоков. Проверять watermark 70/85/95%; отдельный volume для брокера и DB при росте.

## Модель токенов
C_LLM = N_calls * (input_tokens_per_call/1e6*P_input + output_tokens_per_call/1e6*P_output) + retries/caching/other charges.
Пример планирования, НЕ замер: малый шаг 1800 входных + 500 выходных токенов; тяжёлый 8000+2000; в графе до 4-6 ролей, но не каждый сценарий обязан вызывать каждую роль. Для 100 агентных сценариев по 4 шага малых: ~0.72 млн input + 0.20 млн output, до повторов. При 2x резерве: ~1.44 млн input + 0.40 млн output.
Ставка на 2026-10-13 из опубликованной таблицы для **Claude Haiku 4.5**: input 196,42 руб./1 млн, output 982,10 руб./1 млн; пример 100 сценариев*4 шага*2x reserve = ~675,69 руб. **только токены** этой модели, без premium models, инфраструктуры, cache и сетевых/служебных расходов. Это иллюстрация, не обязательный выбор модели. Смена модели и контекста резко меняет cost.

## Маршрутизация моделей
- 0: детерминированные проверки, запретительные инварианты, протокол и V2 **без LLM**.
- Small model: извлечение кандидатов семантики, нормализация текста, предложение связей.
- Strong model on-demand: сложный semantic conflict, поиск противоречий/критик, подготовка объяснения для человека.
- Policy Engine отдельно валидирует типизированные доказательства; confidence LLM не разрешает RELEASE.
- Зафиксировать model ID/revision, price, prompts checksum, tokens, latency, retries, cache hits, errors в run_manifest.
- При высоких расходах остановить агентные вызовы, не менять молча семантические правила. Детерминированный контур продолжает работу на достаточных формализованных входах.
- Не отправлять реальные пользовательские/договорные сведения в внешний model API без согласования и оценки безопасности.

## Budget envelope (предлагаемый лимит расходов, а не прогноз тарифа)
| Пакет | Ограничение денег | Что допустимо |
|---|---:|---|
| Pilot lean | до 15 000 руб. | короткое облачное окно + стабильный UI только в нужный период, малый объём моделей |
| Working target | до 50 000 руб. | несколько итераций интеграции, публичный демо-UI, тесты моделей, E4 в коротких окнах |
| Expanded | 70 000-120 000 руб. | больше окон multi-VM, повторов и страховки |

Важное ограничение: лимит 50 000 руб. не является доказательством, что можно держать 12/48 VM 24/7 вместе с остальными сервисами. Например, **две** постоянно включённые 12/48 VM = 46 116 руб. за 720 ч уже без дисков, IP и моделей. Поэтому нужны расписание, autosuspend/ручная остановка и предварительная калькуляция. Для production uptime 24/7 пересчитать отдельно.

## Учёт и стоп-правила
До создания ресурсов: утвердить бюджет по фазам, поставить billing alerts на 50%/75%/90% лимита, владельца реакции, еженедельную таблицу `date; resource; hours; billed RUB; input/output tokens; model; purpose; run_id`. По 90% - остановить необязательные ВМ и LLM, проверить persistent IP/disks. Избегать автоматического выключения UI в согласованные часы интервью.
Перед основным экспериментом вручную зафиксировать реальные тарифы на дату и условия кредита/гранта; не смешивать денежные расходы, provisioned ресурсы и фактический CPU/RAM.
