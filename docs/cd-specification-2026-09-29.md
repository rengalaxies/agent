Статус реализации пакета 2: локальный трёхпроцессный E4 выполнен в ускоренном и номинальном профилях. [Проверки и ограничения](package-2-distributed-2026-09-29.md). Облачный прогон и основной E3 впереди; спецификация не означает доказанный промышленный SLA.

Версия: cd-0.1, 29.09.2026. Проект до freeze. Карта knowledge-1 реализована; E4 ещё не выполнен. Три режима: V0, V1-ind, V2. Scoring oracle остаётся отдельной эталонной разметкой.

## C1. Записи карты

Идентификаторы стабильны, версии неизменяемы. Каждая запись имеет record_id, version, owner_domain, confirmed_by, evidence_ref, valid_from, valid_until (null допустим), status=candidate/confirmed/revoked. Stale вычисляется по времени и версии, а не утверждается вручную как подтверждение. Время - UTC RFC3339. Смена владельца требует новой версии и подтверждённых полномочий.

| Тип | Обязательные поля сверх общих | Кто вправе подтвердить |
| --- | --- | --- |
| Team | team_id, domain_id, authority_ref | Владелец домена |
| Product | product_id, producer_team_id, contract_ref, contract_version | Производитель |
| Attribute | product_id, field_path, semantic_profile_ref, contract_version | Производитель |
| Usage | consumer_id, consumer_team_id, product_id, field_paths, purpose, calculation_ref, active | Потребитель; факт подключения должен иметь источник регистрации |
| Obligation | obligation_id, obligation_version, usage_ref, typed_requirement_ref, mandatory | Потребитель в своей области полномочий |
| Coverage | product_id, membership_epoch, registered_consumer_ids, registry_evidence_ref, authority_ref | Регистрационный контур по установленным правилам; не произвольный агент |
| GlobalRule | rule_id, rule_version, scope, predicate_ref, priority | Федеративная функция |

Минимум - использование и требования зарегистрированных участников. Неизвестные внешние потребители не считаются автоматически найденными. В Coverage явно описываются граница регистрации, последний подтверждённый membership_epoch и список обязательных участников; отсутствие Coverage не равно пустому списку потребителей. Коллективные полномочия и источник регистрации должны быть проверяемы; подпись платформенного индекса не подтверждает бизнес-смысл.

## C2. Неизменяемый KnowledgeSnapshot

Поля: snapshot_id; schema_version; proposal_id; product_id; as_of; membership_epoch; old_contract_ref/hash; new_contract_ref/hash; coverage_ref/version/hash; required_consumer_ids; selected_usage_refs; selected_obligation_refs; global_rule_refs; constitution_refs; record_versions_and_hashes; completeness=complete/incomplete/unknown; issues[]; canonical_payload_hash.

snapshot_id = SHA-256 канонического JSON полезной нагрузки без собственного ID/hash; списки ссылок сортируются по ID/version, дубликаты запрещены. Для прототипа канонизация: UTF-8, JSON sort_keys=True, separators=(',', ':'), без NaN и бинарных float для значимых значений. Выбор записей выполняется по as_of; snapshot не меняется после создания. Хеш доказывает целостность, не истинность сведений.

Проверки снимка: все ссылки разрешимы; владелец имеет полномочия; записи confirmed и действуют на as_of; product/field/usage согласованы; каждого обязательного потребителя покрывают активные требования; нет двух конфликтных действующих версий одного требования; membership_epoch соответствует Coverage. Полнота требует подтверждённого реестра регистрации, а не отсутствия найденных связей.

Операции модуля: propose_record; confirm_record; revoke_record; list_impact(product, changed_fields, as_of); build_snapshot(proposal); resolve_snapshot(snapshot_id). Все мутации добавляют версию и событие с actor/authority/evidence; индекс допускает восстановление из доменных записей. Первый прототип можно хранить в типизированных JSON/YAML и строить индекс в памяти; выбор БД не является исследовательским результатом.

## C3. Правила V2

| Ситуация | Семантический итог / состояние | Причина |
| --- | --- | --- |
| Полный подтверждённый снимок, все обязательные проверки TRUE | ACCEPT / готовность к COMMITTED | Доказана совместимость в объявленной границе |
| Есть действующее обязательное требование с FALSE | REJECT / QUARANTINED | Конкретное нарушение с consumer/field/version |
| Нет FALSE, есть UNKNOWN, candidate, просроченная запись, неизвестная полнота | NEEDS_REVIEW / ESCALATED | Недостаточный подтверждённый контекст |
| Отсутствует обязательный LocalVerdict к deadline | NEEDS_REVIEW / ESCALATED | Молчание не означает согласия |
| Действующие локальные правила конфликтуют без правила приоритета | NEEDS_REVIEW | Нужна уполномоченная доработка |
| Изменился membership_epoch/контракт/конституция после фиксации | ABORTED как состояние запуска, без разрешения выпуска | Новый run_id и snapshot |
| Повтор идентичного события | Итог без изменения | Дедупликация event_id; выпуск однократен |
| Два различных ответа одного домена на один run/snapshot | NEEDS_REVIEW; если нарушена целостность - ABORTED | Не выбирать удобный ответ |

REJECT > NEEDS_REVIEW > ACCEPT действует только среди валидных ответов одного снимка. Техническая недействительность не отменяет доказанное нарушение, но может блокировать использование всего запуска. ABORTED не добавляется в enum семантических решений: это отдельное состояние жизненного цикла. После подтверждения недостающего факта создаётся новый снимок и запуск, старое решение не переписывается. Перед COMMITTED проверяется неизменность состава и версий.

Трасса: proposal_id, run_id, snapshot_id, consumer_id, obligation_id/version, field, reason_code, evidence_ref, terminal_state, release_id. Producer view показывает команды и причины; consumer view - изменение определения и его подтверждённое использование. Логирование raw пользовательских данных для этой задачи не требуется.

## D1. H1 и контекст карты

E3 сравнивает V2 и V1-ind парно на одном изменении. Подтверждённые требования дополнительны для V2 по определению механизма; V1-ind не искусственно ослабляется и не получает новые правила после evaluation. Основной каталог качества ядра использует полный фиксированный снимок. Неполная/устаревшая карта образует отдельный негативный набор с ожидаемым NEEDS_REVIEW, чтобы не смешать её полноту и семантическую детекцию.

Эталон отдельно хранит опасность для хотя бы одного обязательного потребителя, допустимость для всех, решение и причины. NEEDS_REVIEW не выдаётся за доказанное обнаружение опасности: публикуются unsafe_accept_rate, strict_reject_rate и review_rate раздельно. false_block_rate в текущем коде объединяет допустимые REJECT и NEEDS_REVIEW; это сохраняется для совместимости порога, а компоненты публикуются отдельно.

Строгие текущие критерии: delta >= 0.15; no dangerous paired regressions; false_block_rate <= 0.10; needs_review_rate <= 0.10; нижняя граница 95% cluster CI > 0; двустороннее cluster sign-flip p <= 0.05. Повторы не увеличивают число наблюдений.

## D2. H3/E4: локальный эталон и время

Локальный эталон - чистая финализация неизменяемого снимка и полного набора валидных LocalVerdict. Он не запускает распределённый транспорт и не использует ожидаемую метку сценария как правило. При отказе ожидаемый исход задаётся спецификацией тайм-аута отдельно, поскольку полного набора ответов нет.

Рабочие параметры стенда (инженерный выбор, не отраслевой SLA): три доменных процесса; deadline TTL=10 s от регистрации запуска по монотонным часам координатора; задержка доставки одного сообщения <=1 s; локальная проверка <=2 s; при доступных участниках финализация <=8 s; после deadline безопасное завершение <=1 s. Время полного завершения не смешивается с временем сетевой доставки. Локальный эталон принимает те же версии, а не актуальные записи "на сейчас".

| ID | Воздействие | Ожидаемый исход | Повторы |
| --- | --- | --- | --- |
| E4-01 | Полные ответы, обычная доставка | Совпадение решения с локальным эталоном | 30 seeded schedules |
| E4-02 | Дублирование каждого события 1-5 раз | Тот же итог; release_count <=1 | 30 |
| E4-03 | Все перестановки трёх локальных ответов | Тот же итог и каноническая трасса доказательств | 6 |
| E4-04 | Обязательный узел не отвечает | Никакого выпуска; NEEDS_REVIEW к TTL+1 s | 30 |
| E4-05 | Все доступны, задержки в границах | Корректное решение <=8 s | 30 |
| E4-06 | Ответ приходит после deadline | Старый запуск не переоткрывается | 30 |
| E4-07 | Старые snapshot/version/run_id | Ответ отклоняется; нет ложного ACCEPT | 30 |
| E4-08 | Membership/контракт меняется перед commit | ABORTED, новый снимок; release_count=0 | 30 |
| E4-09 | Конфликтные вердикты одного домена | NEEDS_REVIEW/ABORTED по целостности | 30 |
| E4-10 | Независимая финализация другим узлом | Тот же итог и набор причин | 30 |
| E4-11 | Отказ домена во время независимого выпуска другого продукта | Независимый запуск завершается; зависимый безопасно ждёт/эскалирует | 30 |
| E4-12 | Два адаптера одинаковой семантики | Канонически эквивалентный снимок и итог | 30 |

Для E4-01/02/03/05/10 использовать случаи ACCEPT, REJECT и NEEDS_REVIEW. Один seed - расписание, не независимое доказательство промышленной надёжности. Критерий H3 на испытанном наборе: ноль нарушений safety и соответствия эталону; все bounded-delay случаи проходят временную границу. Любое нарушение публикуется и исключает заявление о поддержке соответствующего свойства. Фиксируются версии, seed, задержки, журналы, expected/actual, release_count и длительность. Падение координатора с восстановлением выпуска остаётся дополнительным сценарием, если не реализован устойчивый журнал commit.
