## Зачем

Ревьюер должен понять, какое изменение может затронуть другой сервис, увидеть основание и ограничения. Оператор должен отличить проблему анализа от проблемы публикации и понять безопасный следующий шаг. Сейчас есть сценарное demo и технические HTML/JSON surfaces; общей рабочей оболочки нет.

Пять основных сценариев, предложенных для пилота:

1. Открыть изменение из списка или ссылки в трекере, понять итог и применимость к текущему поколению.
2. Перейти от затронутого потребителя к конкретному основанию: repository/path/commit/lines; увидеть факт, гипотезу и неизвестное отдельно.
3. Отличить новый отказ от старого результата; увидеть разницу между завершённым анализом и недоставленным комментарием.
4. Оператору найти недоступный источник/трекер и ошибку привязки PR→задача, получить порядок восстановления.
5. После исправления открыть новое поколение, проверить обновление результата и публикации; если история не загружена, не обещать сравнение с ней.

## Подходы и выбор

| Подход | Польза | Цена/ограничение |
|---|---|---|
| Только панель оператора | Быстрее дать UI над диагностикой10 | Ревьюер остаётся с комментариями и JSON; не решает путь к основанию |
| **Одно приложение, результаты + операторский раздел — выбран владельцем** | Единый вход и навигация; разделение задач и прав | Нужен реальный серверный доступ, нельзя просто спрятать кнопки |
| Два самостоятельных интерфейса | Можно независимо развивать поверхности и поставку | Два входа/навигации/релиза; лишняя сложность первого пилота |

## Предлагаемые границы пилота

Одна организация/одна установка, desktop в приоритете; узкий экран читабелен, native mobile не нужен. Доступ через защищённый частный контур/HTTPS reverse proxy. Это предлагаемое условие первой поставки, не подтверждённая конфигурация нынешней ВМ. Несколько организаций в одном процессе, billing, приглашения по почте, SSO, редактор требований, запуск модели, произвольный shell, SQL и универсальный редактор policy вне первой версии.

Первая рабочая версия показывает **результаты и состояние управления read-only**. Создание подключения/изменение bindings/повторы — следующая отдельная пачка после прототипа и серверных команд. Сейчас таких mutation API нет. Операторская панель полезна и до них: показывает источник проблемы и безопасную инструкцию, без фальшивых рабочих кнопок.

## Навигация и экраны

Предлагаемые browser routes используют новые `/ui/...`; существующие служебные API сохраняют контракт.

- `/ui/login`: вход; просроченная сессия ведёт сюда без показа прежних данных. Возврат только на локальный разрешённый путь; external return URL отвергается.
- `/ui/changes`: «Изменения». Источник/ссылка PR или задачи, заголовок при наличии, время, текущий analysis state, свежесть, publication state. Если metadata нет — честный fallback ID, не выдуманный заголовок. Фильтры только по реально доступным данным. Ограничение списка явно видно.
- `/ui/changes/{opaque_id}`: «Результат». Вверху источник/поколение/pins и краткий итог; затем затронутые потребители/что проверить/ограничения; выбор основания открывает детали в этой странице. Граф вспомогателен: список путей и текстовое доказательство должны работать без него. Диагностические hashes в раскрываемом разделе.
- `/ui/operations`: только operator. Worker/очередь/notices/ошибки, список проблем с переходом к конкретному результату. Liveness процесса не заменяет доступ к источникам. Если состояние не наблюдалось — «не проверено» с временем последнего наблюдения.
- `/ui/connections`: только operator. Репозитории и трекеры: ID/тип/разрешённая область/последнее наблюдение/ошибка. Для Яндекса до подключения — «не подключён», без fake-PASS. Карточка привязки показывает явные PR→tracker target IDs и конфликты; отсутствие binding не означает отсутствие влияния.

Маршруты и состав входят в подтверждённый дизайн первой версии. Визуальная цель — выбранный workbench вариант2; мягкая зелёная палитра и трёхколоночная компоновка сохранены, более компактная типографика принята после замечания владельца. Framework не выбирает продуктовый объём.

## Значение состояний

| Состояние | Что видит человек |
|---|---|
| Нет результата | «Анализ ещё не выполнен»; не «влияния нет» |
| QUEUED/RUNNING | Текущее задание и время наблюдения; предыдущий анализ отдельно, если есть |
| FAILED нового поколения + старый raw | Ошибка нового задания наверху; старый результат с явным STALE |
| CURRENT | Совпадает поколение открытого ресурса; не гарантия совместимости и не успешная публикация |
| PARTIAL/нет доступа/лимит | Что не прочитано и почему; вывод ограничен, зелёного общего успеха нет |
| USEFUL/preliminary без diff | Предварительная область влияния по задаче; не доказанная поломка |
| ABSTAINED/неподдерживаемый случай | Причина воздержания, а не «безопасно» |
| DELIVERED | Доставлен выбранный результат; отдельный статус анализа сохраняется |
| SENDING/UNKNOWN | Исход публикации неизвестен; инструкция readback/recovery, без слепого повторного POST |
| CLOSED/несовместимый raw | Закрытый ресурс либо непригодный результат явно; incompatible raw/document не отображаются |

Известные коды локализуются таблицей с сохранением оригинала в деталях. Неизвестный код не понижается до успеха. Время показывается с timezone, snapshot commit остаётся отличным от destination tip. Обновление страницы не запускает анализ и публикацию.

## Права и аутентификация

Предложение автора для первой установки: две роли — **reviewer** и **operator**. Технический продакт пока reviewer; организационный superadmin пока не выделяется. Все пользователи одной пилотной установки допускаются к одному и тому же согласованному corpus scope. Если нужны разные права на проекты, данный упрощённый режим неприменим: до выдачи доступа нужно расширить серверные grants и проверить отсутствие утечек в тексте, графе, счётчиках и поиске. Скрытие строк в браузере этого не решает.

| Возможность | reviewer | operator |
|---|---|---|
| Разрешённые результаты/основания | Да | Да |
| Операционная очередь/notices/connection metadata/bindings | Нет | Да |
| API-ключи, env, парольные hashes, HTTP Authorization | Нет | Нет |
| Перезапуск/публикация/редактирование policy из первой UI | Нет | Нет |
| Обслуживание секретов и пользователей средствами поставки | Нет | Вне UI, локальными операторскими средствами |

Служебный AGENT_SERVICE_STATUS_TOKEN остаётся server-to-server; в HTML/JS/localStorage/URL/комментарии его нет. Предлагаем серверные сессии с непрозрачной случайной cookie, HttpOnly/Secure/SameSite, ограниченным сроком и отзывом. Для одного частного пилота — локальные учётные записи, пароль вводится локальным оператором вне Git/чата; adaptive password hashing, ограничение попыток входа и отсутствие default password. Конкретную библиотеку/численные параметры срока/хеширования проверяет реализатор в security-пачке, это не повод добавлять SSO сейчас. HTTPS обязателен для развёрнутой версии; loopback прототип не обещает production login.

Роль проверяется на сервере каждого UI API, включая direct resource/evidence URL. Logout/истечение сессии убирает данные и не продолжает background polling. Результаты не кэшируются общим proxy/browser cache. Исходники — текст, не исполняемый HTML; ссылки только на разрешённые источники и схемы. При неизвестных/несовпадающих grants отказ в доступе, без частичного раскрытия результата.

## Данные и необходимые расширения

Существующие `resource_listing/resource_diagnostics`, `/status` и grant-scoped graph — базовые источники. Browser не обращается к operator API напрямую с общим ключом: новый same-origin слой авторизует пользователя и проецирует допустимые поля. Не импортировать demo session/worker/runtime модель в service.

Для первого пилота допустим явно ограниченный список последних100, если владелец принимает эту границу; полный архив требует cursor pagination и server-side filters. Текущий `/result` отдаёт выбранное последнее сохранённое analysis generation, не историю всех поколений. Сравнение версий появляется только после отдельного history API с корректными pins и grants.

Source evidence сейчас может содержать координаты/hash без самого quote. UI сначала показывает ровно доступное основание; «Открыть исходник» только при разрешённом закреплённом URL. Если нужен встроенный quote, добавить отдельный scoped evidence API: только commit/blob из разрешённого результата, проверка целостности/строк, ограничения длины, без произвольных repo/path/revision. При недоступном blob — явное отсутствие фрагмента; не читать текущую ветку вместо snapshot.

Connection/binding metadata endpoint нужен отдельно: секретные конфиги не сериализуются целиком. Пробу внешнего API не выполнять автоматически каждым GET; показывать сохранённое наблюдение. Store/SQLite остаются текущими; A5 PostgreSQL этим не запускается.

## Действия и ключи

Первая UI read-only. В следующей фазе любая команда получает actor/scope/expected generation/idempotency key и durable audit outcome; повтор HTTP не создаёт вторую команду. Неизвестный исход публикации сначала проверяется существующим recovery-протоколом, не «повторить POST». Сброс durable history и удаление результатов не включать как универсальную кнопку.

Ключи хранятся в закрытой операторской конфигурации/secret reference; UI показывает тип и состояние, не значение. Создание/отзыв/ротация пока через средства поставки с фиксацией времени/actor/outcome без токена. Потеря доступа видна как отдельная проблема. Следующая UI-ротация потребует отдельного дизайна прав и одноразового ввода. Журнал первой версии охватывает вход/выход/отзыв сессии и административные операции вне UI в доступном объёме; не заявлять полноценный immutable audit до реализации.
