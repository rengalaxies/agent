# Демонстрационный стенд графа зависимостей: проект решения

Дата: 21 октября 2026. Статус: спецификация согласована владельцем продукта 21 октября 2026; реализация и развёртывание этим документом не подтверждены.

## 1. Цель и основание

Дать разработчику и потенциальному участнику пилота возможность увидеть законченный путь: обнаружить зависимость по исходникам, получить контекст до изменения, понять риск после diff, проверить последствие на работающих сервисах, исправить потребителя и повторно использовать обновлённое знание.

Основной пользователь графа — coding agent в связке с разработчиком. UI делает доступными контекст, основания и историю. Синтетический стенд показывает работу механизма; спрос и экономию труда проверяет отдельный внешний пилот.

Техническое основание — [PR №28](https://github.com/rengalaxies/agent/pull/28), изученный HEAD `f1c4546725e759ffc06ca0281f7103132dbcfe73`, профиль `http-requests-2`:
- [Фактический CLI и ограничения](https://github.com/rengalaxies/agent/blob/f1c4546725e759ffc06ca0281f7103132dbcfe73/examples/agent_graph/README.md).
- [Реализация CLI](https://github.com/rengalaxies/agent/blob/f1c4546725e759ffc06ca0281f7103132dbcfe73/src/agent_graph/__main__.py).
- [Политика и контракты](https://github.com/rengalaxies/agent/blob/f1c4546725e759ffc06ca0281f7103132dbcfe73/src/agent_graph/contracts.py).

PR остаётся draft для повторной технической приёмки после исправления R1–R7. Подключение и развёртывание демо выполняются на принятом точном SHA после устранения блокирующих замечаний; текущий HEAD не считается заранее принятым. Проект решения находится в отдельной ветке от main и не меняет ветку PR №28.

## 3. Реальный предметный сценарий

### Сервисы и исходники

- Orders API: FastAPI, GET /orders, 250 детерминированных заказов. Базовая версия возвращает всю коллекцию при отсутствующем page_size; параметр cursor уже предусмотрен.
- Reporting: Python requests, один запрос без page_size; ожидает полную коллекцию.
- Billing: Python requests, обходит страницы по cursor.
- Health: вызывает отдельный Status API с похожим маршрутом /orders; это контроль ошибочного сопоставления разных сервисов.
- Новый Export consumer добавляется в ходе показа, без заранее подготовленного ребра в графе.

У каждого логического сервиса отдельный каталог/снимок репозитория и идентификатор. Монорепозиторий стенда может хранить их исходные заготовки; в анализ передаются отдельные разрешённые корни. Оператор задаёт соответствия адресов сервисам и разрешения, но не список зависимостей. Корень Export изначально разрешён, существует и не содержит HTTP-вызова: шаг E добавляет новый callsite в этот корень без изменения policy/view_id. Это обнаружение новой зависимости внутри разрешённой области, не автоматическое подключение неизвестного репозитория. Добавление действительно нового корня меняет view_id и требует нового prepare_context; межобластное сравнение не имитируется.

Тестовые данные и независимые проверки полноты находятся вне исследуемого корпуса. Подтверждённое требование Reporting получать полную коллекцию хранится отдельным доверенным источником и digest в policy; оно доступно участникам сравнения. Код вызова сам по себе не утверждает бизнес-требование.

### Последовательность показа

| Шаг | Действие | Проверяемый результат |
|---|---|---|
| A | Запустить базовую версию; prepare_context | Reporting и Billing получают все 250 уникальных ID; граф извлекает их вызовы Orders и отдельный вызов Health к Status |
| B | Подготовить diff: default page_size меняется с None на 100 | analyze_change показывает условный риск Reporting с основаниями; развёрнутая версия ещё A |
| C | Оператор запускает версию B в изолированном стенде | Reporting получает 100 из 250 ID; Billing — полный набор; независимая проверка выявляет неполноту Reporting |
| D | Внешний coding agent исправляет Reporting и запускает проверки | Воспроизводимая проверка получает все 250 уникальных ID; новый анализ пересматривает вывод, история B сохраняется |
| E | Добавить вызов Orders в заранее разрешённый, ранее не содержавший его корень Export и явно обновить источники | Обнаруживается новая зависимость без записи готового ребра |
| F | Следующее изменение/повторный запрос | Видны доступное накопленное знание, версии и реальные затраты пересканирования |
| G | Сбросить только текущую демонстрационную сессию | Новый показ начинается с A; предыдущая история доступна отдельно |

Проверяется множество ID, количество и отсутствие дублей, а не только сумма или HTTP 200. Billing считается корректным по фактической независимой проверке; CURSOR_LOOP_OBSERVED остаётся синтаксическим признаком графа и не удостоверяет полноту.

Дополнительный отрицательный сценарий: динамический URL либо недоступный разрешённый источник. UI показывает неполноту и её причину, а не «потребителей нет».

## 4. Интерфейс первого показа

Один основной экран, рассчитанный на desktop, с понятными русскими названиями:

1. Верхняя строка: выбранное изменение, версия предложенного кода, версия запущенных сервисов, ID контекста, свежесть и состояние задачи.
2. Карта слева: сервисы, операции и потребители; различимые направления связей. Клик по ребру открывает callsite и основание. Требование, наблюдение и кандидат имеют разные подписи; цвет не является единственным признаком.
3. Рабочая область: задача разработчика, diff, затронутые потребители, механизм возможного последствия, предлагаемая проверка и нерешённые вопросы.
4. Панель оснований: repository, путь, revision/digest, строки и точный фрагмент. Исходники отображаются как текст с экранированием HTML.
5. История: подготовка контекста, анализ, действия внешнего агента при наличии записи, запуск теста, исправление и новый анализ. Для старых результатов видны версии и исторический статус.

Действия UI: обследовать разрешённый корпус, проанализировать предложенную версию, открыть основание, обновить состояние и предложить исправление знания. Human correction идёт через предусмотренную capability correct, с происхождением, supersedes и проверкой версии. Она не переписывает технический факт или утверждённое требование.

Сброс и переключение версий стенда — явные действия оператора. В интерфейсе просмотра не появляется универсальное поле shell-команды или автоматический допуск к выпуску.

На первом закрытом показе оператор может выполнять запуск сервисов и coding-agent работу из локальной сессии; UI показывает поступившие реальные результаты. Это маркируется как работа оператора/внешнего агента. Последовательность кнопок с заранее заданным исправлением не выдаётся за автономное исправление моделью.

## 5. Архитектура и границы исполнения

| Компонент | Ответственность и размещение |
|---|---|
| Существующий Nginx | Reverse proxy к новому backend/UI; настройка отдельным location или host после резервной копии текущего конфига |
| UI | Статические assets, тот же origin с API |
| Backend и последовательный worker | Журнал задач/сессий, валидация запросов, вызов CLI фиксированным argv; один серверный процесс с одним worker выполнения |
| agent_graph | Единственный источник результатов discovery, контекста, анализа, proposals и их доверия; SQLite отдельно от web-журнала |
| Sandbox services | Orders, Reporting, Billing, Health/Status, при необходимости Export; внутренняя Docker-сеть |
| Операторский runner | Фиксированные сценарии запуска/проверок и переключения тестовых версий; вызов оператором по SSH, отдельно от web-процесса |
| Внешний coding agent | Получает JSON-контекст, готовит diff и запускает проверки в своей рабочей среде |

Backend публикуется только на 127.0.0.1:18081. Порты 8000/8080 сохраняем за существующими конфигурациями. Сервисы sandbox не публикуются в интернет. Web-процесс не получает Docker socket, членство в docker group, sudo, SSH-ключ или cloud credentials.

Один web/backend контейнер может обслуживать статические assets и worker; дополнительные хранилища не вводим. Код/образы собираются вне ВМ и доставляются как версионный пакет с digest. Рабочие имена новых каталогов: /opt/agent-graph-demo/releases и /var/lib/agent-graph-demo. UID приложения и права каталогов фиксируются при реализации.

Старую dmrp-ui.service и /opt/agent-cloud-runtime обследовать до развёртывания, сохранить конфигурацию и журналы. Не запускать старую службу ради нового демо и не читать её секреты в отчёт. Изменение её автозапуска — отдельный явно описанный шаг плана, если оно действительно требуется.

### Один активный sandbox на установку

На всей ВМ одновременно допускается не более одного работающего sandbox-проекта, включая Orders/Status и consumer/test jobs. Несколько сохранённых сессий означают несколько историй и снимков, а не несколько запущенных окружений. Backend/UI — отдельный постоянный Compose-проект agent-graph-demo; sandbox использует имя agent-graph-demo-sbx-<session UUID>.

Операторский runner хранит root-owned runtime registry с generation, состоянием STOPPED/STARTING/RUNNING/UNKNOWN, session_id, project_name, manifest_sha256 и observed_at; web читает его через read-only mount и не может менять. Runtime observation не считается криптографической attestation. SQLite хранит историю наблюдений, но поле running в текущем ответе выводится из свежего registry: остановленный или принадлежащий другой сессии runtime не показывается работающим.

Все graph/consumer/test jobs используют общий installation workload lock. Порядок блокировок фиксирован: workload lock → root runtime guard для runner → session lock; graph worker берёт workload lock → session lock. Runner с эксклюзивным runtime guard и CAS generation:
1. Проверяет registry и точные Docker labels/project IDs из списка собственных demo-проектов; посторонние проекты и постоянный backend исключены.
2. Перед запуском другой session/version выполняет down предыдущего sandbox по его закреплённой конфигурации без -v, проверяет отсутствие его работающих контейнеров и записывает STOPPED. История, manifests, receipts и постоянный state backend сохраняются.
3. Только после подтверждённой остановки записывает STARTING для новой версии и выполняет up. После readiness и сверки manifest записывает RUNNING с новой generation. Повтор того же session/manifest идемпотентен; stale generation не запускает второй проект.
4. При неудачной остановке, противоречии registry/Docker или прерванном STARTING сохраняет UNKNOWN и блокирует новый запуск до reconciliation. Recovery не возобновляет все исторические Compose-проекты.

Переключение target_version в POST jobs меняет только предложенный корпус, не Docker runtime. UI показывает прежний running, пока оператор не выполнит runner. У web по-прежнему нет полномочий на Docker.

Reset активного стенда — явная двухшаговая операция: оператор вызывает run_scenario.py stop --session ID --expected-generation N, runner останавливает текущий sandbox и обновляет registry; затем POST reset с expected_revision и idempotency_key создаёт новую A-сессию без автоматического запуска контейнеров. Пока registry не STOPPED, reset возвращает 409 operator_stop_required (для UNKNOWN — 409 runtime_unknown) с понятным сообщением UI. Backend проверяет registry под workload lock, поэтому новый старт не может вклиниться между проверкой и reset. Сбой остановки сохраняет текущую сессию; успешный reset не удаляет её историю.

Приёмка: пять последовательных показов разных сессий и смен A→B→D→E/reset, два конкурентных activate, неудачный down и crash во время STARTING. На каждом наблюдаемом шаге количество работающих собственных sandbox-проектов <=1; перед новым up прежний уже остановлен; после stop/reset — 0; постоянный backend и чужой контрольный проект продолжают работать. Контейнеры исторических sandbox не накапливаются и не возрождаются после рестарта Docker.

## 6. Контракты приложения

Предлагаемые HTTP-маршруты нового backend; в PR №28 их пока нет:

| Маршрут | Назначение |
|---|---|
| POST /api/demo/sessions | Создать изолированную сессию из фиксированного сценария |
| GET /api/demo/sessions/{id} | Код/версия runtime, текущие контексты, задания, проверки и история |
| POST /api/demo/sessions/{id}/jobs | Поставить разрешённое действие prepare_context/analyze_change/investigate в очередь |
| GET /api/demo/jobs/{id} | Состояние, частичный результат, ошибка и ссылки на основания |
| GET /api/demo/sessions/{id}/graph | Узлы и рёбра из сохранённого ответа модуля |
| GET /api/demo/sessions/{id}/evidence/{id} | Разрешённый фрагмент по серверному citation ID |
| POST /api/demo/sessions/{id}/proposals | Кандидат или разрешённое human correction |
| POST /api/demo/sessions/{id}/reset | После остановки sandbox оператором закрыть текущую сессию и создать новую из A; expected_revision/idempotency_key обязательны, история сохраняется |

Браузер передаёт task, известный scenario/action ID, expected session revision и idempotency key. Он не выбирает пути на хосте, executable, policy, произвольный URL, доверенные digests или identity субъекта. CSRF/origin проверяются на изменяющих запросах. Обычный опрос состояния не выполняет скрытый дорогостоящий перескан.

### Выбор предложенной версии через POST jobs

Отдельный маршрут materialize не добавляется. Оператор UI вызывает POST /api/demo/sessions/{id}/jobs с таким JSON:

```json
{
  "action": "analyze_change",
  "expected_revision": 1,
  "idempotency_key": "select-B-001",
  "payload": {
    "target_version": "B",
    "base_context_id": "published-context-id",
    "task": "Ограничить страницу Orders до 100 заказов"
  }
}
```

Для analyze_change обязательны target_version из B/D/E и опубликованный base_context_id той же сессии и профиля; task — необязательная строка до 4000 символов. manifest выбирается сервером из закреплённого сценария, пути и digests из браузера не принимаются. Для prepare_context payload содержит только необязательный task; исходную A материализует создание сессии. Для investigate payload содержит только context_id опубликованного контекста. Лишние поля/сочетания дают 422.

Правила очереди и публикации:
1. Сначала проверяется идемпотентный повтор: одинаковые actor/session/key и каноническое тело возвращают тот же job даже после публикации новой revision; другое тело с тем же ключом — 409 idempotency_conflict.
2. Для нового запроса одной SQLite-транзакцией проверяются expected_revision=r и отсутствие незавершённого mutating job этой сессии, резервируется job с session_revision=r и target_revision=r+1, устанавливается pending_job_id. Ответ 202 содержит job_id, status, session_revision и target_revision. Второе конкурентное переключение с тем же r получает 409 session_busy либо revision_conflict; приём запроса ещё не меняет опубликованные proposed/running.
3. Worker под общей блокировкой выполнения и session lock повторно сверяет revision/pending_job_id, проверяет закреплённый целевой manifest, материализует его в стабильные рабочие корни и вызывает analyze_change с зарезервированным base_context_id. Изменение корней и вызов CLI — один сериализованный job.
4. При успешно завершённом CLI-вызове CAS по r/pending_job_id одной транзакцией публикует revision=r+1, scenario_version, proposed_manifest_sha256, current_context_id и result_ref, затем снимает reservation. Полнота анализа/найденный риск остаются отдельными полями: SUCCEEDED не означает «изменение безопасно». running_manifest_sha256 не меняется. Применимость selection-result оценивается по target_revision, а не по исходной session_revision задания; результат с более старой target_revision остаётся историческим.
5. При ошибке, отмене, deadline или crash незавершённая materialization восстанавливается из последнего опубликованного manifest до допуска следующего mutating job. Сначала под теми же lock выполняется reconciliation файлов и reservation, затем reservation снимается. SQLite и файловая система не объявляются одной атомарной транзакцией. Принятые модулем immutable записи сохраняются в истории; непубликованный/поздний результат не становится текущим. Восстановление не перезаписывает уже опубликованную более новую revision.
6. UI показывает queued target_version отдельно от опубликованного proposed и реально running; reset/correction во время reservation возвращают 409 session_busy. Это исключает незаметную смену кандидата между нажатием анализа и получением результата.

Жизненный цикл задания: QUEUED, RUNNING, SUCCEEDED, PARTIAL, FAILED, CANCELLED, UNKNOWN_AFTER_RESTART. Семантический тестовый FAIL хранится отдельно от успешного выполнения задачи сбора результата. Отмена не считается подтверждённой остановкой внешнего inference billing.

Начальные пределы: одно исполняемое задание; до четырёх ожидающих, затем явный busy; общий job deadline 180 секунд; max_files 256, max_file_bytes 65536, max_corpus_bytes 2000000, scan_seconds 15, freshness_seconds 3600, max_tool_lines 60. Лимиты — стартовая конфигурация, не измеренная производительность. Очередь и история устойчивы к рестарту; RUNNING без подтверждённого завершения становится UNKNOWN, автоматически не повторяется.

## 7. Снимки, версии и результаты проверок

В каждой сессии раздельно фиксируются:
- точный принятый SHA кода продукта и профиль extractor;
- исходный manifest корпуса и предложенный manifest;
- фактически запущенная версия сервисов и dataset digest;
- base_context_id, context_used_id, basis, задания и проверки.

Исходные и кандидатные версии архивируются неизменяемо. У анализируемых корней внутри сессии стабильные пути: изменение root меняет view_id графа. Контроллер последовательно обновляет рабочую копию из закреплённого снимка под той же блокировкой, что защищает запуск анализа; параллельное редактирование во время обследования не допускается. Перед запуском сверяются digests, после результата сохраняется использованный manifest.

У каждого проверочного запуска есть scenario/session/revision, версия реально выполнявшегося кода, dataset digest, команда из allowlist, время, exit code и проверенный результат. Несовпадение версии с текущим кандидатом помечает результат историческим/неприменимым.

Тесты выполняет отдельный runner, а не agent_graph. Если результат передан в граф через report_check, статус остаётся EXTERNAL_REPORTED. UI может показать фактический результат локального runner с указанием его происхождения, но не изображает криптографически удостоверенный корпоративный receipt.

## 8. Модель и способы показа

Два явно различимых режима:
- Детерминированный: реальные парсеры/граф/сервисы/проверки, без LLM-вызовов. Недоступность модели видна в UI; исследование моделью не симулируется.
- С реальной моделью: investigate через один одобренный endpoint, существующий ModelConfig, явный маршрут данных и token/денежные лимиты. Показываются реальные вызовы и кандидатные предложения.

Первый закрытый прогон инфраструктуры допустим без LLM. Для заявления «встроенный агент реально сопровождает граф» требуется второй режим и квалификация интеграции на сценарии. Маленькая CPU-модель не становится заменой выбранной конфигурации только потому, что помещается в RAM. В этой спецификации модель и GPU не закупаются и не квалифицируются.

Внешний coding agent сохраняет собственную среду разработки. В демонстрации фиксируем хотя бы один реальный вызов prepare_context до предметного плана и analyze_change после diff. Действия оператора и модели не смешиваются в истории.

## 9. Ресурсы, доступ и эксплуатация

Предлагаемые стартовые memory caps: backend/worker/graph 768 MiB, Orders 192 MiB, Status 128 MiB, каждый consumer job 128 MiB, тестовый runner 256 MiB. Это плановые пределы, не гарантия fit; consumer/test jobs идут последовательно с анализом. Общее целевое потребление приложений до 2 GiB, сборки на ВМ не выполняются.

При превышении лимитов возвращается ошибка/частичный результат; swap не используется как доказательство достаточной RAM. Логи ротируются; история ограничивается отдельной политикой хранения с сохранением экспортируемого отчёта.

Поставка в два проверяемых этапа:
1. Закрытый приёмочный показ оператором через SSH-туннель к loopback backend. Доступ участнику через его браузер этим ещё не обеспечен.
2. Для самостоятельного внешнего просмотра: выбранное имя хоста, HTTPS и аутентификация всего UI/API, сессии с разграниченным доступом; отсутствие публичного произвольного исполнения. Точный домен и способ выпуска сертификата выбираются по фактически доступному имени до этого этапа.

В качестве первого полноценного показа потенциальному участнику допустима демонстрация экрана оператором. Обещание «участник открывает ссылку и работает сам» считается выполненным только после этапа 2.

Чувствительные файлы и модельный секрет доступны только нужному серверному компоненту. Ключи не передаются браузеру или модели. Многоарендность, SSO и устойчивость к злонамеренному владельцу OS-account не заявляются.

## 10. Приёмка

| Область | Необходимое свидетельство |
|---|---|
| Discovery | Рёбра извлечены из разрешённых исходников; исходной таблицы consumers нет; control Health/Status не сопоставлен с Orders |
| Реальное поведение | В A оба потребителя получают ровно заданное множество 250 ID; в B Reporting теряет 150; Billing полон; после исправления Reporting полон |
| UI | В браузере можно найти затронутого потребителя, открыть источник, различить риск/тест и proposed/running версии; ошибки и UNKNOWN видны |
| Обновление | Новый consumer найден, удалённый/изменённый пересмотрен, старое основание помечено устаревшим |
| Исправление знания | Разрешённая correction сохраняется в истории и корректно устаревает при смене basis |
| Повторный показ | Пять последовательных показов не накапливают контейнеры; одновременно <=1 sandbox, перед запуском нового старый остановлен; reset после stop создаёт чистую A-сессию и сохраняет историю, backend/чужие проекты не затрагиваются |
| Надёжность | Повтор запроса не запускает второй job; рестарт не выдаёт незавершённое за успех; переполнение очереди/тайм-аут видимы |
| Границы | Нет Docker/sudo у web, произвольного shell из UI, source HTML-инъекции, чтения вне allowlist и ложного PASS от графа |
| Ресурсы | На ВМ записаны фактические пиковые RAM/CPU и длительности cold/warm, OOM-события, disk/log growth; отсутствуют OOM и необъяснённые failures на серии показов |
| Внешний доступ | Для этапа 2 проверены HTTPS/auth, отсутствие доступа без входа и корректные серверные границы сессий |
| Модель | Детерминированный и реальный режимы различимы; заявление о live-agent подкреплено настоящим запуском |
| Перезапуск | Проверены сохранность SQLite/истории и восстановление сервисов после согласованного рестарта стенда |

Не заменяем эту приёмку общим числом unit-тестов. Проверки выбираются по изменяемым границам; документация и косметические изменения не требуют повторного платного inference.
