# Фиксация baseline V1-ind для протокола 0.3.0

## Роль baseline

`V1-ind` - воспроизводимая промышленно мотивированная конфигурация контроля, с которой в основном эксперименте сравнивается V2. Это не реализация одного конкретного продукта, не прямой запуск Pact Broker или Confluent Schema Registry и не максимально возможная ручная настройка всех существующих платформ. Baseline воспроизводит выбранные классы типовых механизмов, доступных до consumer-aware интерпретации обязательств: структурную совместимость схемы, заранее заданные policy-as-code правила и явно объявленные миграции.

`V1-ind` не получает полный `ConsumerObligation`, эталонную метку или правило, созданное под отдельный evaluation-сценарий. Политика одинакова для development- и evaluation-наборов.

## Проверенные промышленные возможности

| Возможность | Основание | Отражение в V1-ind |
|---|---|---|
| Совместимость структуры и типов | [Confluent Schema Registry: Schema Evolution and Compatibility](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html) описывает backward, forward, full и transitive проверки версий схем | Общая структурная проверка выполняется во всех режимах |
| Декларативные правила качества и ограничений | [Confluent Data Contracts](https://docs.confluent.io/platform/current/schema-registry/fundamentals/data-contracts.html) поддерживают domain validation, field constraints и действия при нарушении | Фиксированные правила lineage и purpose представлены как policy-as-code |
| Преобразования между версиями | Confluent Data Contracts поддерживают upgrade/downgrade migration rules и транзитивное применение преобразований | Изменения единиц и области идентичности требуют заранее объявленной проверенной миграции |
| Контроль по опубликованным проверкам потребителей | [Pact Broker `can-i-deploy`](https://docs.pact.io/pact_broker/can_i_deploy) принимает решение по матрице ранее выполненных consumer-provider verification results | Возможность учитывается при определении границ промышленного comparator, но реальный Pact Broker в детерминированном ядре не запускается; поэтому результат нельзя выдавать за продуктовое сравнение с Pact |
| Формализованные схема и правила качества | [ODCS 3.0.2](https://bitol-io.github.io/open-data-contract-standard/v3.0.2/) описывает логическую и физическую схему, authoritative definitions и data-quality rules | Контракт и политика представлены машиночитаемыми отдельными артефактами |

## Замороженная матрица возможностей

| Семейство | Изменение | Правило V1-ind | Почему так |
|---|---|---|---|
| F1 | Смысл и формула | Только структурная проверка | Автоматическая проверка произвольного бизнес-смысла не выводится из одной схемы. Специальное правило формулы потребовало бы знания обязательства конкретного потребителя |
| F2 | Единица и масштаб | `require_migration_on_unit_change` | Декларативная миграция является воспроизводимым промышленным механизмом |
| F3 | Временное окно | Только структурная проверка | Минимально допустимое окно зависит от конкретного потребителя и не задаётся универсальным schema-compatibility правилом |
| F4 | Область идентичности | `require_migration_on_identity_change` | Без проверенного отображения новый идентификатор нельзя считать совместимым со старой областью |
| F5 | Происхождение | `allowed_sources = [crm, transactions, loyalty, web_events]` | Это заранее зафиксированная федеративная allowlist для модельного стенда |
| F6 | Цель использования | `required_purposes = [risk_scoring]` | Это заранее зафиксированный обязательный purpose для модельного стенда |

## Ограничения baseline

- F5 и F6 относятся к конфигурации трёх модельных доменов, а не объявляются универсальной политикой любой организации.
- Реализация сравнивает алгоритмические стратегии в модельном стенде, а не конкретные коммерческие продукты или их предельную ручную настройку.
- В промышленном внедрении V1-ind можно усилить ручными правилами, но добавление правила после просмотра evaluation-сценария нарушит протокол эксперимента.
- `V1-oracle` не является baseline: он получает полные типизированные обязательства и используется только как положительный контроль чувствительности.
- Сравнение показывает эффект consumer-aware интерпретации внутри зафиксированной экспериментальной постановки, а не превосходство над любой возможной конфигурацией коммерческого продукта.

## Правило заморозки

После фиксации commit протокола 0.3.0 файл `policies/v1-ind.yaml`, код интерпретатора V1-ind и эта матрица не изменяются до завершения E3. Любое содержательное изменение создаёт новую версию протокола и требует нового evaluation-набора.
