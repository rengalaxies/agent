# Сценарная экономическая модель V1-ind и V2

## Назначение и границы

Модель переводит результаты сравнения V1-ind и V2 в управленчески интерпретируемые категории затрат. Она отвечает на вопрос: при каких предположениях о потоке изменений более точная проверка компенсирует дополнительную стоимость V2?

Модель не является расчетом фактического ROI. Частота опасных изменений, стоимость инцидента, задержки, ручной проверки и владения V2 пока не измерены в организации. Поэтому все денежные параметры выражены в относительных единицах `REU` - эквивалентах стоимости одной стандартной ручной проверки. Значения low/base/high в `business/economic-model.yaml` являются синтетическими точками чувствительности, а не эмпирическими оценками.

## Единица и формула

Для каждого сценария задаются число предложений `N`, внешняя доля опасных предложений `p`, стоимости одного пропущенного опасного изменения `C_escape`, ложного отклонения `C_reject`, ручной проверки `C_review` и фиксированные затраты режима `C_fixed`.

Для режима `m` рассчитывается:

`Cost_m = N * p * r_escape,m * C_escape + N * (1 - p) * r_reject,m * C_reject + N * r_review,m * C_review + C_fixed,m`.

`r_review,m` пересчитывается с учетом заданной доли опасных изменений: это сумма ручных проверок среди опасных и допустимых предложений, а не общая доля из сбалансированного evaluation-набора.

Положительное значение `V2 savings = Cost_V1-ind - Cost_V2` означает преимущество V2 в рамках заданных предположений. Точка безубыточности - минимальная стоимость одного пропущенного опасного изменения, при которой расчетная стоимость V2 не превышает стоимость V1-ind при неизменных остальных параметрах.

## Связь экспериментальных показателей и затрат

| Экспериментальный показатель | Использование в модели | Ограничение |
|---|---|---|
| `unsafe_accept_rate` среди опасных сценариев | Ожидаемая доля пропущенных опасных изменений | Умножается на внешнюю частоту опасных предложений, а не на баланс каталога |
| `false_block_rate` среди допустимых сценариев | Контроль суммы ложных `REJECT` и `NEEDS_REVIEW` | Не монетизируется напрямую, чтобы не считать ручную проверку дважды |
| Допустимый `REJECT` из scored results | Задержка и доработка допустимого изменения | Стоимость задается сценарием |
| `needs_review_rate` и разложение по классам | Ручная проверка | Для пересчета на рабочий поток используются условные доли по классам |
| `dangerous_safe_detection_rate` | Контроль, обратный `unsafe_accept_rate` | Отдельная выгода не добавляется, иначе один предотвращенный случай учитывался бы дважды |
| `median_latency_ms`, `p95_latency_ms` | Не монетизируются | Это время локального вычисления прототипа, а не длительность бизнес-процесса |
| `exact_decision_accuracy` | Диагностическая характеристика | Не имеет однозначной стоимости без типа ошибки |

Расчет извлекает взаимоисключающие исходы из scored results и сверяет их с `unsafe_accept_rate`, `false_block_rate` и `needs_review_rate` в отчете метрик. Несогласованная пара файлов отклоняется.

## Три сценария чувствительности

| Сценарий | Предложений | Доля опасных | Стоимость пропуска, REU | Стоимость ложного REJECT, REU | Фиксированная стоимость V2, REU |
|---|---:|---:|---:|---:|---:|
| Low-impact | 100 | 1% | 5 | 0,25 | 20 |
| Base | 100 | 5% | 50 | 1 | 20 |
| High-impact | 100 | 15% | 200 | 3 | 20 |

Сценарии специально охватывают область, где V2 может не окупаться, и области, где цена пропуска опасного изменения доминирует. Это анализ чувствительности, а не прогноз распределения рабочих изменений.

## Воспроизведение

Development-расчет выполняется только после формирования scored results:

```bash
make business-pilot
```

Команда создает `results/business-case-development.json`. Поле `experiment_purpose` наследуется из отчета метрик, а `realized_roi_supported` всегда остается `false`. После E3 тот же неизменный алгоритм можно применить к confirmatory scored results, однако даже тогда модель покажет только сценарный экономический эффект. Фактический ROI требует организационного пилота и измеренных входных стоимостей.
