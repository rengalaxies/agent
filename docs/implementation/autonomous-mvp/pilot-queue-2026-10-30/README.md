## Исправления

1. `published_result` раньше брал последний DONE job даже тогда, когда пользователю
   была опубликована только заметка о несовместимости. Следующий ответ мог утверждать,
   что скрытый риск «больше не обнаружен». Теперь проверяется совместимость исходного
   документа и соответствие сохранённого доверенного view verdict его reason_code.
   Это также исключает результат с чужим request_id. Последний отклонённый результат
   не заменяется более старым «удобным» результатом. Исходный JSON и история сохранены.
2. Пересчёт после смены основы ставит фоновые jobs на диск. Теперь свежие jobs имеют
   преимущество; при наличии обоих классов после четырёх свежих выдаётся один фоновый.
   Счётчик и классификация сохраняются в приватных checkpoints в той же SQLite.
   Внешний event_id не может выбрать себе другой бюджет. Нет миграции таблиц,
   нового брокера или публичной конфигурации.
3. Фоновое задание получает срок выполнения при первой выдаче, а не теряет его
   в ожидании очереди. Уже начатые jobs не получают новый срок при повторе без
   увеличения attempts или после восстановления lease. `revive()` по-прежнему явно
   открывает новый ограниченный раунд для FAILED jobs — это отдельная операция,
   не продление текущей попытки.
4. При старте история достраивает отсутствующие маркеры фоновых jobs. Используется
   сохранённая позиция в append-only history, а не одноразовый флаг миграции:
   после отката старый writer может добавить немаркированные jobs; следующее
   обновление распознаёт их. SQLite schema version остаётся 1; добавлен индекс jobs_due.

## Ограничения и решения

Ruling: четыре свежих jobs на один фоновый — внутреннее правило планирования для
одного worker, не SLA. Уже выполняющийся анализ не прерывается ради нового события;
ingest и публикации сохраняют прежний приоритет. Гарантии времени при outage нет.

Общий backlog на диске не ограничен этой правкой. Minor deferred: запрос отсутствующего
класса jobs может просматривать весь доступный backlog; полное опустошение большого
однородного backlog имеет квадратичную составляющую. Нагрузочная приёмка на целевой
2-vCPU ВМ не выполнена. Для небольшого выделенного пилота это оставлено наблюдаемым
ограничением; рост нагрузки потребует индексации класса планирования/другого хранения.
Независимый review не является человеческой приёмкой клиентской пользы.
