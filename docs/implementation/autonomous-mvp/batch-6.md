## Уровни доказательств

Уровни не смешиваются. Число с одного уровня не переносится на другой.

| Уровень | Что это | Есть в этой пачке |
|---|---|---|
| L1 синтетический Git-стенд | сгенерированные репозитории, эталон по исполнению кода потребителей | да |
| L2 локальный HTTP-стенд | настоящий сервис: webhook-приёмник, очередь, коннекторы, ядро и граф против локальных эмуляций GitHub и Jira | да |
| L3 живая интеграция | GitHub App, тестовый проект Jira Cloud, установка на ВМ | нет |
| L4 данные компании | настоящие репозитории, история изменений, потребители, инциденты, люди | нет |

Все числа ниже относятся к L1 и L2. Они говорят, что механизм работает на мирах, которые мы сами
построили. Они не говорят, сколько пользы сервис принесёт в компании.

## Что измеряется

Техническая готовность (ворота `technical`): каждое изменение доходит до комментария; на ресурс один
обновляемый комментарий; повторная доставка webhook ничего не пишет; комментарий показывает последнюю
версию; отозванный источник не виден; устаревшее основание не выдаётся за свежее; задержка от
доставки до записи комментария; граф отражает слитое изменение после одной сверки.

Полезность на синтетических стендах (ворота `quality`): верный исход по каждой стадии, полнота по
ломающимся потребителям, ложные срабатывания, верный путь (операция и место вызова), владельцы без
угадывания, отказ от ответа там, где он верен.

Полезность для бизнеса программа не измеряет и не может измерить. Для неё нужны настоящие изменения
компании, их фактические последствия и записанные минуты людей. До этого вердикт по ней
`UNVERIFIED`, и в `program.json` это записано как правило, а не как пропуск.

## Программа 6-r1

Единица счёта: изменение. Задача Jira и PR, который её делает, это одно изменение, а не два. Каждое
изменение идёт на своём стенде и на чистой установке сервиса, состояние между изменениями не
переносится, поэтому изменения независимы и интервал Уилсона для долей по изменениям применим.

| Набор | Изменений | Использование |
|---|---:|---|
| development | 20 | можно смотреть и настраивать; можно перезапускать |
| heldout | 60 | не для настройки; один прогон на конфигурацию после коммита manifest |

Почему 60. Ворота считаются по изменениям. При n = 60 половина 95%-интервала Уилсона: 0,113 при доле
0,7, 0,100 при 0,8, 0,060 при 0,95. Этого хватает, чтобы отличить годный сервис (0,7 и выше) от
монетки (0,5): интервалы не пересекаются. Ноль событий на 60 изменениях ограничивает долю сверху
0,060; ноль на 120 ресурсах (комментарий Jira и комментарий PR) по правилу трёх даёт 0,025. По
семействам (5 изменений) выводов нет, только описание. Разница с baseline парная на тех же 60
изменениях; для непарного худшего случая заметна разница около 0,18, поэтому порог сравнения 0,10
сообщается с обоими интервалами, а не как статистическая значимость. Больше синтетических изменений
не нужно: точность лучше ±0,1 на наших мирах ничего не добавляет к вопросу о данных компании.
Следующий шаг доказательства это история компании, а не больший синтетический набор.

### Семейства

| Семейство | Что проверяет | Dev | Held-out | Ожидаемо: Jira / PR |
|---|---|---:|---:|---|
| F01 truncation | стандартная страница уменьшается; одиночный запрос ломается, курсор и явный `page_size` требуют перепроверки; рядом одноимённый провайдер-приманка | 2 | 5 | answer / answer |
| F02 operation removed | операция удалена, ломаются все потребители | 2 | 5 | answer / answer |
| F03 no impact | правка README или docs; Jira называет сервис или ничего | 2 | 5 | no_impact или abstain / no_impact |
| F04 no consumer | меняется операция без потребителей; потребители другой операции не затронуты | 1 | 5 | no_impact / no_impact |
| F05 runtime only | адрес провайдера в конфигурации развёртывания, ни в одном репозитории его нет; вызов видят только свежие access-логи | 2 | 5 | partial / partial |
| F06 code only | runtime-источник есть, но одного кодового потребителя в логах нет | 1 | 5 | answer / answer |
| F07 stale runtime | как F05, но окно логов двухдневной давности, старше предела свежести 24 ч | 2 | 5 | partial / partial |
| F08 revoked source | репозиторий потребителя был доступен и отозван; он затронут, но показывать его нельзя | 2 | 5 | answer / answer |
| F09 ownership conflict | у одного потребителя две команды, у другого нет записи | 2 | 5 | answer / answer |
| F10 ambiguous Jira | маршрут объявлен двумя провайдерами, Jira не называет ни одного | 2 | 5 | abstain / answer |
| F11 vague Jira | Jira не называет ни маршрута, ни сервиса | 1 | 5 | abstain / answer |
| F12 unclassified | тело объявления меняется так, что классификатора нет | 1 | 5 | answer / partial |

В каждом мире провайдер объявляет ещё одну, неизменную операцию `.../count`, и у неё 1-2
потребителя-свидетеля. Вместе с приманками это даёт отрицательные пары для ложных срабатываний: 42 в
development и 128 в held-out. Ожидаемых пар потребитель-изменение на PR: в development 24 breaking и
10 recheck, в held-out 62 breaking и 33 recheck.

### Стенды

`world.py` строит мир из `random.Random("6-r1:<split>:<index>")`. Имена провайдеров, потребителей,
ключи Jira и проекты двух наборов не пересекаются, байты файлов тоже; это проверяет тест. Коммиты
пишутся сантехникой Git стенда Orders/Reporting (фиксированные автор и даты), поэтому один и тот же
файл изменения всегда даёт одни и те же SHA. Файл изменения (`changes/<split>/<id>.json`) содержит
только то, что видят сервис и baseline: репозитории с ветками, задачу Jira, PR, адреса, маппинг
владельцев, записи access-логов и отозванные права. Факты мира (конфигурация развёртывания, число
записей за день, размеры страниц по веткам) лежат только в эталоне.

### Эталон

`oracle.py` не спрашивает ни сервис, ни статический extractor, ни модель. Функция `load_day` каждого
потребителя исполняется дважды против записывающей подмены `requests`: с провайдерами как на `main` и
как на ветке PR. Подмена отдаёт записи дня с семантикой провайдера: размер страницы по умолчанию для
ветки, явный `page_size`, курсор, удалённый маршрут отвечает 404. Дальше:

- потребитель не вызывает изменённую операцию: `none`;
- вызывает, и результат после изменения другой (меньше записей или HTTP-ошибка): `breaking`;
- вызывает, и результат тот же: `recheck`.

Потребитель с адресом из конфигурации исполняется с этой конфигурацией. Владелец берётся из
маппинга: одна команда KNOWN, несколько CONFLICT, нет записи UNKNOWN. Ожидаемый исход задают
правила, записанные в `program.json` до прогона: на Jira `abstain`, если текст не определяет
операцию; `no_impact`, если никто не затронут; `partial`, если у затронутого потребителя только
runtime-основание; иначе `answer`. На PR то же без первого правила, плюс `partial` для
неклассифицированного изменения.

Изоляция как в 2Б: эталон читают только `scorer.py` и тесты корпуса. Runner и baseline получают файлы
изменений и стенды; тест запускает runner на копии программы без каталога `oracle`. Эталон проверяется
сам: `oracle.check` пересчитывает его исполнением для всех 80 изменений и сверяет размеры страниц в
фактах с кодом провайдера. Тесты подменяют серьёзность, объявляют приманку затронутой или расходят
факты с кодом, и проверка это ловит.

## Метрики и знаменатели

| Метрика | Знаменатель |
|---|---|
| полезный автономный вывод | изменения: обе стадии верны, публикация цела, без падения |
| исходы answer / partial / abstain / failure | стадии, отдельно по Jira и PR |
| верный путь | ожидаемые пары; операция провайдера, а на PR для кодового потребителя и место вызова |
| FN по серьёзности | пары breaking и пары recheck отдельно; недооценка (breaking назван как recheck) отдельно от пропуска |
| FP | отрицательные пары: приманки, свидетели, потребители неизменной операции |
| уверенный ответ там, где верен отказ | стадии с ожидаемым abstain или no_impact |
| владельцы | названные ожидаемые потребители |
| утечка отозванного | имя отозванного сервиса в результате или в тексте комментария |
| устаревшее как свежее | названные потребители только со stale-основанием |
| потерянная, дублирующая, устаревшая публикация | ресурсы (Jira и PR каждого изменения), из очереди сервиса и счётчиков стенда |
| задержка | секунды от доставки webhook до последней принятой записи комментария на стадии |
| свежесть графа | изменения: после merge и одной сверки версия git-источника провайдера равна head, активные операции равны операциям head |
| стоимость | вызовы модели и токены из `AnalysisResult.costs`; рубли только при известной цене каждого вызова |
| минуты человека | только записанные оператором значения (`scorer --human-minutes`); runner не ждёт человека, `interventions` = 0, активные минуты `NOT_RECORDED` |

Пары одного изменения не независимы, поэтому интервалы по парам оптимистичны; ворота по изменениям
этим не страдают. Изменение, которое упало или не опубликовалось, считается отказом во всех долях, а
не пропуском.

## Baseline: обычный агент с поиском

`baseline.py`, протокол `baseline-search-1`. Те же источники: текст Jira, заголовок PR, изменённые
файлы и diff, те же Git-снимки (все разрешённые репозитории на ветке по умолчанию, провайдер на head
PR на стадии PR), тот же маппинг владельцев и те же окна access-логов. Те же права: отозванный
репозиторий не читается. Графа, extractor и сервиса нет.

Один JSON-ответ модели на шаг (`response_format` json_schema strict, как `actions-v3` в 2Б), результат
действия уходит следующим сообщением. Действия: `list_repositories`, `list_files`, `read_file`,
`search`, `read_ownership`, `read_access_logs`, `finish`. Пределы: 12 шагов, 2 невалидных действия,
120 с. Интерфейс транспорта тот же, что в 2Б (`complete(payload, *, deadline) -> TransportResult`),
поэтому для живого прогона подключается `CloudRuTransport` с той же моделью и той же точкой доступа,
что у сервиса. Живых вызовов в этой пачке нет.

Офлайн есть два транспорта. `ScriptedTransport` из 2Б для тестов. `NaiveSearchTransport` это
фиксированная политика: берёт маршрут из задачи или diff, ищет его строкой и называет каждый другой
репозиторий с совпадением ломающимся потребителем. Это проверка трубопровода и нижняя планка, а не
baseline: модели в нём нет, и для ворот `comparison` он не засчитывается.

## Runner

`runner.py`, конфигурация `service-no-model`: `CoreAnalyzer` с `model=None`, окно runtime 3 суток
(чтобы двухдневное окно было прочитано и показано устаревшим), остальное как в smoke. На каждое
изменение:

1. стенд и чистая установка сервиса, начальная сверка графа, как у установщика;
2. webhook Jira `issue_created`, worker до простоя; та же доставка ещё раз;
3. webhook PR `opened` на head изменения, worker до простоя; та же доставка ещё раз;
4. merge: ветка провайдера по умолчанию переходит на head, одна периодическая сверка графа.

Ledger пишет результаты, тексты комментариев, счётчики стенда, состояния intents и jobs из очереди,
задержку, свежесть графа, стоимость. Эталон runner не читает. Отложенный набор запускается только при
актуальном manifest и только один раз на конфигурацию: существующий ledger не перезаписывается.

### Что это значит

Технически сервис без модели на этих стендах готов: 120 ресурсов без потерь, дублей и устаревших
комментариев, повторные webhook ничего не пишут, отозванный репозиторий не виден ни в одном
комментарии, устаревшие runtime-основания показаны как STALE, граф подхватывает слитое изменение за
одну сверку.

По качеству три настоящих провала, и все три видны в коде:

1. PR не использует runtime-рёбра. Анализ PR (`change_result`) строится только по статическому diff,
   а потребитель, которого видно лишь в access-логах (F05, F07), на PR пропадает: 10 пропущенных

   она про измерение, и правка потребовала бы новой ревизии программы.

3. Из-за п. 1 верный путь на PR 0,895 при пороге 0,90.
