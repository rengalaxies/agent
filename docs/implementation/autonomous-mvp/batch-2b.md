## Программа 2b-r1

`run_id = amvp-2b-20261024-r1`. Каждый случай идёт через `agent_graph.executor.run_investigation`
с actions-v3 и неизменённой конституцией `constitutions/agent-service-v1.yaml` (версия
`agent-service-v1.0:1d33cc53a75f`): 12 шагов, 120 секунд, 24 чтения, 8 предложений, 2 невалидных
действия. Только контроль F09 получает копию конституции, где `max_steps` снижен до 2.
Параметры одинаковы для всех моделей: temperature 0, stream false, `response_format` json_schema
strict, `max_completion_tokens` 4096 (максимум `ModelConfig` ядра), таймаут запроса 60 с, запрос
до 64000 байт, 0 повторов, один запрос за раз на модель, три модели параллельно. Фикстуры читаются
как закреплённые Git-коммиты (`snapshot: git`), а не как рабочее дерево.

Каждый случай идёт с постоянным графом, как в итоговой конфигурации сервиса. Граф строит доверенный
код runner до запроса к модели: `GraphStore.sync_code` по коду фикстур и `sync_ownership` по
ownership-маппингу из конфигурации случая (не из файлов репозитория). Репозитории со `scope:
revoked` попадают в граф через более широкую политику, но в политику модели не входят; снимок
`GraphQuery.for_policy` строит исполнитель по grants политики модели. Конституция разрешает
`graph_find`, `graph_neighbors`, `graph_impact`, `graph_relationship` и `graph_owner` с её
собственными лимитами.

| Фаза | Набор | Повторы | Предел фазы | Нужна перед ней |
| --- | --- | ---: | ---: | --- |
| transport | S01 | 3 | 1800 с | ничего |
| development | 20 случаев | 1 | 7200 с | transport: 2 из 3 полных циклов read -> propose -> finish |
| evaluation-1..3 | 40 случаев | по 1 | 10800 с каждая | development с transport >= 0,80 и валидностью действий >= 0,60 |

Каждая фаза для каждой модели выполняется ровно один раз. Повторный запуск, rerun в Actions,
другой manifest или другой SHA отклоняются ledger. Development можно смотреть и по нему менять
prompt или параметры, но только новой ревизией программы. Evaluation для настройки не используется.

Стоп-правила фазы: первый HTTP 401/403; 5 подряд транспортных отказов; больше 20% отказов после
20 запросов. Случаи F10 (timeout) в счётчики не входят.

Изменения до запуска записаны в `program.json` (`pre_run_changes`): привязка к исполнителю 2А,
лимиты по конституции, таймаут 60 с и 4096 токенов по пределам ядра, удаление метрик impact и
признания неизвестного, добавление точности исхода. Результатов в этот момент не было.

Группа graph-инструментов: F15-F18, 4 случая в development и 12 в evaluation. Эталон для неё:
рёбра проверены исполнением фикстур, как у остальных; статусы владельцев следуют из маппинга
(одна команда KNOWN, несколько CONFLICT, нет записи UNKNOWN), это проверяет `oracle_check.py`;
отозванный репозиторий действительно вызывает orders (его утверждение в `unverifiable_claims`).
Runner наблюдает ответы graph-инструментов, которые увидит модель: считает вхождения имён отозванных
репозиториев, дайджесты выданных ID графа и статусы владельцев. Сами ответы не сохраняются.

Группа сверх готового AST-ребра: F04, F11, F12, 9 случаев в evaluation. Статический extractor
ребра для них не находит (проверено тестом), правильный ответ: подлинный кандидат, не факт.

Откуда эталон. Каждый случай состоит из Git-репозиториев, записанных прямо в JSON. Runner создаёт
из них настоящие коммиты; SHA считается из байтов независимо от Git и сверяется с тем, что выдал
Git. `oracle_check.py` исполняет функции потребителей с записывающими подменами `requests`/`httpx`
и фейковым Orders на 50 заказов при странице 100 и 20. Наблюдаемые вызовы дают истинные
направленные рёбра; собственные тесты фикстур (`tests/test_export.py`) дают impact. Модель и
extractor в эталон не входят. Impact в эталоне сохранён как проверенная истина для пачек 4 и 6,
в 2Б он не оценивается (почему, см. "Решения").

## Как устроены runner, исполнитель и ledger

- `runner.py` для каждого case-run материализует Git-фикстуры и вызывает `protocol.run`.
- `protocol.run` строит `Policy` (закреплённые коммиты, адреса сервисов, конституция, `ModelConfig`
  с `protocol: actions-v3`), готовит контекст ядром и вызывает `run_investigation`. Своего цикла,
  разбора действий и проверки оснований в 2Б нет.
- `AccountedModel.complete_raw` и есть модель для исполнителя. Он отправляет запрос через
  транспорт 2Б, записывает попытку (HTTP, usage, latency, признак позднего ответа) и переводит
  отказ транспорта в коды `GraphError`, которые знает исполнитель. Поздний ответ исполнитель
  отбрасывает сам: он проверяет срок после ответа.
- `case_result` переводит отчёт исполнителя в записи 2Б в словаре agent-graph-output 2.0: `fact`
  или `hypothesis`, `origin`, `provenance` AUTHENTIC/UNVERIFIED/REJECTED, `sufficiency`,
  `UnknownCode`. Утверждение каждого предложения восстанавливается собственным `actions.parse`
  исполнителя; текст ответа не сохраняется. Диагностика отказа берётся из записи исполнителя:
  `layer`, `reason_code`, путь поля, ожидаемый тип.
- Если ядро отказывает в случае (`GraphError`, например `stale_context`), runner записывает
  `CORE_REFUSED` как результат case-run и продолжает фазу. Фазу останавливает только ошибка
  самого runner.
- `transport.py` решает только транспорт: HTTP 200, JSON-тело до 1 МБ и ровно один choice со
  строкой. Без SDK, прокси, редиректов и повторов. Ключ читается из `CLOUDRU_FOUNDATION_API_KEY`
  в момент отправки.
- `ledger.py` хранит JSON на ветке `experiment-state/autonomous-mvp/<run_id>/<модель>`, по файлу на
  фазу, с compare-and-swap на каждой записи. Две записи на case-run укладываются в лимит
  GITHUB_TOKEN. Перед каждой записью проверяется, что значения секретов не попали в состояние.

## Dry-run всей программы

```bash
PYTHONPATH=".;src" .venv/Scripts/python -m tools.autonomous_mvp.dryrun --behaviour follow
```

`ScriptedAgentTransport` стоит на месте `CloudRuTransport`; всё остальное, включая исполнитель
2А, ledger и scorer, тот же код, что в live. Сценарий читает эталон, поэтому dry-run проверяет
трубопровод и scorer, а не качество модели. Поведение `follow` играет атакующие случаи атакующе:
в F06 сначала предлагает поддельные refs, в F07 читает путь вне списка, в F16 цитирует ID графа,
в F17 ищет в графе отозванный сервис; graph-случаи начинает с `graph_find` и `graph_impact`. F09
упирается в лимит шагов, F10 ждёт за пределами срока. `decoy_taker` дополнительно предлагает запрещённые утверждения
как факты и как гипотезы. `broken` отвечает невалидным JSON.

Результат `follow` на всей программе, одна модель, основа `b8ee515` + ветка 3 `f8781ae`
(Windows, 974 с): все пять фаз COMPLETED, 183 case-runs (156 в evaluation), 948 сценарных ответов.

## Живой прогон: точная последовательность

Предусловия:

1. Стек 2А -> 3 -> 2Б слит в `main`. Merge делает владелец.
2. В Settings, Environments создано окружение `autonomous-mvp-live` с required reviewer (владелец)
   и правилом deployment branches "только `main`". Workflow указывает это окружение для jobs с
   секретом. Если окружение не создать, GitHub создаст его при первом запуске без защиты, и прогон
   пойдёт без ручного одобрения.
3. Секрет `CLOUDRU_FOUNDATION_API_KEY` есть в репозитории или в этом окружении. В 22.10 он работал

5. Расход: ожидается около 2,7 тыс. ₽, конечный предел 55,7 тыс. ₽ за всю программу.

### Можно ли без merge в main

Надёжного способа запустить **этот** workflow без merge нет. GitHub запускает `workflow_dispatch`
только для файла, который лежит в default branch; запуск на другой ветке через API возможен лишь
после того, как workflow хотя бы раз отработал из default branch
([документация, проверено 24.10.2026](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)).
Файла `autonomous-mvp-model.yml` на `main` нет.

Технически возможный обход: отдельный workflow с триггером `push` на выделенную ветку
(например `live/autonomous-mvp-2b`) и тем же окружением `autonomous-mvp-live` с обязательным
одобрением и правилом deployment branches на эту ветку. Fork и обычный PR CI секрет не получат:
`pull_request` из fork не видит секретов, а `push` в репозиторий доступен только тем, у кого есть
запись (репозиторий публичный, поэтому окружения с reviewers доступны на любом тарифе). Но у этого
пути три слабых места, поэтому я его не делаю и не рекомендую:

- запускаемый код и сам файл workflow берутся из несмёрженной ветки, то есть код, получающий
  секрет, не прошёл merge-ревью;
- любой с правом записи может создать такую ветку со своим workflow; защиту даёт только правило
  окружения, и оно должно быть настроено до первого push;
- это второй файл workflow с автоматическим триггером, а задание требует ручного запуска.

Если владелец всё же хочет этот путь, ему нужно самому создать окружение с reviewer и правилом
веток, затем дать команду добавить такой workflow. Без этого остаётся merge.

## Решения

- **Граф во всех случаях, не только в F15-F18.** Итоговая конфигурация сервиса включает
  постоянный граф; модель квалифицируется с ним везде, как будет работать. Граф строится из кода
  фикстур тем же extractor, поэтому случаи сверх AST остаются сверх AST: граф их не подсказывает.
- **Ревизия осталась `2b-r1`.** Evaluation-набор не был заморожен: ни одного запроса к модели
  не отправлено, и по правилу программы она меняется только до первого запроса. Добавление
  записано в `pre_run_changes` с датой и причиной.

- **Новая программа, а не продолжение 22.10.** Старый runner жёстко связан со своей серией,
  ledger-веткой и шестью случаями. Новый код его не импортирует.
- **Тонкого адаптера больше нет.** Runner вызывает `run_investigation` 2А и подаёт модель через
  `complete_raw`. Dry-run и live различаются только транспортом.
- **Impact не оценивается в 2Б, новый код в `output_contracts.py` не нужен.** В actions-v3 у модели
  нет действия для вердикта impact: `finish` несёт только `outcome` и `reason`. Impact строит
  доверенное ядро по diff в `results.change_result` (`Finding POSSIBLE_TRUNCATION`,
  `requirement_unknown` по потребителю), а пробелы источников (`commit_unavailable`) ядро выдаёт
  само. Значит, impact и признание неизвестного проверяются на `AnalysisResult` в пачках 4 и 6;
  эталон для них в корпусе уже есть. mvp-2a-core об этом сообщено.
- **Structured output, а не native tool calls.** json_schema strict подтверждён в 22.10 на двух
  моделях; tool calls на этом endpoint никем не проверены. Ответ с `tool_calls` считается
  неудачным обменом.
- **Резерв на случай, а не на запрос.** Запись ledger на каждый запрос дала бы около 20 тыс.
  вызовов GitHub API, больше лимита GITHUB_TOKEN 1000 в час. Плата: при падении процесса внутри
  случая теряются строки попыток этого случая, но деньги остаются зарезервированы по максимуму.
- **Evaluation разбит на три фазы по одному повтору.** Худший случай фазы 40 x 120 с, это
  укладывается в предел job.
- **Эталон по исполнению фикстур.** Так группа сверх AST получает эталон, не зависящий от того
  extractor, чьи пределы она проверяет.
- **Отказ ядра считается результатом случая.** Дефект ядра виден в отчёте как провал конкретного
  семейства, а не прячется за остановкой фазы. Так dry-run и нашёл дефект `pinned_freshness`.

## Ограничения и открытые вопросы

- **Тесты 2Б на Linux ещё не запускались.** `core-tests.yml` их уже подключает (`c850731`), но CI
  на этой ветке не смотрел: без `gh` и токена результат проверок здесь не виден.
- DNS-разрешение в `http.client` не прерывается сроком. Поздний ответ исполнитель всё равно
  отбрасывает, но сам запрос может длиться дольше срока.
- Корпус синтетический. Он квалифицирует цикл модели на контролируемых случаях, а не пользу на
  данных компании (это пачка 6).
