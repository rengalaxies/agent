# Пачки 1-3: результат и маршрут собственного аудита

Дата: 2026-10-15. Все результаты ниже - диагностика на предоставленных синтетических материалах, не пилот и не независимая экспертная валидация. Пачка 4, развертывание, постоянный журнал подтверждений и транзакционная выдача разрешения не входят в изменение.

## Как замечания специалистов повлияли на реализацию

| Замечание | Что изменено | Что остается открытым |
|---|---|---|
| Кто будет заполнять и поддерживать семантику? | SQL и manifest дают наблюдаемые зависимости, хеши и ссылки на исходники. Они не создают подтвержденных требований | Смысл, допустимые изменения и ожидаемые результаты предоставляет владелец. Их стоимость сопровождения не измерена |
| Код - неполная картина; есть JSON и недокументированные потребители | Поддержка имеет явные границы; JSON path, динамический SQL, orphan refs и наблюдаемые потребители без требований становятся gaps | Неизвестного потребителя, которого нет ни в одном входном артефакте, обнаружить нельзя |
| После предупреждения нужно конкретное действие | Локальный разбор diff готовит SQL совместимой версии, контракт и исполняемую fixture-проверку | Нужно проверить пригодность старого поведения и направить потребителей на совместимый endpoint |
| Глобальное согласование тормозит автономные команды | Только advisory-отчет; безопасное изменение не создает нового требования согласовать его | Политика включения gate и SLA согласований требуют пилота |
| Почему не обычные потребительские тесты? | Добавлены сильные тесты с теми же метаданными, SQL и входными данными; сравнение допускает проигрыш V2 | Превосходство продукта не доказано; каталог + тесты могут оказаться достаточным решением |

## Пачка 1. Импорт наблюдаемых зависимостей

`dependency_import.py` компилирует SQL через SQLite authorizer на пустой изолированной схеме. Он фиксирует чтение таблиц и колонок, включая join/filter, CTE, wildcard и count без чтения конкретной колонки. Это не разбор произвольного PostgreSQL и не output-column lineage: поля участвуют в вычислении/условии, но не обязательно прямо появляются в результате.

SQL при импорте не выполняется. При неуспешной компиляции частичный callback prefix отбрасывается: результат не означает нулевые зависимости, а содержит explicit gap. JSON-колонка видна, но вложенные schema/semantics не считаются восстановленными. Не выполняются Jinja, динамический SQL, внешние функции или DDL.

dbt importer читает `depends_on.nodes` ресурсов v12, сохраняет resource IDs, immutable-source reference и хеш исходника. Явный bindings связывает resource ID с логическим продуктом/потребителем; его нельзя надежно угадать по сходству имен. Manifest дает relation-level связи; field-level зависимости из него не выдумываются. Валидируются используемые поля, не вся JSON Schema dbt.

Диагностика `import-catalog.json` содержит 10 авторских случаев: шесть полностью поддержанных, четыре с явно ожидаемыми пробелами. Все 10 дают заявленный результат и статус gap. Отдельная проверка CI запускает настоящий `dbt parse` на приложенном маленьком проекте с DuckDB adapter и проверяет три связи и трехшаговый путь seed -> spending -> aggregate -> retail. Это проверка совместимости с реальным форматом, не production-нагрузки или PostgreSQL runtime.

Primary sources checked 2026-10-15: [dbt manifest](https://docs.getdbt.com/reference/artifacts/manifest-json), [SQLite authorizer](https://www.sqlite.org/c3ref/set_authorizer.html), [Python sqlite3](https://docs.python.org/3/library/sqlite3.html). Адаптер использует документированные dependency поля и callbacks компиляции. Возможности этих механизмов не означают автоматического восстановления бизнес-смысла.

## Пачка 2. Разбор изменения и проверяемый вариант исправления

```sh
PYTHONPATH=src python tools/run_pr_assistant.py --output /tmp/pr-assistant-review
```

Команда загружает development U-01: производитель меняет RUB на kopeck, а исполняемый SQL умножает amount на 100. Из предоставленных запросов и manifest находятся потребитель и промежуточная модель. Владельцы/требования берутся из явных входов, а не из названия таблицы.

Отчет показывает diff, изменения профиля, затронутые требования, владельцев, пути и gaps, результат V2 и отдельно результат выполнения SQL на fixture. SQLite execution read-only, в памяти, с ограничениями размера входов, числа строк и шагов. Пустая input fixture не считается успешным доказательством. Ожидаемые значения предоставлены независимо как вход примера; система не выводит их из нового SQL.

При REJECT готовится кандидат совместимой версии рядом с новой: сохраняется старый SQL и старые смысловые условия с отдельным номером версии контракта. Генерируются `compatibility.sql`, `compatibility-contract.json`, `regression-fixture.json`, `analysis.json` и читаемый `pr-review.md`. На основном примере исходное изменение получает REJECT, кандидат повторно получает ACCEPT на typed требованиях и fixture. Контракт не доказывает соответствие реальному коду автоматически: в примере оба артефакта предоставлены явно и проверены только на заданных данных.

Новая версия продукта и исходный diff не переписываются. Маршрутизация потребителей и выпуск compatibility endpoint автоматически не выполняются. Кандидат может быть бизнес-непригоден, например если старые источники больше недоступны. Он остается предложением для владельца. Старые artifact-файлы не переиспользуются для другого отчета: CLI требует новый output directory при изменившемся report hash.

Записи `requirement_states.status=confirmed` в этом стенде - заявленные входные метаданные. Здесь не проверяется Ed25519 registry из предыдущего PR и не выдается release authorization. Изменение owner/version, отсутствие provenance, неподтвержденная или истекшая запись вызывают review. Фактическая проверка личности и подключение доверенного хранилища потребуются в пачке 4. На отчете нельзя заявлять, что произвольный JSON со словом confirmed получил криптографическое доверие.

## Пачка 3. Сильные альтернативы и стоимость сопровождения

```sh
PYTHONPATH=src:tools python tools/compare_pr_assistant.py --output /tmp/pr-comparison.json
PYTHONPATH=src:tools python tools/check_dependency_import.py --output /tmp/import-results.json
```

Все три режима получают идентичные контракты, требования и их состояния, SQL, fixture, ожидаемые строки, registration boundary и извлеченные связи. Проверки не получают expected decision/rationale из scoring catalog.

| Режим | Что проверяет | Получение контекста |
|---|---|---|
| consumer_tests_scan | Независимые typed проверки, но formula-string predicate заменен исполняемым consumer-output test; общие provenance/coverage проверки | Обычные повторные проходы по тем же связям |
| consumer_tests_catalog | Те же проверки и те же входы | Построенный adjacency index и BFS |
| v2_graph_assistant | Существующий V2 с literal formula predicate, тот же исполняемый тест и общие metadata проверки | Тот же индекс/BFS |

Это не развернутые dbt/Pact тесты: сильная baseline самостоятельно выполняет SQL на SQLite и проверяет требования. Она не доказывает формулу на всех возможных данных. Различие expressive capabilities указано явно: тесты могут пропустить измененную формулу, если fixture не различает поведения; V2 может отклонять эквивалентные строковые записи. Новая диагностика не меняет frozen V2 и не является повторным H1.

Авторский каталог содержит 16 случаев: смена единицы, безопасное изменение, форматирование формулы, отсутствие/истечение/кандидат подтверждения, смена владельца, неподтвержденная граница, недокументированный потребитель, динамический SQL, orphan manifest, JSON, конфликт потребителей, отсутствующее требование, противоречие кода контракту и неподдерживаемый producer SQL.

| Режим | Совпадений с авторской ожидаемой оценкой | Ложных REJECT на ожидаемо безопасных | Выходов NEEDS_REVIEW |
|---|---:|---:|---:|
| consumer_tests_scan | 16/16 | 0 | 11 |
| consumer_tests_catalog | 16/16 | 0 | 11 |
| v2_graph_assistant | 15/16 | 1 | 11 |

Контрпример - только пробелы в символической формуле при неизменном исполняемом SQL. По определению этой диагностики это безопасно; V2 следует своему правилу literal equality и отвергает. Это ограничение смысловой адекватности предиката, не падение кода V2. Не следует обобщать 16/16 baseline на реальный мир: случаи и ожидания составлены тем же автором, выбраны для проверки механизмов и не являются независимыми наблюдениями или оценкой статистической мощности.

Во всех 16 случаях graph и flat retrieval возвращают одинаковые пути. Считаются edge inspections и отдельно index-build edges; это структурные счетчики, не latency, память, токены или стоимость СУБД. На маленьком наборе необходимости graph DB не установлено. Нет утверждения, что обычные joins хуже или что граф дает дополнительную информацию.

Число введенных требований, ожидаемых строк и явных boundaries сохраняется как инвентаризация ручных входов. Для отсутствующего подтверждения, истекшего требования, смены владельца и нового потребителя перечислены действия сопровождения. Выход NEEDS_REVIEW не равен измеренным человеко-минутам. Истинные затраты на сбор исходной семантики, ожидание владельца и сопровождение остаются неизвестны. В частности, 11 review из 16 специально проблемных случаев не означают 69% review в production.

LLM single-agent/multi-agent comparison остается NOT_RUN: воспроизводимый endpoint не настроен. Никаких преимуществ агентов, сокращения времени команд, спроса или финансового эффекта не заявляем.

## Маршрут аудита

1. Прочитать `examples/pr-assistant/input.json`: какие сведения пришлось предоставить человеку и какие из них могут отсутствовать в организации.
2. Прочитать `pr-assistant-demo/pr-review.md`, затем исполнить его regression fixture из `analysis.json`. Проверить, что исходный kopeck контракт не был заменен compatibility кандидатом.
3. Проверить `catalog.json` и rationale до просмотра результатов: согласны ли вы с авторскими expected decisions. Особое внимание formula-formatting и происхождению fixture expected outputs.
4. Проверить capability matrix выше. Не сравниваются слабые schema-only tests с V2, имеющим дополнительные требования.
5. Проверить `pr-assistant-comparison.json`: исходные input hashes, решения всех режимов, gaps, равенство retrieval и счетчики ручных входов.
6. Проверить unsupported и unregistered случаи: ни один пустой результат импорта не должен интерпретироваться как доказательство безопасности.
7. Проверить CI: 16 новых тестов + 58 предыдущих, точное воспроизведение трех новых artifact bundles и прежних diagnostics, реальный dbt parse. В artifacts сохраняются actual manifest, import report и версии зависимостей.
8. После аудита отдельно решить, оправданы ли развитие помощника поверх существующих тестов/каталога и переход к пачке 4. До этого release authorization, миграция хранилища, deploy и изменения основного H1 не выполняются.

Технические тесты не заменяют это ревью и не подтверждают бизнес-полезность. Для следующего исследовательского вывода нужен реальный diff с независимо установленными последствиями и измерением работы владельцев.
