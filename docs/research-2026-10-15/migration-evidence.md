# Исполняемая проверка миграции: opt-in прототип

Продолжение исследования PR #17. Существующий V2 принимает metadata миграции с положительным `validated_examples`, не исполняя `expression`. Новый модуль `migration_evidence.py` проверяет конкретные примеры и выдает отдельный advisory-результат. Версия V2 и основной эксперимент не изменены. Развернутый сайт этим PR не обновляется.

## Что теперь можно проверить

Поддержаны `unit_scale` и ограниченное арифметическое выражение над `value`: числовые константы, скобки, сложение, вычитание, умножение, деление и унарный знак. Выражение разбирается AST, без `eval`, вызовов функций, доступа к файлам и атрибутам. Числа задаются decimal-строками; вычисления используют Decimal с точностью 50 цифр. Проверка точного равенства относится к этой вычислительной модели, не к произвольной математической эквивалентности или особенностям production SQL.

| Случай из development U-02 | Legacy V2 | Новый advisory gate |
|---|---|---|
| `value / 100`, 123 -> 1.23, -50 -> -0.5 | ACCEPT | ACCEPT |
| `value * 100`, заявленный пример 123 -> 1.23 | ACCEPT | REJECT |
| `WRONG` с положительным `validated_examples` | ACCEPT | NEEDS_REVIEW |
| Нет исполняемых примеров | ACCEPT | NEEDS_REVIEW |
| Неверное `value * 100`, единственный пример 0 -> 0 | ACCEPT | ACCEPT, только для этого примера |

Последняя строка принципиальна: слабый набор примеров может пропустить неверное преобразование. Корректность ожидаемых ответов, их независимость и репрезентативность пока подтверждает владелец. Прототип не доказывает истинность единиц или всей семантики. Не реализованы выполнение произвольного SQL, identity mappings, округление по правилам конкретной БД, доказательство биективности и автоматический подбор достаточного набора тестов.

Receipt содержит полное объявление миграции, примеры, фактические результаты, решение, версию и SHA-256 исходного файла verifier, хеш входного пакета и хеш результата. Изменение выражения, примеров или реализации меняет привязку. Хеш не является подписью доверенного владельца: для production понадобится подтверждение происхождения fixture и связь с результатом CI конкретного commit.

`run_with_migration_evidence` повторно вычисляет receipts, а не принимает чужой флаг `passed`. Он связывает их с `scenario_snapshot_id`, сохраняет исходное решение V2 и явно возвращает `release_authorization=False`. Проверяются все перечисленные миграции, включая неиспользованные; порядок fixture sets соответствует порядку миграций. Несовпадение количества считается ошибкой вызова. При любом REJECT итог REJECT; иначе неизвестность дает NEEDS_REVIEW. Существующий отказ V2 не отменяется успешными fixture.

## Воспроизведение

```sh
PYTHONPATH=src:tests python -m unittest discover -s tests -p 'test_migration_evidence.py' -v
PYTHONPATH=src python tools/run_migration_evidence_demo.py
```

Локально пройдены 15 новых тестов. Они покрывают неверное преобразование при положительном legacy-счетчике, отсутствие примеров, десятичную арифметику, отрицательные и нулевые значения, unsupported syntax, деление на ноль, пределы входов, привязку хешей и сохранение старого отказа. Полный воспроизводимый результат - `migration-evidence-results.json`; отдельный GitHub workflow повторяет тесты и сравнивает результат побайтно.

## Связь с графом и продуктом

Следующее ребро карты - Migration -> VerificationReceipt -> FixtureEvidence. В интерфейсе PR это позволит перейти от предложения миграции к выполненным примерам и их владельцу. До появления доверенного источника fixture статус такого ребра должен быть "результат вычислен, ожидания предоставлены автором", а не "миграция доказана". В текущую release-карту receipt автоматически не добавлен: ее schema knowledge-1 не содержит такой сущности, и неявное расширение нарушило бы границы версий.

Следующий необходимый шаг для production-интеграции - договориться о версии модели evidence и включении ее хешей в авторизуемый снимок с проверкой актуальности. До этого прототип пригоден для диагностики и CI-комментария, но не заменяет KnowledgeReleaseEngine и его commit fence.
