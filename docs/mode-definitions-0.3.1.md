# Рабочие определения режимов для протокола 0.3.1

## Статус

Документ фиксирует каноническую модель режимов после внутреннего аудита 0.3.0. Это рабочая версия до завершения контура E3, метрик и повторной заморозки. Основной evaluation-запуск не выполнялся.

## Общая основа

Все режимы получают один и тот же входной сценарий и выполняют одинаковую структурную проверку схемы. Ни один режим не получает `ScenarioOracle`, ожидаемый класс или ожидаемое решение. Для всех режимов действует единая финализация `REJECT > NEEDS_REVIEW > ACCEPT`.

## Режимы

### V0

Нижний структурный ориентир. Проверяет удаление полей и несовместимость типов. Семантический профиль и обязательства потребителей не интерпретирует.

### V1-ind

Воспроизводимый промышленно мотивированный comparator. После структурной проверки применяет одну заранее зафиксированную матрицу общих правил по семействам изменений: обязательность миграции единиц и области идентичности, allowlist происхождения и обязательный purpose.

V1-ind не получает `ConsumerObligation` как источник правил и не является эмуляцией конкретного коммерческого продукта. В прототипе не запускаются Pact Broker или Confluent Schema Registry; воспроизводятся выбранные классы их механизмов в детерминированной модели.

### V1-oracle

Положительный контроль чувствительности. После структурной проверки применяет полный набор явно запрограммированных предикатов ко всем полям предоставленного `ConsumerObligation`. Реализация использует отдельный кодовый путь `_oracle_predicate_checks` и reason codes с префиксом `ORACLE_`.

V1-oracle показывает, достижим ли результат посредством полного ручного кодирования известных обязательств. Он не является промышленным baseline, не использует `ScenarioOracle` и не входит в primary contrast.

### V2

Consumer-aware стратегия. После структурной проверки передаёт типизированный `ConsumerObligation` единому повторно используемому `TypedObligationInterpreter`. Интерпретатор имеет фиксированный для версии протокола реестр обработчиков и reason codes с префиксом `V2_`. Сценарные предикаты в V2 не добавляются.

V2 и V1-ind являются параллельными стратегиями контроля поверх общей структурной основы. V2 не определяется как механическое объединение всех запретов V1-ind с обязательствами потребителя: общая политика baseline может блокировать изменение, которое явно разрешено действующей версией конкретного обязательства.

## Сравнения

- primary contrast: V2 против V1-ind;
- нижний ориентир: V0;
- анализ чувствительности: V2 против V1-oracle;
- равенство итоговых решений V1-oracle и V2 допустимо, но их audit traces и реализация должны оставаться независимыми.

## Защитные инварианты

- V1-oracle и V2 не используют общую функцию семантической проверки;
- reason codes V1-oracle и V2 не пересекаются;
- изменение реестра обработчиков V2 требует новой версии протокола;
- добавление правила V1-ind под отдельный evaluation-сценарий запрещено;
- совпадение решений с oracle проверяется только оценочным контуром после validator runs.
