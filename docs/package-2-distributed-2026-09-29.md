# Пакет 2: распределённый стенд и локальные проверки E4

Пакет 2 реализован и проверен локально. Три отдельных Python-процесса sales, risk и analytics работают с собственными SQLite-хранилищами и подписанными HTTP-событиями. Облачного запуска пока нет. Основной E3, экспертная разметка и подтверждение H1 не выполнялись; p <= 0,05 и evaluation-каталог не менялись.

## Что устроено в стенде

| Элемент | Реализация | Ответственность |
| --- | --- | --- |
| Доменный узел | `stand/node.py`, отдельный PID и SQLite WAL / synchronous FULL | Хранит собственные записи, вычисляет локальный вердикт, сохраняет ответ до отправки |
| Карта | Типизированный knowledge-1 и неизменяемый снимок | Явно задаёт зарегистрированных потребителей, границу полноты, эпоху и версии |
| Событие | WorkItem и Ed25519 SignedMessage | Привязывает ответ к run, proposal, snapshot, версиям контрактов, эпохе и ревизии домена |
| Доставка | HTTP на 127.0.0.1, bearer-токен, ограничение размера и времени запроса | Передаёт событие; повтор обрабатывается через устойчивый inbox узла |
| Финализация | Одинаковая чистая функция в каждом процессе; `REJECT > NEEDS_REVIEW > ACCEPT` | Проверяет подписи, состав участников, конфликты, полноту и revision fence |
| Координатор | Монотонный TTL, замороженный набор ответов, knowledge-ledger-2 | Сохраняет терминальный результат и единственное разрешение; повтор run возвращает результат без новых ответов |
| Два адаптера | YAML-реестр и JSON-события propose/confirm/revoke | Восстанавливают одинаковые типизированные записи и канонические снимки |
| Запуск | LocalStand, `stand/demo.py`, Makefile, lock-файл зависимостей | Поднимает процессы, сохраняет их идентичности, поддерживает повторный запуск |

Coverage и Constitution в синтетической конфигурации принадлежат федеративной роли, обслуживаемой процессом sales. Это явное отображение ролей на процессы, а не передача владения потребительскими обязательствами производителю. Доменный вычислитель использует свои записи для проверки актуальности и собственные обязательства для решения; общая схема и подтверждённый снимок поступают в запросе. Центральная копия карты остаётся у координатора для сборки и проверки снимка. Поэтому результат относится к распределённому вычислению решений с локальным владением, а не к полностью распределённой базе знаний или консенсусу.

## Проверки и наблюдения

Ускоренный профиль: TTL = 0,15 s, по 30 seed для большинства классов. Номинальный профиль: TTL = 10 s, по одному seed и все шесть перестановок. Для E4-01/02/03/05/10 использованы ACCEPT, REJECT и NEEDS_REVIEW. Seed определяет порядок и число повторов; криптографические ключи и времена генерируются заново. Воспроизводится логический результат, а не побайтовая трасса нового запуска.

| Класс | Проверяемое воздействие | Ускоренный / номинальный | Наблюдение |
| --- | --- | ---: | --- |
| E4-01 | Полная доставка | 90 / 3 | Ожидаемые три решения |
| E4-02 | От 1 до 5 повторов ответа | 90 / 3 | Итог не меняется; inbox сохраняет ответ |
| E4-03 | Все 6 порядков трёх ответов | 18 / 18 | Решение не зависит от порядка |
| E4-04 | Нет обязательного analytics | 30 / 1 | Нет COMMITTED; завершение после TTL |
| E4-05 | Задержка доставки ответа | 90 / 3 | Совпадение решений; максимум 0,628 s в номинальном профиле |
| E4-06 | Ответ после терминального решения | 30 / 1 | Ответ отмечается LATE_IGNORED, итог не открывается заново |
| E4-07 | Неверные run / snapshot / версия | 30 / 1 | Ответ не закрывает обязанность участника; нет ACCEPT |
| E4-08 | Отзыв Coverage / Constitution / Product перед commit | 30 / 1 | ABORTED |
| E4-09 | Два противоречивых подписанных ответа домена | 30 / 1 | Конфликт; нет COMMITTED |
| E4-10 | Финализация одинаковой трассы каждым узлом | 90 / 3 | Совпадают решение, причины и доказательства |
| E4-11 | Реально остановлен analytics | 30 / 1 | Зависимый продукт эскалируется; независимый получает COMMITTED |
| E4-12 | YAML и доменные события | 30 / 1 | Равны снимки и проекции решений для всех трёх исходов |
| Всего | 12 классов | 588 / 37 | Все испытания прошли |

Номинальные испытания с недостающими ответами завершились за 10,006-10,008 s, в пределах TTL + 1 s. Доступные сценарии завершились быстрее 8 s. Это измерения текущего локального окружения, а не промышленный SLA. Ускоренный профиль проверяет покрытия и инварианты, не заменяет номинальные измерения. Номинальный профиль не является 30-seed облачным экспериментом.

Дополнительно: 111 unittest-тестов пройдены; семь проверок восстановления прошли, включая перезапуск домена, конфликт event_id, восстановление подписанного журнала координатора, подмену журнала, сохранение обновлённых метаданных, abort при смене локальной ревизии и сохранение идентичностей после общего перезапуска. Два запуска переносимого demo дали одинаковое содержимое полного JSON-результата. Архивная проверка заново проверила подписи и финализацию 594 трасс; 31 группа E4-12 проверяет адаптеры и не содержит отдельной трассы решения в архиве.

E4-07 и E4-09 используют явно подписанную инъекцию ошибочного отправителя в тестовом драйвере. Штатный узел не имеет endpoint для произвольного подписания. E4-04 моделирует потерю доставки, а E4-11 действительно завершает процесс. Задержки задаются драйвером перед доставкой уже вычисленного ответа; не измерялись отдельные сетевые каналы между ВМ.

## Как повторить

Из корня репозитория, Python 3.12 и Linux:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r stand/requirements.lock
pip install --no-deps -e .
make test
make e4-fast
make e4-standard
make e4-recovery
python stand/archive_results.py
PYTHONPATH=src python stand/verify_archive.py
PYTHONPATH=src python stand/demo.py --state .runtime/demo --run-id demo-1 --outcome ACCEPT
```

Тот же demo с тем же state/run-id возвращает прежний результат. Каталог `.runtime` содержит приватные ключи и токены, имеет локальную область использования и не публикуется. Узлы слушают только loopback. Для отдельного узла доступен `python -m datamesh_release_protocol.stand.node --config /path/domain.json`; конфигурация принадлежит развёртыванию, не пользовательскому запросу.

Полные журналы сохранены без потерь в `results/e4-local-fast.json.gz.b64` и `results/e4-local-standard.json.gz.b64`; `verify_archive.py` проверяет SHA-256, распаковывает JSON, проверяет подписи и воспроизводит проекции. Сводка и хеши: `results/e4-local-manifest.json`. Частные ключи в результаты не включены. Наличие публичных ключей в архиве обеспечивает воспроизведение этой тестовой трассы; доверие в рабочем развёртывании задаётся отдельно конфигурацией владельца, а не самим журналом.

## Что переносится на Cloud.ru и что остаётся пакету 3

Готовы исходники, Linux-команды запуска, зафиксированные версии Python-зависимостей, сохраняемое состояние, synthetic-каталог, два профиля и Dockerfile. Нативный запуск проверен; Dockerfile подготовлен, но образ не собирался: Docker в окружении отсутствует. Python base image не зафиксирован digest, зависимости не зафиксированы wheel-хешами; окончательная фиксация образа входит в облачный пакет.

| Пакет 3 | Что потребуется | Проверяемый результат |
| --- | --- | --- |
| ВМ и диски | Доступ к проекту Cloud.ru, согласованный бюджет и регион | Работающий стенд на реальных ресурсах |
| Изоляция доменов | Приватная сеть, адреса узлов, сервисные идентичности | Отдельные процессы/контейнеры, затем при необходимости разные ВМ |
| Защита канала | TLS или защищённая приватная сеть, управление секретами | Токены и ключи не передаются через публичный HTTP |
| Доставка | Очередь/повтор отправки, наблюдаемость и сохранение событий | Проверка сбоев сети и перезапуска посредника |
| Данные и разрешение | Снимки, резервирование, восстановление и проверка тома | Повтор E4 и durability на выбранном облачном диске |
| Прогон | Полный номинальный профиль с фиксированным числом повторов | Отдельный manifest с платформой, образами и измерениями |

Revision fence обнаруживает изменение, видимое при запросе fence, и координатор повторно проверяет свою карту перед commit. Он не удерживает распределённую транзакционную блокировку: изменение домена после fence возможно. Поэтому COMMITTED обозначает устойчивое разрешение по наблюдённому контексту, а физический адаптер обязан заново проверять актуальность непосредственно перед применением. Атомарное изменение трёх платформ, Byzantine fault tolerance, failover единственного журнала разрешений и масштабирование здесь не доказаны. При падении координатора до сохранения решения запрос можно повторить с прежним event_id и получить ответы из inbox; восстановление истёкшего монотонного таймера незавершённого запуска не реализовано.

Эксперты не блокируют пакет 3. До основного E3 нужны экспертный пилот, независимая разметка, методологическое согласование H1 и freeze.
