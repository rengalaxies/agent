# Решение по стеку

Вопрос: подходит ли Python как язык реализации продукта для небольшой команды
и закрытого корпоративного контура. Язык анализируемых репозиториев это
отдельная ось: сейчас поддержан только Python-клиент `requests` и FastAPI или
OpenAPI на стороне поставщика.

## Где сейчас уходит время

По [MEASUREMENTS.md](MEASUREMENTS.md), без модели:

1. Запуск процесса CLI: 0,46 с на вызов при 1,6 мс полезной работы `evidence`.
   Worker демо запускает процесс на каждую цитату.
2. Повторные полные обходы корпуса: `prepare_context` обходит его дважды,
   последующий `dependencies` ещё раз, `analyze_change` трижды.
3. Сериализация контекста с полным текстом корпуса и чтение его целиком ради
   одной цитаты.
4. Извлечение: 2,1 с на 1000 файлов, 18,4 с на 9000, больше всех остальных
   фаз в одном процессе. Профиль (`bench/profile_extract.py`): `ast.parse`,
   написанный на C, занимает 4% времени извлечения. Остальное это обход дерева
   на Python, повторённый на каждом файле 5-6 раз (`bindings` вызывается дважды,
   отдельные `ast.walk` для родителей, вызовов и каждой функции), и
   сопоставление каждого вызова со всеми операциями сервиса с построением
   регулярного выражения на каждую пару (`match_url`, 24%). Другой язык ускорил
   бы эту часть, но тот же выигрыш на порядок дешевле получить одним обходом на
   файл и индексом операций по `(service, method)`, а при инкрементальном
   извлечении (ADR-005) она вообще выполняется только для изменённых файлов.
5. Ожидание модели: 4,9-7,2 с на запрос, 26-37 с на случай. На порядки
   дороже всего остального, но в демо выключено.

Пункты 1-3 устраняются изменением архитектуры на том же Python
(ADR-002, ADR-005). Прототип инкрементального извлечения на неизменённом
Python-коде ядра даёт 0,14 с на обновление после правки одного файла из 1000.

## Сравнение языков для этого продукта

| Критерий | Python (сейчас) | Go | Rust |
|---|---|---|---|
| Разбор анализируемого Python | `ast` стандартной библиотеки, точная грамматика версии интерпретатора | Нет стандартного парсера Python; tree-sitter через cgo или свой | tree-sitter или `ruff_python_parser` (не стабильный API) |
| Скорость разработки команды | Код уже написан, 1200 строк ядра, команда пишет на Python | Переписывание ядра и тестов | Переписывание и более медленная итерация |
| Время запуска | 50 мс голый интерпретатор, 175 мс с pydantic, 340 мс импорт ядра | Единицы мс | Единицы мс |
| Память | 37 МБ на малом корпусе; рост определяется копиями корпуса в JSON, не языком | Меньше при той же архитектуре (оценка, не измерялось) | Меньше при той же архитектуре (оценка, не измерялось) |
| Упаковка в закрытый контур | Интерпретатор + колёса с хешами; уже работает (#38) | Один статический бинарник | Один статический бинарник |
| Обновления зависимостей | pydantic-core бинарный, колёса под платформу; lock с хешами | `go.sum`, вендоринг | `Cargo.lock`, вендоринг |
| Библиотеки вокруг | FastAPI, pydantic, SDK моделей, MCP SDK, py-tree-sitter | net/http, MCP SDK есть | меньше готового для веба и LLM |
| Привязка к версии анализируемого языка | Да: 3.12 не разбирает синтаксис 3.14 | Нет, но и точной грамматики нет | Нет, но и точной грамматики нет |

Вывод: Python оправдан. Его реальные издержки в этом продукте это время
запуска процесса и привязка грамматики к версии интерпретатора. Первая
снимается отказом от процесса на вызов, вторая обновлением интерпретатора в
образе.

## Четыре варианта

| Вариант | Выигрыш | Цена перехода | Новый эксплуатационный риск | Когда оправдан |
|---|---|---|---|---|
| A. Сохранить архитектуру и Python | Нет затрат | 0 | Остаются: job демо превышает 180 с уже на корпусе в 20 файлов; запрос стоит O(корпус); правка любого файла делает STALE всё; новый репозиторий скрывает решения людей | Только как замороженный показ на синтетическом сценарии |
| **B. Упростить границы и убрать измеренные узкие места (рекомендуется)** | Job демо без процессов на цитату; обновление после правки пропорционально изменению (0,14 с против 2,36 с на 1000 файлах); рост хранилища в 26 раз меньше; решения людей переживают расширение и чужие правки | 5 шагов, каждый 1-2 недели одного разработчика ([README.md](README.md)) | Миграция схемы SQLite, которой сейчас нет; кеш, который может разойтись с полным пересчётом (лечится проверкой совпадения в тестах) | Сейчас |
| C. Выделить компонент на другом стеке | Быстрее разбор на очень больших корпусах; разбор других языков | Второй язык сборки, FFI или протокол, отдельные колёса под платформы | Сборка в закрытом контуре, расхождение семантики с `ast` | Когда после B полный пересчёт на корпусе команды превышает бюджет, либо выбран второй анализируемый язык и `py-tree-sitter` не справляется |
| D. Существенно изменить архитектуру или стек: графовая БД, брокер, сервисы, либо переход на чужую платформу (Sourcegraph, Backstage + oasdiff) | Готовая кодовая навигация и каталог сервисов у больших организаций | Месяцы; эксплуатация нескольких сервисов в закрытом контуре | Самая высокая: новые компоненты без измеренной потребности | Когда подключено больше 50 репозиториев или нескольких команд, либо когда проверка v4 §7 покажет, что агент с поиском даёт тот же результат, и продукт сводится к интеграции чужих инструментов |

Прототип альтернативы C не делался: вариант B снимает узкое место, которое C
мог бы ускорить, и неопределённости, которую разрешил бы прототип C, нет.
Прототип делался для B, потому что именно там был вопрос "хватит ли Python
без смены архитектуры хранения".

## Решение

[ADR-001](adr/ADR-001-keep-python.md): Python остаётся. Вариант B. Условие
пересмотра записано в ADR-001.
