# ADR-008. Серверный журнал с причинами и длительностями

Статус: предложено аудитом 22.10.2026.

## Контекст

В пути графа нет ни одного вызова `logging`. Ядро отдаёт только стабильный
код ошибки, `GraphCLI` отправляет stderr ядра в `DEVNULL`, worker превращает
неожиданное исключение в `worker_failed`, падение потока worker записывается
строкой в список без traceback, access log uvicorn выключен. Принцип "не
возвращать наружу текст ошибки и входные данные" верен, но он применён и к
серверу: оператор не узнает причину сбоя без воспроизведения.

Метрик тоже нет. `metrics.prepare_seconds` пишется в контекст и нигде не читается.
Поэтому замеры этого аудита пришлось снимать обёртками вокруг функций.

## Решение

1. Стандартный `logging` в JSON-строках в stdout процесса, без новых
   зависимостей. Поля: job, операция, код результата, длительность фаз
   (обход, извлечение, запись, проверка цитат), число файлов, байт, цитат.
2. Traceback пишется в журнал на уровне ERROR. В ответ API и CLI уходит прежний
   стабильный код.
3. Текст исходников, цитаты, policy и секреты в журнал не пишутся. Это
   проверяется тестом, который подаёт файл с маркером и ищет маркер в журнале.
4. Отдельной системы метрик не вводить, пока нет потребителя. Длительности
   из журнала достаточно для сравнения до и после каждого шага перехода.

## Последствия

- Журнал собирает journald или docker logs, как уже сделано на ВМ.
- Шаги целевой архитектуры получают измеримый критерий без отдельной
  инфраструктуры.

## Как проверить

Искусственный сбой worker (например, повреждённый JSON контекста) оставляет
в журнале traceback и job id, а API возвращает прежний код.
