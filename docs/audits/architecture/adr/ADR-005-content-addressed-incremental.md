# ADR-005. Хранение по содержимому, инкрементальное извлечение, свежесть по цитатам

Статус: предложено аудитом 22.10.2026. Прототип: `bench/proto_incremental.py`.

## Контекст

- Каждый `prepare_context` дважды обходит и хеширует весь корпус, а
  `dependencies`, `propose` и каждый шаг модели обходят его ещё раз ради
  `freshness`. На 9000 файлах это десятки секунд на запрос
  ([MEASUREMENTS.md](../MEASUREMENTS.md)).
- Контекст хранит полный текст корпуса и весь граф с цитатами. На 1000 файлах
  это 5,4 МБ на контекст, и каждый анализ добавляет новый. Удаления нет.
- Свежесть считается по basis всего корпуса: правка одного байта в любом файле
  делает STALE все контексты и все исправления людей.

## Решение

1. Хранить исходники как blob-ы по хешу содержимого (при ADR-004 это blob Git).
2. Кешировать результат извлечения по файлу: поставщики по
   `(sha файла, PROFILE)`, потребители по `(sha файла, PROFILE, digest набора
   операций)`. Сборка графа соединяет готовые части.
3. Контекст хранит манифест: список `(путь, sha)` и ссылки на части. Цитата
   хранит `(sha, строки)`; текст цитаты материализуется при чтении.
4. Свежесть вывода определяется хешами файлов, на которые он ссылается:
   зависимость STALE, если изменился файл вызова или объявления операции.
   Отрицательные выводы ("потребителей нет") по-прежнему зависят от состава
   всего корпуса, как требует v4 §6.
5. Хранилище остаётся SQLite. Графовая БД не нужна: запросы это выборка по
   операции и по файлу, объём измеряется мегабайтами.

## Что показал прототип

На синтетическом корпусе из 1000 файлов и трёх правках одного файла:

| Показатель | Сейчас | Прототип |
|---|---|---|
| Обновление после правки одного файла | 2,30-2,38 с | 0,14-0,15 с |
| Совпадение графа с полным `extract()` | | побайтно, 4 из 4 |
| Прирост хранилища на контекст | 5,4 МБ | 0,21 МБ |
| Прирост, если вынести только тексты файлов в blob-ы | | 4,2 МБ |

Последняя строка важна: экономия даёт не дедупликация исходников, а хранение
результата по файлам. Основной объём контекста это граф с цитатами.

## Альтернативы

- Только stat-кеш (mtime, size) без изменения хранения. Ускоряет обход, но
  хранилище растёт так же. Подходит как первый шаг до ADR-004.
- Фоновая перепроверка по расписанию. Скрывает задержку, но не убирает
  стоимость и добавляет процесс; нужна, только если появится уведомление об
  устаревании без запроса пользователя.

## Последствия

- Стоимость обновления становится пропорциональной изменению, а не корпусу.
- Нужна миграция схемы SQLite с версией схемы; сейчас версий нет.
- Исправления людей перестают устаревать от несвязанных правок (вместе с ADR-006).

## Как проверить

Медиана обновления после правки одного файла и прирост хранилища на контекст
на корпусе команды. Цели: не больше 2 с и не больше 1 МБ на 10 000 файлов.
