# ADR-001. Python остаётся языком реализации, отдельный компонент на другом стеке не выделяем

Статус: предложено аудитом 22.10.2026, ждёт решения владельца.

## Контекст

Ядро это 1200 строк Python плюс 580 строк модельного цикла, одна внешняя
зависимость (pydantic). Замеры ([MEASUREMENTS.md](../MEASUREMENTS.md)) показали:

- полезная работа одного вызова `evidence` занимает около 1,6 мс, а процесс CLI
  целиком 0,46 с: 99% времени уходит на запуск интерпретатора и импорт;
- извлечение (`ast.parse` и обход) стоит единицы миллисекунд на файл; основное
  время запроса уходит на повторные полные обходы корпуса (три на
  `prepare_context` с последующим `dependencies`) и копирование корпуса в JSON;
- инкрементальное извлечение на том же Python-коде после правки одного файла
  занимает 0,14 с против 2,36 с полного прохода на 1000 файлах при побайтно
  одинаковом результате.

Узкие места архитектурные. Язык не входит в первую десятку причин задержки.

## Решение

Продукт остаётся на Python 3.12+. Парсер Python-исходников остаётся `ast`
стандартной библиотеки. Отдельный сервис или бинарник на Go/Rust не выделяется.

## Рассмотренные альтернативы

| Вариант | Выигрыш | Цена перехода | Новый риск | Когда оправдан |
|---|---|---|---|---|
| Переписать ядро на Go или Rust | Один статический бинарник, быстрее обход AST, нет интерпретатора в поставке | Новый парсер Python (tree-sitter или самописный), перенос закрытой грамматики и всех регрессий; 2-3 месяца для небольшой команды | Расхождение семантики с `ast`, потеря точной грамматики Python, второй стек в команде | Если после ADR-002 и ADR-005 полный обход корпуса остаётся частой операцией на 50k+ файлов и не укладывается в бюджет |
| Выделить extractor на Rust через tree-sitter | Быстрый разбор многих языков | Привязка к Python через FFI или отдельный процесс, вторая сборка, отдельные wheels под платформы | Сборка под закрытый контур, ещё один протокол | Когда анализируемых языков станет больше одного и Python-обвязка tree-sitter окажется узким местом |
| `py-tree-sitter` внутри Python-процесса | Разбор TypeScript, Java, Go без смены языка продукта | Колёса с грамматиками в wheelhouse | Грамматики tree-sitter отстают от языков, нет семантики импортов | Когда выбран второй анализируемый язык; это расширение профиля, не смена стека |

## Последствия

- Язык анализируемых репозиториев не определяет язык продукта. Для Python
  точнее всего `ast` той же версии интерпретатора. Отсюда ограничение: ядро на
  3.12 даёт `python_parse_error` на синтаксисе 3.14 (`except A, B:`, t-строки).
  Интерпретатор продукта нужно держать не старше самой новой версии Python в
  анализируемых репозиториях. Это проверяемое требование к поставке.
- Поставка в закрытый контур остаётся колёсами с хешами и образом с
  закреплённым digest; эта схема уже работает (отчёт #38).
- Переписывание откладывается до измеренной потребности, условие указано в таблице.

## Как узнаем, что решение неверно

Пересмотреть, если после шагов 1-3 целевой архитектуры
([README.md](../README.md)) медиана обновления после правки одного файла на
корпусе команды превышает 2 с или пиковая память процесса превышает 1 ГБ.
