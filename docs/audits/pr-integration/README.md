## Техническое заключение

Принятой основой продукта можно считать:

- статическое ядро `src/agent_graph` в профиле `http-requests-3`: закрытая AST-грамматика
  для `requests` и FastAPI/OpenAPI, версия исходников через basis, свежесть,
  `analyze_change` для изменения default `page_size` и удаления операции;
- очередь, revision CAS, отмену и восстановление демо: эта часть выдержала
  проверку гонок и сбоев лучше остального;
- разделение proposed и running версии и привязку receipt к ревизии и manifest.

Ограничения, которые обязан учитывать следующий исполнитель:

- "Нет findings" не означает "нет риска". Грамматика узкая, новые потребители
  не считаются изменением (L5), покрытие всегда PARTIAL из-за FastAPI-декораторов
  (L1), так что сигнал несут только конкретные коды в gaps.
- Сила свидетельств в порядке убывания: receipt операторского runner (реальный
  запуск, но наблюдение оператора) > статическое ребро ядра (условный прогноз) >
  принятый модельный кандидат (повторяет статическое ребро, ничего не добавляет) >
  EXTERNAL_REPORTED. Ни одно из них не является допуском к выпуску. Новый текст в
  UI и отчётах должен сохранять это различие: F2, F3, F7 показывают, как легко оно
  стирается одной подписью.
- Модельный цикл в текущем протоколе не расширяет граф. Работа над моделью имеет
  смысл, только если sufficiency научится принимать связи, которых нет в
  статическом выводе, с отдельным статусом.
- Любое изменение семантики extractor требует нового `PROFILE` и
  перезакрепления демо (`core.lock.json`, `CORE_SHA`, оба workflow, delivery).
  Merge PR с ядром должен быть merge commit: CI и delivery ссылаются на SHA ядра.
- Ветку `codex/cloudru-graph-model-cycle` (#31) не удалять: на `5b5b955`
  ссылается `tests/graph/fixtures/pr31/provenance.json`.
- Локальная разработка возможна только на Linux.
