# Формальная внутренняя ревизия 20 development-сценариев

## Результат

Все 20 сценариев прошли структурную и логическую самопроверку. Каталог сбалансирован: 10 опасных и 10 допустимых изменений, в каждом из шести семейств присутствуют оба класса. Ревизия не заменяет независимую экспертную разметку.

## Критерии

- старый контракт, новый контракт и обязательства относятся к одному продукту;
- идентификаторы сценариев, обязательств и потребителей уникальны;
- версии старого и нового контрактов различаются;
- структура схемы не меняется, поскольку каталог проверяет именно скрытые семантические изменения;
- изменяемые семантические поля соответствуют заявленному семейству;
- каждый активный потребитель покрыт отдельным эталонным решением;
- опасный сценарий имеет глобальный эталон `REJECT`, допустимый - `ACCEPT`;
- эталон и его обоснование физически отделены от входного сценария;
- политика V1-ind вынесена из карточек и фиксирована на уровне семейства;
- списки источников, целей, единиц и областей идентичности не содержат дублей.

## Обнаруженные и устранённые проблемы

1. Эталоны находились внутри YAML-сценариев. Они перенесены в `oracles/development.yaml`.
2. Правила V1-ind находились внутри отдельных сценариев. Они перенесены в `policies/v1-ind.yaml`.
3. Попытка применить baseline по `product_id` дала ложные отклонения: один синтетический продукт используется в нескольких контекстах. Политика зафиксирована как матрица возможностей по семействам изменений.
4. `M-03` одновременно меняет формулу и добавляет необходимый ей источник. `web_events` заранее включён в разрешённый baseline-набор, поэтому V1-ind не получает случайного преимущества по lineage.

## Ограничение вывода

Ревизия подтверждает внутреннюю непротиворечивость каталога и воспроизводимость эталона. Она не подтверждает реалистичность частот сценариев в промышленной среде и не является внешней валидностью.
