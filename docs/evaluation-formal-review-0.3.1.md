# Формальная ревизия evaluation-набора 0.3.1

## Статус

Ревизия выполнена до окончательной заморозки протокола и без запуска валидаторов на evaluation-наборе. Проверялись структура сценариев, отделение oracle, логика эталонных решений, покрытие семейств и пригодность кластеризации. Ревизия является внутренней и не заменяет независимую экспертную разметку.

## Результат проверки

- 40 уникальных evaluation-сценариев не пересекаются с 20 development-сценариями по идентификаторам и точным семантическим переходам;
- набор сбалансирован: 20 опасных и 20 допустимых изменений;
- представлены шесть семейств F1-F6, в каждом есть оба класса;
- входные YAML не содержат `scenario_class`, `expected_decision`, `expected_consumer_decisions` и правил V1-ind;
- oracle хранится отдельно, а ключи ожидаемых локальных решений точно совпадают с активными потребителями сценария;
- изменения каждого сценария ограничены измерениями заявленного семейства, структурные схемы не меняются;
- scoring-only каталог использует шесть кластеров по семантическим семействам, что делает кластерную поправку содержательной для основной метрики на опасных сценариях;
- рабочие experiment, catalog, oracle и analysis plan согласованы с линией протокола 0.3.1;
- `main_e3_executed: false`; результаты H1 в ходе ревизии не рассчитывались.

## Исправленный блокер

Предыдущая карта содержала 20 кластеров, каждый из которых включал один опасный и один допустимый сценарий. Основной эффект H1 рассчитывается только на опасных сценариях, поэтому внутри этого расчёта каждый кластер содержал одно наблюдение и кластерная поправка была эквивалентна сценарию как независимой единице.

В версии 0.3.1.dev4 `cluster_id` определяется семантическим семейством. Теперь в каждом кластере находится несколько опасных и несколько допустимых сценариев с общими правилами генерации и типом продукта. Cluster bootstrap перевыбирает целые семейства, а sign-flip тест агрегирует вклад сценариев внутри семейства. При шести кластерах мощность ограничена, что явно учитывается как ограничение исследования.

## Решение

После исправления кластеризации и выравнивания версий набор проходит внутреннюю формальную ревизию и может перейти к отдельной процедуре окончательной заморозки. Сам факт этой ревизии не является заморозкой, запуском E3 или подтверждением H1.
